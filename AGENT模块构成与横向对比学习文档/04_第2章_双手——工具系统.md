# 第2章 双手——工具系统

> "实习生不会用意念查资料。他需要浏览器、Excel、邮件客户端——这些是他的'双手'。Agent 也一样，LLM 的'脑子'再聪明，没有工具系统这双'手'，也只能坐在椅子上空谈。"

## 2.1 开篇故事：小李的工具箱

早上 10:00，小李开始执行主管交给他的竞品调研任务。

他打开**浏览器**，搜索竞品 A 的官网。找到定价页面后，他把价格信息复制到**Excel** 里。接着他打开竞品 B 的官网，发现价格隐藏了，需要填写表单才能看。小李没有填写，而是换了个搜索引擎，在第三方评测网站上找到了参考价格——这是他**灵活切换工具**的能力。

11:00，小李发现竞品 C 的定价模式很奇怪，想发**邮件**给行业朋友确认一下。他打开邮件客户端，写好邮件，但在点击"发送"前停住了——公司规定不能把内部调研数据发到外部邮箱。他删除了附件，只发了文字描述。这是他**知道什么能做、什么不能做**的职业底线。

下午 2:00，小李想用公司的**数据分析平台**跑一个价格趋势对比。他输入了参数，但平台报错："起始日期格式错误，应为 YYYY-MM-DD"。小李看了一眼，发现自己写成了 "2024/5/1"，改成 "2024-05-01" 后重试，成功了。这是他**遇到参数错误时自己修正**的能力。

4:00，小李整理报告时，发现 Excel 里竞品 A 的数据和官网上看到的不一致。他回头重新打开浏览器核对——**工具的结果是可以被验证和修正的**。

这个过程中，小李的"双手"做了以下几件事：

1. **执行动作**：打开浏览器、操作 Excel、发送邮件——把"想法"变成"真实世界的副作用"
2. **参数校验**：日期格式错了，系统报错，他自己修正
3. **权限控制**：知道什么数据能外发、什么不能
4. **错误反馈**：工具坏了不假装没事，而是明确告诉用户"我失败了，原因是..."

**Agent 的工具系统，就是这套"双手 + 使用规矩"。**

## 2.2 业务概念：工具系统是什么

**工具系统（Tool System）**是 Agent 与外部世界交互的**执行通道**。它负责把 LLM 输出的"函数调用意图"（"我想搜索竞品 A 的价格"）转化为对文件系统、网络、进程的真实操作，并把操作结果以 LLM 能理解的格式回灌。

### 技术定义

工具系统由三个核心组件构成：

1. **Tool（工具）**：一个自描述的可执行单元，包含名称、描述、参数 Schema 和执行逻辑
2. **ToolRegistry（注册中心）**：统一管理工具的注册、发现、查询和调度
3. **Schema（参数契约）**：定义工具接受什么参数、参数类型是什么——这份契约同时给 LLM 看（作为函数签名）和给运行时看（作为校验依据）

> 💡 **名词解释：JSON Schema**
>
> 通俗地说：工具的"说明书"。告诉 LLM "这个工具需要什么参数、参数是什么类型、哪些是必填的"。
>
> 技术定义：一种用于描述 JSON 数据结构的声明式语言。在 Agent 工具系统中，它定义了每个工具的名称、描述、参数类型（string/integer/boolean 等）、必填字段、取值范围等。LLM 根据这个 Schema 生成符合要求的函数调用参数。

### 一句话说清边界

- **工具系统负责**：暴露给 LLM 的函数签名、参数校验、工具执行、错误格式化、权限控制
- **工具系统不负责**：什么时候调用工具（那是编排循环）、工具结果怎么存储（那是记忆系统）、提示词怎么组装（那是 Prompt 构建）

### 没有工具系统会怎样？

如果把工具系统从 Agent 中拿掉：

- LLM 说"我需要搜索竞品 A"，但系统不知道"搜索"是什么、去哪里找、需要什么参数
- LLM 把 `offset=1` 输出成字符串 `"1"`，直接传给文件读取函数，程序抛 `TypeError` 崩溃
- 文件读失败了，有的工具返回 `"File not found"`，有的抛异常，有的返回空字符串——LLM 看到的错误形态各不相同，无法学会"失败后该怎么做"
- 模型可能在未经用户同意的情况下删除文件、执行危险命令——没有任何安全边界

## 2.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，工具系统的**最小可行实现**只需要以下五个要素：

### 要素一：Tool 抽象

每个工具必须有统一的接口：名称、描述、参数 Schema、执行方法。

### 要素二：Registry（注册中心）

统一管理工具的注册和查找。LLM 请求 `"read_file"` 时，Registry 能快速找到对应的工具实例。

### 要素三：Schema 自描述

工具的参数 Schema 必须同时承担两个角色：给 LLM 看的函数签名、给运行时用的校验依据。**同一份数据，零冗余**。

### 要素四：参数校验与类型转换

LLM 输出的参数经常类型错乱（数字写成字符串、布尔写成 `"true"`）。系统需要在执行前做安全的类型转换和严格的参数校验。

### 要素五：错误统一格式化

工具执行失败时，必须以 LLM 能读懂的字符串形式返回错误信息，而不是抛异常打断整个循环。

```python
# 所有 Agent 都必须有的"最小可行工具系统"
# 就像实习生工具箱的"最低配置清单"

class Tool:
    """工具的抽象基类——每个工具必须实现这4个东西"""
    
    @property
    def name(self) -> str: ...           # 工具名字，如 "read_file"
    
    @property  
    def description(self) -> str: ...    # 给 LLM 看的说明
    
    @property
    def parameters(self) -> dict: ...    # JSON Schema——既是说明书也是校验规则
    
    def execute(self, **kwargs) -> str: ...  # 实际干活的方法


class ToolRegistry:
    """工具注册中心——工具箱的'索引本'"""
    
    def __init__(self):
        self._tools = {}                  # 简单字典，名字 -> 工具实例
    
    def register(self, tool: Tool):
        self._tools[tool.name] = tool     # 把新工具放进工具箱
    
    def get_definitions(self) -> list[dict]:
        # 把所有工具的 Schema 转成 OpenAI 格式，交给编排循环发给 LLM
        return [tool.to_schema() for tool in self._tools.values()]
    
    def execute(self, name: str, params: dict) -> str:
        tool = self._tools.get(name)
        if not tool:
            # 工具不存在？告诉 LLM "你没这个工具"，让它换个思路
            return f"Error: Tool '{name}' not found."
        
        # 第一步：宽容转换——LLM 常把数字写成字符串，先试着救一下
        params = tool.cast_params(params)
        
        # 第二步：严格校验——必填字段有没有？类型对不对？范围超没超？
        errors = tool.validate_params(params)
        if errors:
            return f"Error: Invalid parameters: {'; '.join(errors)}"
        
        # 第三步：执行！把 LLM 的意图变成真实世界的动作
        try:
            return tool.execute(**params)
        except Exception as e:
            # 工具自己崩了也要兜住——不能让一个坏工具毁掉整个任务
            return f"Error: {type(e).__name__}: {e}"
```

**这就是"底线"**。少于这五点，Agent 的工具链就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| Tool 抽象 | 每个工具各写各的，新增工具要改遍整个系统 |
| Registry | LLM 说"read_file"，系统找不到对应的执行逻辑 |
| Schema 自描述 | "给 LLM 看的签名"和"实际校验的规则"不同步，LLM 传的参数总被拒 |
| 参数校验 | 类型错误直接崩溃，LLM 没有机会学习和修正 |
| 错误统一格式化 | 不同工具错误形态各异，LLM 无法形成稳定的"错误→修正"策略 |

## 2.4 四个项目的实现对比

四个框架在"底线"之上，各自扩展了不同的能力维度。

### Hermes Agent：自注册 + 生成计数缓存 + Toolset 分组

**设计定位**：模块自注册、去中心化维护、按场景分组——适合工具数量多、跨平台部署的网关型 Agent。

> 💡 **名词解释：自注册（Self-Registration）**
>
> 通俗地说：每个部门自己填一张"设备登记表"，交到一个中央柜子里。新增设备时，只需要在那个部门自己的登记表上添一行，不需要跑到管理中心去更新总表。
>
> 技术定义：每个工具模块在文件顶部通过 `registry.register(...)` 声明自己的元数据（名称、Schema、执行函数等），Registry 通过扫描文件自动收集。避免了"中央清单文件"与"工具实现文件"之间的同步问题。

> 💡 **名词解释：AST 发现（AST Discovery）**
>
> 通俗地说：管理员不用逐个去问"你们部门有没有新设备"，而是直接翻各部门的登记表，看哪些文件上有"register"签名，就知道哪些部门有设备需要登记。
>
> 技术定义：Registry 用 Python 的 AST（抽象语法树）模块扫描 `tools/*.py` 文件，自动识别哪些文件包含顶层的 `registry.register(...)` 调用，然后只 import 这些文件。避免了手动维护工具模块列表。

> 💡 **名词解释：生成计数器（Generation Counter）**
>
> 通俗地说：公司发了一个"版本号"公告板，每次有人登记或注销设备，版本号就加 1。各部门看一眼版本号，如果发现和自己记得的不一样，就知道设备列表有变动，需要去重新查一遍。
>
> 技术定义：Registry 维护一个单调递增的 `_generation` 整数计数器。每次工具注册、注销或 MCP 刷新时 +1。上层缓存以 `(enabled, disabled, generation, config_mtime)` 为 key，当 generation 变化时缓存自动失效——不需要显式的发布/订阅机制。

> 💡 **名词解释：Toolset（工具集）**
>
> 通俗地说：公司把设备按"项目组"分组——IT 组有电脑和打印机，行政组有复印机和传真机。主管给实习生派任务时，可以根据任务类型只给对应的项目组设备，而不是把所有设备都摆出来。
>
> 技术定义：Hermes 将工具按功能分组（如 `file` 组包含 read/write/patch/search，`web` 组包含 search/extract）。不同部署场景（CLI、Discord、cron）可以启用不同的 toolset，控制 LLM 能看到的工具范围。

> 💡 **名词解释：coerce_tool_args（参数强制转换）**
>
> 通俗地说：实习生填申请表时把"年龄"写成了"25岁"而不是"25"，系统在录入前自动把"25岁"转成数字 25，而不是直接退回表格让实习生重填。
>
> 技术定义：在调度入口统一处理 LLM 输出的参数类型漂移。例如把字符串 `"42"` 转成整数 `42`、把单元素标量包成数组。只对有明确模式的值做转换，转换失败则保留原值让后续校验处理。

**关键源码位置**：
- 自注册与 AST 发现：`tools/registry.py:42-74`
- 生成计数器缓存失效：`tools/registry.py:226-279`
- 参数类型纠正：`model_tools.py:540-574`

### nanobot：ABC 基类 + 宽容转换 + 统一错误引导

**设计定位**：Schema 即契约、先 cast 再 validate、错误信息也是 prompt——适合工具数量少、追求极简的个人助手。

> 💡 **名词解释：ABC 基类（Abstract Base Class）**
>
> 通俗地说：公司给所有工具发了一本"标准化手册"，上面写着"每个工具必须有名字、有说明书、有参数表、有执行方法"。如果有人做了一个新工具但没按手册写，系统在启动时就会报错，而不是等到用起来才发现缺东西。
>
> 技术定义：Python 的 `abc.ABC` 配合 `@abstractmethod` 装饰器，强制所有工具子类必须实现 `name`、`description`、`parameters`、`execute` 四个成员。未实现的子类在实例化时会抛出 `TypeError`。

> 💡 **名词解释：cast_params（参数宽容转换）**
>
> 通俗地说：实习生填表格时把"是否已婚"写成了"是"而不是打勾，系统在录入前先看一下——"是"≈"true"，"否"≈"false"，能认出来的就先帮着转一下，认不出来的再让实习生重填。
>
> 技术定义：在参数校验之前，根据 JSON Schema 的类型定义做一次安全的类型转换。例如字符串 `"42"` → 整数 `42`、字符串 `"true"` → 布尔 `True`。转换只对白名单值进行，无法转换的值保留原样，留给 `validate_params` 给出标准错误。

> 💡 **名词解释：_HINT（错误引导提示）**
>
> 通俗地说：实习生做表格填错了，系统不只是说"你错了"，而是多说一句"看看上面的错误，换个思路再试"。这样实习生就不会死盯着同一个格子反复填同一个错误答案。
>
> 技术定义：一个固定的字符串后缀 `\n\n[Analyze the error above and try a different approach.]`，在工具出错时追加到错误信息末尾。引导 LLM 在看到错误后改变策略，而不是重复调用同一个工具。

**关键源码位置**：
- Tool ABC 与 Schema 三合一：`nanobot/agent/tools/base.py:7-181`
- Registry 统一执行入口：`nanobot/agent/tools/registry.py:38-59`
- 参数宽容转换：`nanobot/agent/tools/base.py:55-122`
- JSON Schema 子集校验：`nanobot/agent/tools/base.py:124-170`

```python
# nanobot 的工具系统：像一个个人助理的"标准化工具包"
# 每个工具都有统一的规格，参数类型乱了自动修，错了给明确提示

class Tool(ABC):
    """工具抽象基类——强制每个工具实现4个核心属性"""
    
    @property @abstractmethod
    def name(self) -> str: ...
    
    @property @abstractmethod
    def description(self) -> str: ...
    
    @property @abstractmethod
    def parameters(self) -> dict: ...       # ← 同一份 Schema，三重职责
    
    @abstractmethod
    async def execute(self, **kwargs) -> str: ...
    
    def cast_params(self, params: dict) -> dict:
        """宽容转换：LLM 把数字写成字符串？先救一下。"""
        schema = self.parameters
        return self._cast_object(params, schema)
    
    def _cast_value(self, val, schema):
        target_type = schema.get("type")
        
        # 类型已经对了，直接返回
        if target_type == "integer" and isinstance(val, int) and not isinstance(val, bool):
            return val
        
        # 字符串 "42" → 整数 42（能转则转，不能转保留原样让 validate 报错）
        if target_type == "integer" and isinstance(val, str):
            try:
                return int(val)
            except ValueError:
                return val                  # ← 不抛异常，留给 validate 处理
        
        # 字符串 "true" → 布尔 True（只认白名单）
        if target_type == "boolean" and isinstance(val, str):
            if val.lower() in ("true", "1", "yes"): return True
            if val.lower() in ("false", "0", "no"): return False
            return val                      # ← 不认识的不乱猜
        
        # 数组和对象递归处理
        if target_type == "array" and isinstance(val, list):
            item_schema = schema.get("items")
            return [self._cast_value(item, item_schema) for item in val]
        if target_type == "object" and isinstance(val, dict):
            return self._cast_object(val, schema)
        
        return val
    
    def validate_params(self, params: dict) -> list[str]:
        """严格校验：类型、必填、范围、长度"""
        return self._validate(params, schema, "")
    
    def _validate(self, val, schema, path: str) -> list[str]:
        t, label = schema.get("type"), path or "parameter"
        
        # 类型检查（注意：bool 是 int 的子类，要排除！）
        if t == "integer" and (not isinstance(val, int) or isinstance(val, bool)):
            return [f"{label} should be integer"]
        
        errors = []
        # 枚举检查
        if "enum" in schema and val not in schema["enum"]:
            errors.append(f"{label} must be one of {schema['enum']}")
        
        # 范围检查
        if t in ("integer", "number"):
            if "minimum" in schema and val < schema["minimum"]:
                errors.append(f"{label} must be >= {schema['minimum']}")
        
        # 对象：必填字段 + 递归属性校验
        if t == "object":
            for k in schema.get("required", []):
                if k not in val:
                    errors.append(f"missing required {path + '.' + k if path else k}")
            for k, v in val.items():
                if k in props:
                    errors.extend(self._validate(v, props[k], path + "." + k if path else k))
        
        return errors
    
    def to_schema(self) -> dict:
        """直接把 parameters 塞进 OpenAI 格式——零复制零重构"""
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.parameters,   # ← 直接复用！
            },
        }


class ToolRegistry:
    async def execute(self, name: str, params: dict) -> str:
        _HINT = "\n\n[Analyze the error above and try a different approach.]"
        
        tool = self._tools.get(name)
        if not tool:
            # 工具不存在时，告诉 LLM 有哪些可用工具——引导它自我纠正
            return f"Error: Tool '{name}' not found. Available: {', '.join(self.tool_names)}"
        
        try:
            params = tool.cast_params(params)       # ① 先宽容转换
            errors = tool.validate_params(params)    # ② 再严格校验
            if errors:
                return f"Error: Invalid parameters: {'; '.join(errors)}{_HINT}"
            
            result = await tool.execute(**params)    # ③ 执行！
            
            # 工具自己返回了错误（如 "Error: File not found"）
            if isinstance(result, str) and result.startswith("Error"):
                return result + _HINT                 # ④ 加一句"换个思路试试"
            return result
        except Exception as e:
            # 最后一层兜底：工具自己崩了也不让循环断
            return f"Error executing {name}: {e}{_HINT}"
```

### OpenClaw：多层策略管道 + 循环检测 + Schema 规范化

**设计定位**：工具系统是整个 Agent 的安全边界与资源管理器——适合 7×24 运行的生产级网关。

> 💡 **名词解释：多层策略管道（Tool Policy Pipeline）**
>
> 通俗地说：公司有一套层层递进的审批制度——先过部门主管、再过安全部、最后过总经理。每一层都可以说"不行"，但层与层之间有优先级：总经理的决定可以覆盖部门主管的决定。这样既能精细化管理，又不会因某一层卡死而导致整个流程瘫痪。
>
> 技术定义：OpenClaw 在工具调用前应用 6 层策略过滤（profile → provider → global → agent → group → sandbox），后层覆盖前层。`stripPluginOnlyAllowlist` 防御机制确保如果某层策略只包含插件工具，系统会剥离该限制而不是禁用核心工具——"fail open for core tools"的安全哲学。

> 💡 **名词解释：循环检测（Tool Loop Detection）**
>
> 通俗地说：实习生反复打开同一个网页查同一个信息，查了三遍还在查——主管看不下去了，说"你已经查过这个了，换个思路"。如果实习生继续执迷不悟，主管直接阻止他再打开这个网页。
>
> 技术定义：在工具执行前检测模型是否陷入重复调用模式。支持三种检测：同一工具+相同参数的重复调用、`process` 工具的 poll 无进展、两个工具之间的 ping-pong 交替。Critical 级别直接阻断执行，warning 级别每 10 次一个桶发出警告。

> 💡 **名词解释：Schema 规范化（Schema Normalization）**
>
> 通俗地说：公司要给不同客户发产品说明书，但每个客户对格式要求不同——A 客户不要加粗字体，B 客户不要表格，C 客户只要纯文本。于是公司在发送前，先把说明书统一转成"标准格式"，再按客户要求去掉不适用的元素。
>
> 技术定义：不同 LLM Provider 对 JSON Schema 的兼容性要求不同（Gemini 拒绝约束关键字、OpenAI 拒绝根级 anyOf、xAI 拒绝验证关键字）。OpenClaw 在工具调用前，将 Schema 扁平化为单一 object 并按当前 Provider 清洗不兼容关键字。

> 💡 **名词解释：沙箱（Sandbox）**
>
> 通俗地说：公司给实习生一间独立的办公室，里面只有他需要用的文件和设备。即使实习生不小心把咖啡洒在电脑上，也只会影响他这间办公室，不会影响公司主服务器。
>
> 技术定义：通过 Docker 容器隔离命令执行环境，文件操作通过 `SandboxFsBridge` 转发为容器内命令。默认配置下 exec 工具在 sandbox 中运行，需要显式提权才能访问 gateway 主机。防止模型生成的危险命令（如 `rm -rf /`）破坏宿主环境。

### OpenCode：Zod Schema + Tool.define DSL + 权限内嵌

**设计定位**：Schema 即类型、权限即工具属性、截断是必需品——适合和 IDE 深度集成的 Agent。

> 💡 **名词解释：Zod Schema**
>
> 通俗地说：公司用一套"智能表单系统"来定义每个工具的参数要求——这套系统不仅能生成给实习生看的"填表说明"，还能在实习生交表时自动检查有没有填错。更厉害的是，这套系统是用编程语言写的，如果参数要求变了，代码会自动报错提醒开发者同步修改。
>
> 技术定义：TypeScript 的运行时类型校验库。用 Zod 定义参数 Schema 后，可以自动生成 JSON Schema 给 LLM、在运行时自动校验参数类型、还能推导 TypeScript 类型——一份定义，三重用途。

> 💡 **名词解释：Tool.define DSL**
>
> 通俗地说：公司给每个工具发了一个"标准化模具"——只要把工具的描述、参数表、执行逻辑塞进去，模具就会自动给工具加上"参数检查"和"输出截断"功能。开发者只需要关注工具本身的业务逻辑，不需要重复写检查代码。
>
> 技术定义：OpenCode 定义工具的高阶函数。接收工具的 `id` 和 `init` 工厂函数，返回一个延迟初始化的工具定义对象。内部对 `execute` 做 AOP 式包装：先 Zod 校验参数，再执行真实逻辑，最后自动截断输出。

> 💡 **名词解释：权限内嵌（Permission Embedding）**>
> 通俗地说：不是在公司门口设一个统一的安检门，而是每个办公室门口都有自己的门禁系统。会议室的门禁只要刷卡就能进，但财务室的门禁还需要指纹。每个房间根据自己的安全级别设置不同的准入规则。
>
> 技术定义：每个工具在自己的 `execute` 方法内部显式调用 `ctx.ask` 请求权限审批。例如 bash 工具用 tree-sitter 解析命令 AST，针对性地为 `rm`/`cp` 等敏感操作请求权限。不同工具的权限粒度可以不同——`ls` 不需要审批，但 `rm -rf /` 会被拦截。

**关键源码位置**：
- Tool.define DSL：`packages/opencode/src/tool/tool.ts:48-88`
- 权限审批内嵌：`packages/opencode/src/tool/bash.ts:139-159`
- 输出截断：`packages/opencode/src/tool/tool.ts:74-83`
- 模型级工具过滤：`packages/opencode/src/tool/registry.ts:131-172`

// OpenCode 的工具系统：像一个和设计软件深度集成的"插件生态"
// 每个工具用 Zod 定义参数——Schema 即类型，类型即校验

// ── Tool.define：高阶函数包装，自动加校验和截断 ──
export function define<Parameters extends z.ZodType>(
    id: string,
    init: (ctx?: InitContext) => Promise<{
        description: string
        parameters: Parameters                // ← Zod Schema，同时是类型 + 校验 + JSON Schema
        execute(args: z.infer<Parameters>, ctx: ToolContext): Promise<Result>
    }>
) {
    return {
        id,
        init: async (initCtx) => {
            const toolInfo = await init(initCtx);
            const originalExecute = toolInfo.execute;
            
            // AOP 式包装：自动加参数校验 + 输出截断
            toolInfo.execute = async (args, ctx) => {
                try {
                    toolInfo.parameters.parse(args);   // ① Zod 自动校验
                } catch (error) {
                    throw new Error(
                        `The ${id} tool was called with invalid arguments: ${error}.\n` +
                        `Please rewrite the input so it satisfies the expected schema.`
                    );
                }
                
                const result = await originalExecute(args, ctx);  // ② 执行真实逻辑
                
                // ③ 自动截断：防止大输出撑爆上下文
                if (result.metadata.truncated === undefined) {
                    const truncated = await Truncate.output(result.output, {}, initCtx?.agent);
                    result.output = truncated.content;
                    result.metadata.truncated = truncated.truncated;
                }
                return result;
            };
            return toolInfo;
        },
    };
}

export const BashTool = Tool.define("bash", async () => {
    return {
        description: "Execute shell commands",
        parameters: z.object({
            command: z.string(),              // 要执行的命令
            workdir: z.string().optional(),   // 工作目录
            timeout: z.number().optional(),   // 超时（毫秒）
        }),
        async execute(params, ctx) {
            // 用 tree-sitter 解析 Bash AST，提取敏感操作
            const tree = await parser().then(p => p.parse(params.command));
            const directories = new Set<string>();
            const patterns = new Set<string>();
            
            for (const node of tree.rootNode.descendantsOfType("command")) {
                const command = extractCommand(node);
                
                // 检测文件操作命令（cd/rm/cp/mv 等）
                if (["cd", "rm", "cp", "mv", ...].includes(command[0])) {
                    for (const arg of command.slice(1)) {
                        const resolved = await fs.realpath(path.resolve(cwd, arg));
                        if (!Instance.containsPath(resolved)) {
                            // 访问了工作区外的目录！请求权限
                            directories.add(path.dirname(resolved));
                        }
                    }
                }
                
                // 所有非 cd 命令都需要 bash 权限审批
                if (command.length && command[0] !== "cd") {
                    patterns.add(commandText);
                }
            }
            
            // 权限审批：访问外部目录
            if (directories.size > 0) {
                await ctx.ask({
                    permission: "external_directory",
                    patterns: Array.from(directories).map(d => `${d}/*`),
                });
            }
            
            // 权限审批：执行 bash 命令
            if (patterns.size > 0) {
                await ctx.ask({
                    permission: "bash",
                    patterns: Array.from(patterns),
                });
            }
            
            // 执行命令，流式上报输出到 UI
            const proc = spawn(params.command, { shell, cwd });
            proc.stdout.on("data", chunk => {
                ctx.metadata({ metadata: { output: accumulatedOutput } });
            });
            
            return { title: params.description, output, metadata: { exit: proc.exitCode } };
        },
    };
});

## 2.5 独特高价值设计：各项目的闪光点

### Hermes Agent：自注册 + AST 发现的"零魔法"模式

每个工具模块在文件顶部执行 `registry.register(...)` 完成自注册，`discover_builtin_tools()` 用 AST 扫描识别哪些文件包含注册调用，然后自动 import（`tools/registry.py:42-74`）。

**解决的问题**：避免了"中央清单文件"与"工具实现文件"之间的同步问题，新增工具只需改一个文件。同时避免了装饰器的"魔法"——AST 只识别顶层的 `registry.register` 调用，函数体内的不会被误识。

**什么场景值得借鉴**：工具数量多、多人协作、频繁新增工具的项目。

### Hermes Agent：Generation 计数器缓存失效

Registry 维护一个单调递增的 `_generation` 计数器，每次注册/注销/MCP 刷新时 +1。调用方以 `(enabled, disabled, generation, config_mtime)` 为 key 做 memo（`tools/registry.py:226-279`）。

**解决的问题**：不需要显式的发布/订阅机制，不需要调用方知道"哪个工具变了"——计数器变了，所有缓存自然失效。这是"cache invalidation 问题"的最简解。

**什么场景值得借鉴**：任何有"运行时可变配置 + 上层缓存"的系统。

### nanobot：`cast_params` 的宽容转换

在 `validate_params` 之前先做 `cast_params`，吸收 LLM 的类型噪声（`nanobot/agent/tools/base.py:55-122`）。字符串 `"42"` → 整数 `42`、字符串 `"true"` → 布尔 `True`。转换失败时保留原值，让 validate 给出标准错误——绝不"猜"。

**解决的问题**：开放权重模型（DeepSeek、Qwen 等）输出的参数类型经常错乱。直接校验会拒绝这些参数，迫使 LLM 多走一轮，浪费 token。

**什么场景值得借鉴**：使用开放权重模型或参数类型要求严格的场景。

### nanobot：`_HINT` 错误引导

工具出错时，在错误信息末尾追加固定提示：`"\n\n[Analyze the error above and try a different approach.]"`（`nanobot/agent/tools/registry.py:40`）。

**解决的问题**：LLM 看到错误后的默认行为是"再试一次同样的调用"。一句明确的"换个思路"能显著降低无意义重试。

**什么场景值得借鉴**：所有 Agent 系统。错误信息也是 prompt 的一部分。

### OpenClaw：六层策略管道

`profile → provider → global → agent → group → sandbox` 六层过滤（`src/agents/tool-policy-pipeline.ts:17-108`），后层覆盖前层。`stripPluginOnlyAllowlist` 防御机制防止用户配置失误导致核心工具被禁用。

**解决的问题**：多租户、多 Agent、多 Provider 的生产环境中，需要细粒度的权限矩阵。单层策略无法表达"这个群组用这套工具、那个 Agent 用那套工具"。

**什么场景值得借鉴**：对外服务、多用户共享的 Agent 系统。

### OpenClaw：循环检测与断路器

`detectToolCallLoop` 在工具执行前检测三种循环模式：同一工具+参数重复、poll 无进展、ping-pong 交替（`src/agents/pi-tools.before-tool-call.ts:91-194`）。Critical 级别直接阻断，warning 级别每 10 次一个桶避免日志风暴。

**解决的问题**：模型在长任务中可能"钻牛角尖"（如反复读取同一个文件），消耗大量 token 和计算资源。这比单纯的迭代预算更智能——它不是"跑满 N 轮就停"，而是"发现重复无用功就停"。

**什么场景值得借鉴**：任何可能执行长时间自动任务的 Agent。

### OpenCode：Zod Schema 作为单一真相源

`Tool.define` 用 Zod 定义参数 Schema，自动生成 JSON Schema 给 LLM，同时在 `execute` 前自动 `parse` 校验（`packages/opencode/src/tool/tool.ts:48-88`）。一份 Schema，三重职责：类型定义 + 运行时校验 + LLM 函数签名。

**解决的问题**：手写 JSON Schema 和手写类型校验容易不同步——加字段时只改了一处，导致 LLM 知道但运行时拒绝，或运行时接受但 LLM 不知道。

**什么场景值得借鉴**：使用 TypeScript 构建 Agent 系统的项目。

### OpenCode：权限审批下沉到工具层

每个工具在自己的 `execute` 内部调用 `ctx.ask` 请求权限（`packages/opencode/src/tool/bash.ts:139-159`）。bash 工具用 tree-sitter 解析 AST 提取敏感操作，针对性地请求权限——`ls` 不需要审批，但 `rm -rf /` 会被捕获。

**解决的问题**：统一的"前置权限拦截器"无法做到精细化（如按命令模式、按文件路径），而让每个工具自己决定"什么情况下需要审批"是最准确的。

**什么场景值得借鉴**：需要精细权限控制的 Agent 系统（如 IDE 插件操作用户代码）。

## 2.6 设计思想总结

如果我要自己构建一个 Agent 系统，工具系统部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | Tool 抽象 | name / description / parameters / execute 四元组 |
| ☐ | Registry | 注册/查找/执行的唯一入口 |
| ☐ | Schema 自描述 | 同一份 Schema 给 LLM 看 + 给运行时校验 |
| ☐ | 参数类型转换 | 吸收 LLM 的类型噪声（str → int / str → bool） |
| ☐ | 参数校验 | 类型、必填、范围、长度检查 |
| ☐ | 错误统一格式化 | 返回字符串而非抛异常，错误信息引导 LLM 修正 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 工具数量多、频繁新增 | 自注册 + AST 发现 | Hermes |
| 需要缓存工具列表 | Generation 计数器失效 | Hermes |
| 按场景启用/禁用工具 | Toolset 分组 | Hermes |
| 使用开放权重模型 | cast_params 宽容转换 + _HINT | nanobot |
| 多租户/多 Agent 权限 | 多层策略管道 | OpenClaw |
| 防止模型"钻牛角尖" | 循环检测与断路器 | OpenClaw |
| 跨 Provider 部署 | Schema 规范化（扁平化 + 清洗） | OpenClaw |
| 需要沙箱隔离 | 三级主机安全模型 | OpenClaw |
| TypeScript 项目 | Zod Schema 单一真相源 | OpenCode |
| IDE 集成/精细化权限 | 权限审批内嵌到工具层 | OpenCode |
| 大输出工具（文件/命令） | 自动截断 + 落盘 | OpenCode |

### 最重要的三条经验

1. **Schema 即契约，契约即 prompt**：工具的参数 Schema 不是给开发者看的"类型声明"，而是 LLM 推理的输入。错误信息、可用工具列表、字段路径——这些都是 prompt 工程的一部分。

2. **先 cast 再 validate**：LLM 90% 的参数"错误"是类型问题（数字写成字符串）。先宽容转换、再严格校验，能把大部分"伪错误"消化掉，显著降低重试轮次。

3. **工具系统是安全边界，不是能力列表**：工具系统的设计核心不是"让模型能调用多少函数"，而是"在什么条件下、以什么权限、用什么参数调用函数"。OpenClaw 的六层策略和 OpenCode 的权限内嵌都体现了这一点。
