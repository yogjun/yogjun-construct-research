# 第3章 笔记本——记忆系统

> "实习生不是金鱼，他能把上周学到的东西记到今天。但笔记本写满了怎么办？重要的和不重要的怎么分类？这就是记忆系统要解决的问题。"

---

## 3.1 开篇故事：小李的笔记本

实习生小李入职第三周，笔记本已经写了大半本。

**第一层：随时翻看的速记页**

笔记本前几页是"用户偏好"——主管喜欢简洁的邮件、周二下午不要打扰他、项目代码用 snake_case。这些小李每做一件事之前都会瞄一眼，确保不出错。

**第二层：按日期归档的工作日志**

后面是按日期写的工作记录：1月15日重构了 auth 模块、1月18日调研了三个竞品的定价……这些内容平时不翻，但如果主管问"上周我让你做了什么"，小李能快速翻到那一页。

**第三层：信息爆炸时的取舍**

到了第四周，笔记本快写满了。小李面临一个问题：新信息往哪记？他做了三个决策：

- **扔掉旧打印稿**：那些已经处理完、不会再查的临时资料（比如 grep 全仓库的冗长输出），直接撕掉
- **压缩长篇记录**：把十页的调研过程缩写成一段话的摘要，保留结论和行动项
- **保留核心速记**：前几页的"用户偏好"永远不删，那是干活的基本盘

**Agent 的记忆系统，就是这位实习生的笔记本管理术。**

但 Agent 面临一个实习生没有的问题：LLM 的"脑子"（上下文窗口）只有那么大，能同时装下的信息有限。如果无限累积，它会"装不下"而直接报错。所以记忆系统不只是"记"，更要会"丢"和"压缩"。

---

## 3.2 业务概念：记忆系统是什么

**记忆系统（Memory System）**是 Agent 的"信息生命周期管家"。它负责回答三个问题：

1. **记什么？** —— 原始对话历史、工具执行结果、用户偏好、项目上下文
2. **存哪？** —— 内存、本地文件、数据库、外部向量存储
3. **怎么丢？** —— 当信息总量超过 LLM 上下文窗口时，如何压缩或丢弃旧信息

### 技术定义

记忆系统不是简单的"把聊天记录存进文件"。它分为两个层次：

- **短期记忆（上下文）**：当前会话中的完整对话历史，直接作为 `messages` 数组传给 LLM。它有硬上限——模型的上下文窗口。
- **长期记忆**：跨会话持久化的事实和日志，在每次会话启动时注入到 system prompt 中，让 Agent"记得"你是谁、你们之前聊过什么。

> 💡 **名词解释：上下文窗口（Context Window）**
>
> 通俗地说：实习生的"短期记忆容量"。他只能同时在脑子里记住最近几轮对话的内容，太多了就"装不下"。
>
> 技术定义：LLM 单次推理能处理的最大 token 数量。超过这个数量，API 会直接返回错误。不同模型的窗口大小不同（如 GPT-4 为 128K，Claude 3.5 为 200K）。

### 一句话说清边界

- **记忆系统负责**：存储对话历史、管理上下文溢出、跨会话持久化关键事实
- **记忆系统不负责**：决定用什么工具（那是工具系统）、决定循环何时终止（那是编排循环）、决定提示词怎么写（那是 Prompt 构建）

### 没有记忆系统会怎样？

如果把记忆系统从 Agent 中拿掉：

- **每次对话都是"初次见面"**：Agent 记不住你的偏好，每次都要重新问"你是谁""你要什么格式"
- **上下文无限膨胀**：对话长了以后，API 直接报 `context_length_exceeded` 错误，Agent 当场崩溃
- **工具结果淹没有效信号**：`cat` 一个大文件可能输出数万字符，如果不清理，下一轮对话里这些垃圾数据会挤占真正重要的用户指令

## 3.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，记忆系统的**最小可行实现**只需要以下四个要素：

### 要素一：消息持久化

对话历史必须能被保存到磁盘，进程重启后不丢失。最简单的方式：每轮对话结束后把 `messages` 追加写入 JSONL 文件。

### 要素二：会话隔离

用户 A 的记忆不能泄露给用户 B。每个会话必须有独立的标识（session key），读写记忆时按 key 隔离。

### 要素三：上下文窗口保护

当消息累积接近 LLM 的上下文窗口上限时，必须有某种机制释放空间——要么丢弃旧消息，要么压缩成摘要。什么都不做 = API 报错 = 循环崩溃。

### 要素四：长期记忆注入

至少能把一些跨会话的事实（如用户偏好）在会话启动时注入 system prompt，让 Agent"有备而来"。

```python
# 所有 Agent 都必须有的"最小可行记忆系统"
# 就像实习生的"最低配置笔记本"

class MinimalMemory:
    def __init__(self, session_key, context_window):
        self.session_key = session_key
        self.context_window = context_window
        self.messages = []          # ① 当前会话的对话历史
        self.long_term = {}         # ③ 跨会话的长期事实
    
    def load_long_term(self):
        # 启动时从磁盘读取"用户偏好"等长期记忆
        path = f"memories/{self.session_key}/profile.json"
        if os.path.exists(path):
            self.long_term = json.load(open(path))
    
    def append_message(self, role, content):
        self.messages.append({"role": role, "content": content})
        # 每轮追加写入 JSONL——即使进程崩溃也不丢数据
        with open(f"sessions/{self.session_key}.jsonl", "a") as f:
            f.write(json.dumps({"role": role, "content": content}) + "\n")
    
    def build_messages_for_llm(self):
        # 把长期记忆拼到 system prompt 里
        system = "You are a helpful assistant."
        if self.long_term:
            system += f"\nUser preferences: {self.long_term}"
        
        all_msgs = [{"role": "system", "content": system}] + self.messages
        
        # ③ 上下文窗口保护：如果超限，从最旧的消息开始删
        while estimate_tokens(all_msgs) > self.context_window:
            # 不能删 system prompt，从第二个消息（最早的 user/assistant）开始删
            if len(all_msgs) > 1:
                all_msgs.pop(1)
            else:
                break
        
        return all_msgs
```

**这就是"底线"**。少于这四点，Agent 的记忆就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 消息持久化 | 进程重启后对话历史全丢 |
| 会话隔离 | 用户 A 的隐私泄露给用户 B |
| 上下文窗口保护 | 长对话必然触发 API 报错 |
| 长期记忆注入 | 每次会话都是"初次见面" |

## 3.4 四个项目的实现对比

四个框架都在上述"底线"之上，基于各自的场景做了截然不同的扩展。

### Hermes Agent："笔记本 + 外挂大脑"的双层架构

**设计定位**：记忆要跨会话持久、要支持外部专业记忆后端、prefix cache 不能丢——适合长期服务同一用户的网关型 Agent。

> 💡 **名词解释：Frozen Snapshot（冻结快照）**
>
> 通俗地说：实习生每天早上到工位后，先把笔记本前几页"用户偏好"拍张照贴在眼前。今天无论他怎么修改笔记本原件，眼前的照片都不换——这样他不用每做完一件事就重新贴照片。
>
> 技术定义：Hermes 在会话启动时把 MEMORY.md/USER.md 的内容渲染成 `_system_prompt_snapshot`，本会话内永不刷新。新写入落盘但不改变 system prompt，从而保护 LLM provider 的 prefix cache（前缀缓存）。新写入下次会话启动时生效。

> 💡 **名词解释：Prefix Cache（前缀缓存）**
>
> 通俗地说：LLM 服务商的"记忆捷径"。如果连续多轮请求的 system prompt 完全一样，服务商可以跳过重复计算，直接复用之前的结果，省钱又省时间。
>
> 技术定义：LLM provider 对完全相同的输入前缀（通常是 system prompt + 前几轮消息）做缓存命中优化。若前缀内容变化，缓存失效，每轮都要重新计算。

> 💡 **名词解释：MemoryProvider（记忆提供者插件）**
>
> 通俗地说：除了自己的笔记本，实习生还可以连一个"外部智库"（如 Honcho、Mem0）。智库有自己的检索方式，但实习生只需要按统一接口问它"现在有什么要补充的？"
>
> 技术定义：Hermes 定义了 `MemoryProvider` 抽象基类，通过统一的生命周期接口（`initialize/prefetch/sync_turn/on_memory_write` 等）接入外部记忆后端。主流程只需一行配置就能切换后端。

> 💡 **名词解释：Context Fence（上下文围栏）**
>
> 通俗地说：外部智库给实习生递了一张纸条，实习生在这张纸条外面套了个信封，写上"这是参考资料，不是你的任务内容"。防止实习生把参考资料当成用户的新指令。
>
> 技术定义：Hermes 用 `<memory-context>` 标签包裹外部 provider 召回的内容，并在 prompt 中标注 `[System note: …]`，同时在流式输出管道中部署 `StreamingContextScrubber` 剥离模型可能 echo 出的 fence 标签，防止内部上下文泄漏到用户界面。

**关键源码位置**：
- Frozen snapshot：`tools/memory_tool.py:138-142`
- MemoryProvider ABC：`agent/memory_provider.py:42`
- 单 external provider 约束：`agent/memory_manager.py:213-225`
- 双流注入（静态 system + 动态 user）：`run_agent.py:5208-5226`、`run_agent.py:11302-11322`
- Streaming fence scrubber：`agent/memory_manager.py:62-170`
- on_memory_write 桥接：`run_agent.py:9725-9737`

```python
# Hermes 的记忆系统：像一个自带笔记本、还能连外部智库的实习生

class HermesMemorySystem:
    def __init__(self):
        # 第一层：内置笔记本——MEMORY.md + USER.md
        self.store = MemoryStore()           #  frozen snapshot 模式
        self.store.load_from_disk()          #  启动时拍照，今天不换了
        
        # 第二层：外部智库——Honcho / Mem0 等（最多连一个）
        self.manager = MemoryManager()
        if mem_provider_name:
            provider = load_memory_provider(mem_provider_name)
            self.manager.add_provider(provider)   # 第二个 external 会被拒绝
    
    def on_turn_start(self, user_msg):
        # 每轮开始前，问问外部智库有什么补充资料
        self._prefetch_cache = self.manager.prefetch_all(user_msg)
    
    def build_api_messages(self, messages, current_user_idx):
        api_msgs = []
        for idx, msg in enumerate(messages):
            api_msg = msg.copy()              # 关键：复制，不污染原始 messages
            
            # 动态召回 → 只拼到当前 user 消息的末尾（不碰 system prompt）
            if idx == current_user_idx and self._prefetch_cache:
                fenced = build_memory_context_block(self._prefetch_cache)
                api_msg["content"] += "\n\n" + fenced
            
            api_msgs.append(api_msg)
        return api_msgs
    
    def on_tool_call(self, name, args):
        if name == "memory":
            # 内置工具：写笔记本
            result = self.store.execute(args)
            # 桥接：把新事实同步给外部智库
            self.manager.on_memory_write(args["action"], args["target"], args["content"])
            return result
        elif self.manager.has_tool(name):
            # 外部工具：honcho_search / mem0_profile 等
            return self.manager.handle_tool_call(name, args)
    
    def on_turn_end(self, user_msg, final_response):
        # 本轮结束，把对话同步给外部智库持久化
        self.manager.sync_all(user_msg, final_response)
        # 后台预热：为下一轮提前做召回
        self.manager.queue_prefetch_all(user_msg)
```

### nanobot："笔记本 + 归档柜"的双层文件存储

**设计定位**：记忆要极简、零外部依赖、人可读写——适合个人助手场景。

> 💡 **名词解释：Consolidation（记忆固化）**
>
> 通俗地说：实习生的笔记本快写满了，他拿出一支红笔，把十页的工作记录浓缩成一段话的摘要，把结论性的信息抄到"长期事实"页，把过程性的信息按日期存到"工作日志"。
>
> 技术定义：nanobot 用 LLM 将一段原始消息历史转换为结构化摘要。LLM 被强制调用 `save_memory` 工具，输出 `memory_update`（更新 MEMORY.md）和 `history_entry`（追加 HISTORY.md）。

> 💡 **名词解释：User Turn Boundary（用户轮次边界）**
>
> 通俗地说：实习生整理笔记时，不会在"用户说了一半的话"中间撕纸。他只会在"用户说完一整句话"的地方下剪刀。
>
> 技术定义：nanobot 在 `pick_consolidation_boundary()` 中只在 `role == "user"` 的消息处选择截断点。因为 LLM API 要求 `tool` 消息必须紧跟 `assistant` 的 `tool_calls`，在 assistant-tool 中间截断会产生"孤儿工具结果"导致 API 报错。

**关键源码位置**：
- 双层 MemoryStore：`nanobot/agent/memory.py:75-100`
- LLM 驱动固化：`nanobot/agent/memory.py:114-199`
- 用户轮次边界：`nanobot/agent/memory.py:254-274`
- 降级归档：`nanobot/agent/memory.py:201-219`
- Token 超限触发：`nanobot/agent/memory.py:302-357`

```python
# nanobot 的记忆系统：一个只用笔记本和归档柜的极简主义者

class NanobotMemorySystem:
    def __init__(self, workspace):
        self.store = MemoryStore(workspace)   # MEMORY.md + HISTORY.md
        self.consolidator = MemoryConsolidator(...)
    
    async def maybe_consolidate(self, session):
        """检查笔记本是否写满了，满了就整理。"""
        target = self.context_window // 2      # 目标是压缩到窗口的一半
        estimated, _ = self.estimate_tokens(session)
        
        if estimated < self.context_window:
            return                              # 还写得下，不用整理
        
        # 写满了——开始一轮轮整理
        for round_num in range(5):            # 最多整理 5 轮
            if estimated <= target:
                break
            
            # 找一个合适的"下剪刀点"（只在用户说完一整轮的地方剪）
            boundary = self.pick_consolidation_boundary(session, estimated - target)
            if boundary is None:
                break                           # 找不到安全边界，停止
            
            chunk = session.messages[session.last_consolidated:boundary[0]]
            
            # 把这一 chunk 交给 LLM 做摘要固化
            success = await self.store.consolidate(chunk, provider, model)
            if not success:
                break                           # 固化失败，停止本轮
            
            session.last_consolidated = boundary[0]   # 标记"已归档到这里"
            self.sessions.save(session)                # 存盘
            estimated, _ = self.estimate_tokens(session)
```

### OpenClaw："文件图书馆 + 索引卡片"的混合检索架构

**设计定位**：记忆要以 Markdown 为唯一真相、支持语义检索、任何后端故障都能优雅降级——适合 7×24 小时运行的生产级网关。

> 💡 **名词解释：Hybrid Search（混合搜索）**
>
> 通俗地说：实习生要在图书馆找资料，他同时用了两种方法——"按内容意思搜"（向量语义相似度）和"按关键词搜"（BM25 全文检索）。前者能找到"Mac Studio gateway host"和"the machine running the gateway"这种同义不同词的记录，后者擅长找精确 ID 和代码符号。最后把两种结果合并起来。
>
> 技术定义：OpenClaw 的 `MemoryIndexManager.search()` 并行执行向量检索和关键词检索，按 `vectorScore * 0.7 + textScore * 0.3` 的加权公式合并结果。当 embedding provider 不可用时自动降级为纯 BM25（FTS-only）。

> 💡 **名词解释：MMR（Maximal Marginal Relevance，最大边际相关性）**
>
> 通俗地说：实习生搜"项目部署"，图书馆返回了 5 条结果——但前 3 条都是同一篇文档的不同段落。MMR 就是帮他在"相关"和"不重复"之间做平衡的筛选器。
>
> 技术定义：MMR 是一种重排序算法，每次选择既与查询相关、又与已选结果差异最大的条目。OpenClaw 用 Jaccard 相似度（基于 token 集合）快速计算内容重复度，避免重复调用 embedding 模型。

> 💡 **名词解释：Temporal Decay（时间衰减）**
>
> 通俗地说：半年前的笔记自然没有昨天的笔记重要。实习生在整理搜索结果时，会给老笔记自动降权。
>
> 技术定义：OpenClaw 对按日期命名的记忆文件（如 `memory/2024-01-15.md`）应用指数衰减公式，age 越大 score 越低。 evergreen 文件（如 `MEMORY.md`）跳过衰减。

> 💡 **名词解释：Compaction（上下文压缩）**
>
> 通俗地说：笔记本写满了，实习生不是撕掉旧页，而是把十页旧笔记缩写成一页摘要，然后用摘要替代旧页。
>
> 技术定义：当消息 token 数超过预算时，OpenClaw 用专门的 summarization agent 生成结构化摘要（保留 Active tasks / Decisions / TODOs 等），替代被压缩的旧消息。支持分阶段摘要（大上下文先分块并行摘要，再合并）。

> 💡 **名词解释：Context Pruning（上下文剪枝）**
>
> 通俗地说：实习生发现笔记本里贴了很多冗长的打印稿（比如 `cat` 了一个大文件的输出）。他没扔掉整页，只是把打印稿中间重复的部分剪掉，保留开头和结尾。
>
> 技术定义：OpenClaw 的 `pruner.ts` 逆向扫描消息历史，将超过阈值的老旧 tool result 做 `softTrim`（保留 head + tail，中间用"…"替换），或直接标记为 `compacted` 丢弃。

**关键源码位置**：
- 混合搜索：`src/memory/manager.ts:282-364`
- MMR 重排：`src/memory/mmr.ts:116-183`
- 时间衰减：`src/memory/temporal-decay.ts:121-167`
- Embedding 弹性架构：`src/memory/embeddings.ts:166-286`
- Compaction：`src/agents/compaction.ts:333-396`
- Context Pruning：`src/agents/pi-extensions/context-pruning/pruner.ts:188-221`
- FallbackMemoryManager：`src/memory/search-manager.ts:118-139`

```typescript
// OpenClaw 的记忆系统：像一家有图书馆、索引系统和应急预案的机构

class OpenClawMemorySystem {
    async search(query: string) {
        // ① 混合搜索：向量 + 关键词并行
        const keywordResults = await this.searchKeyword(query);
        const vectorResults = await this.searchVector(query);
        
        // 合并并按加权分数排序
        const merged = mergeHybridResults(keywordResults, vectorResults, {
            vectorWeight: 0.7, textWeight: 0.3
        });
        
        // ② MMR 重排：平衡相关性与多样性
        return mmrRerank(merged, { lambda: 0.7 });
    }
    
    async compactIfNeeded(messages) {
        // ③ 上下文压缩：超限时用 agent 生成结构化摘要
        if (estimateTokens(messages) > budget) {
            const summary = await summarizeInStages({
                messages,
                parts: 2,   // 分两块并行摘要，再合并
                instructions: "保留 Active tasks / Decisions / TODOs"
            });
            return replaceOldMessagesWithSummary(messages, summary);
        }
        return messages;
    }
    
    async pruneOldToolResults(messages) {
        // ④ 上下文剪枝：逆向扫描，把老旧 tool 输出标记为 compacted
        for (const msg of reversed(messages)) {
            if (msg.role === "toolResult" && isOldEnough(msg)) {
                // softTrim：保留头尾，中间截断
                msg.content = softTrim(msg.content, { headChars: 500, tailChars: 500 });
            }
        }
    }
}
```

### OpenCode："三抽屉档案柜"的数据库存储

**设计定位**：记忆要结构化、支持流式加载、压缩策略分级——适合和 IDE 深度集成、需要处理大量文件操作输出的场景。

> 💡 **名词解释：Part（消息片段）**
>
> 通俗地说：一条消息不只是"一段文字"，可能包含"文字 + 工具调用 + 文件附件 + 压缩摘要"等多个部分。OpenCode 把消息的每个部分都拆成独立的"片段"来存储。
>
> 技术定义：OpenCode 的三层存储中，`PartTable` 存储消息的各个内容片段（text / tool / reasoning / compaction / media 等）。一个 Message 可以有多个 Part，支持精细化查询和独立更新。

> 💡 **名词解释：Prune（剪枝）**
>
> 通俗地说：实习生在整理档案柜时，发现有些工具输出的打印稿已经没用了。他不是压缩，而是直接在这些打印稿上盖个"已处理"的章，以后不再翻它们。
>
> 技术定义：OpenCode 的 `SessionCompaction.prune()` 逆向扫描消息历史，将超过阈值的老旧 tool 输出标记 `compacted = Date.now()`。下次 `filterCompacted` 加载时会跳过这些 part。不调用 LLM，纯计算操作。

**关键源码位置**：
- 三层存储模型：`packages/opencode/src/session/session.sql.ts:11-67`
- 消息流式加载：`packages/opencode/src/session/message-v2.ts:731-782`
- filterCompacted：`packages/opencode/src/session/message-v2.ts:809-825`
- Compaction agent prompt：`packages/opencode/src/session/compaction.ts:173-199`
- Prune 策略：`packages/opencode/src/session/compaction.ts:50-99`
- isOverflow 检测：`packages/opencode/src/session/compaction.ts:32-48`

```typescript
// OpenCode 的记忆系统：像一个有精密分类档案柜的设计工作室

class OpenCodeMemorySystem {
    // 三层存储：Session → Message → Part
    async saveMessage(sessionID, role, content) {
        const msg = await Session.updateMessage({ sessionID, role, ... });
        await Session.updatePart({ message_id: msg.id, type: "text", content });
    }
    
    async loadMessagesForLLM(sessionID) {
        // 流式倒序加载，遇到已压缩的摘要就停止
        const stream = MessageV2.stream(sessionID);
        const messages = await MessageV2.filterCompacted(stream);
        
        // 转换为 AI SDK 兼容格式（处理不同 provider 的媒体支持差异）
        return MessageV2.toModelMessages(messages, model);
    }
    
    async afterLoop(sessionID, tokens, model) {
        // ① 先剪枝：把老旧 tool 输出标记为 compacted
        await SessionCompaction.prune({ sessionID });
        
        // ② 再检测是否溢出：溢出时创建 compaction 任务
        if (SessionCompaction.isOverflow({ tokens, model })) {
            await SessionCompaction.create({ sessionID, ... });
            // 下轮 loop 会执行 compaction agent 生成摘要
        }
    }
}
```

## 3.5 独特高价值设计：各项目的闪光点

### Hermes Agent：Frozen Snapshot —— 用"延迟生效"换"缓存命中"

`tools/memory_tool.py:11-14` 的注释说得明白："Mid-session writes update files on disk immediately but DO NOT change the system prompt — this preserves the prefix cache for the entire session."

**解决的问题**：如果每轮都刷新 system prompt，LLM provider 的 prefix cache 会完全失效，长会话的 API 成本和延迟会暴涨。

**什么场景值得借鉴**：任何需要长会话（>10 轮）且使用支持 prefix cache 的 LLM provider（如 Anthropic）的系统。代价是"用户说'记住我喜欢简洁'后，本会话不会立刻变简洁"——但这个代价远小于 prefix cache 失效的代价。

### Hermes Agent：Streaming Context Scrubber —— 状态机防泄漏

`agent/memory_manager.py:99-140` 实现了一个跨 chunk 边界的状态机，精确 hold 住"可能是 tag 前缀"的最长后缀。

**解决的问题**：模型可能在流式输出中 echo 出 `<memory-context>` 标签，把内部召回内容泄漏给用户。

**什么场景值得借鉴**：任何把"非用户输入的内容"注入到消息中的系统（如 RAG 召回、系统指令）。单靠 prompt 里的"不要输出"不够，必须在输出管道里部署机械防护。

### nanobot：降级归档 —— 智能失败后的"保底"

`nanobot/agent/memory.py:201-219`：当 LLM 固化连续失败 3 次后，不再尝试摘要，直接把原始消息 dump 到 HISTORY.md。

**解决的问题**：LLM API 可能因网络、配额、模型故障而失败，如果失败就丢弃消息，用户数据会永久丢失。

**什么场景值得借鉴**：所有依赖 LLM 做"数据转换"的系统。LLM 不是 100% 可靠，必须有不依赖 LLM 的 fallback 路径。

### nanobot：用户轮次边界 —— 4 行代码保住 API 兼容性

`nanobot/agent/memory.py:266-272`：只在 `role == "user"` 处选择截断点。

**解决的问题**：OpenAI/Anthropic 等 provider 要求 `tool` 消息必须紧跟 `assistant` 的 `tool_calls`。如果在 assistant-tool 中间截断，会产生"孤儿工具结果"导致 API 400 错误。

**什么场景值得借鉴**：任何需要对消息列表做"截断/压缩/摘要"的 Agent 系统。

### OpenClaw：Embedding 弹性架构 —— 从 Hybrid 到 FTS-only 的优雅降级链

`src/memory/embeddings.ts:166-286`：auto 模式下依次尝试 local → remote providers，全部因缺 API key 失败时返回 `provider: null`，进入 FTS-only 模式。`FallbackMemoryManager` 在 QMD 失败后自动切回内置索引。

**解决的问题**：Embedding API 随时可能不可用（缺 key、网络故障、provider 宕机），不能因为记忆检索挂了就让整个 Agent 停摆。

**什么场景值得借鉴**：任何依赖外部 API 的生产级系统。降级链条越长，系统的鲁棒性越强。

### OpenClaw：Context Pruning 的 head+tail 保留策略

`src/agents/pi-extensions/context-pruning/pruner.ts:188-221`：对 tool result 保留开头和结尾，中间替换为"…"。

**解决的问题**：`cat` 大文件或 `grep` 全仓库的输出往往中间都是重复内容，但开头（import/声明）和结尾（结论/错误）更有价值。

**什么场景值得借鉴**：任何需要处理"冗长结构化输出"的系统（如日志、代码文件、JSON 数据）。

### OpenCode：三级压缩策略 —— 从"轻量丢弃"到"智能摘要"到"应急剥离"

- **Prune**：不调用 LLM，直接标记老旧 tool 输出为 compacted
- **Compaction**：调用专门的 compaction agent 生成结构化摘要
- **Overflow**：剥离媒体附件，保留文本

**解决的问题**：不同阶段的上下文压力需要不同成本的释放策略。一开始就调用 LLM 做摘要太浪费，先 cheap prune 掉明显冗余的，不行再上 compaction。

**什么场景值得借鉴**：任何上下文窗口紧张、且工具输出占大头的系统（如 IDE 集成型 Agent）。

## 3.6 设计思想总结

如果我要自己构建一个 Agent 系统，记忆系统部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 消息持久化 | 每轮追加写入，进程崩溃不丢数据 |
| ☐ | 会话隔离 | 不同用户/会话的记忆严格隔离 |
| ☐ | 上下文窗口保护 | 消息累积接近上限时，必须有丢弃/压缩/截断机制 |
| ☐ | 长期记忆注入 | 至少支持把跨会话事实注入 system prompt |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 长会话 + prefix cache 敏感 | Frozen snapshot（加载时冻结，本会话不刷新） | Hermes |
| 需要语义检索跨会话记忆 | Hybrid search（向量+关键词）+ MMR 重排 | OpenClaw |
| 个人助手 / 极简部署 | 双层 Markdown 文件 + LLM 驱动固化 | nanobot |
| IDE 集成 / 大量文件操作 | 三级压缩（Prune → Compaction → Overflow） | OpenCode |
| 外部记忆后端可插拔 | MemoryProvider ABC + 单 external 约束 | Hermes |
| 流式输出防泄漏 | Streaming fence scrubber 状态机 | Hermes |
| Embedding API 不可靠 | 弹性降级链：hybrid → vector → FTS-only | OpenClaw |

### 最重要的三条经验

1. **"静态进 system，动态进 user"是 prefix cache 的标准答案**：任何需要每轮变化的内容（如召回结果）都不该进 system prompt，否则 prefix cache 完全失效。

2. **降级路径比最优路径更重要**：nanobot 的原始归档、OpenClaw 的 FTS-only 降级、Hermes 的 provider 失败静默，都体现了一个原则——记忆系统的故障不能阻塞主流程。

3. **消息边界是硬约束，不是风格问题**：nanobot 的"只在 user 轮次截断"和 OpenClaw 的 `repairToolUseResultPairing` 都在处理同一件事——消息序列的合法性是 API 层面的硬性要求，不是可选项。
