# 第8章 注意力分配——上下文管理

> "实习生面前堆了五十页资料，但他不能全塞进脑子里。他必须决定：哪些放眼前、哪些压箱底、哪些干脆扔掉。上下文管理，就是让 Agent 学会这套'注意力分配'。"

---

## 8.1 开篇故事：小李的资料整理术

实习生小李接到了一个大任务：整理公司过去一年的销售数据。

主管给了他三个文件夹：A 文件夹是"原始数据"（Excel 表格，共 200MB）、B 文件夹是"分析模板"（几个空表和公式说明）、C 文件夹是"参考资料"（去年的报告和行业白皮书）。

小李没有把所有资料都摊在桌上。他的做法很讲究：

**第一层：眼前只放最重要的**

他把 B 文件夹的"分析模板"放在眼前——这是今天的核心任务框架。然后把 A 文件夹中本月的数据挑出来，其余的先放抽屉里。C 文件夹的白皮书他只翻了目录，发现跟今天的任务关系不大，直接放回了书架。

**第二层：给资料标优先级**

小李在每张资料上贴了标签："必读"（分析模板）、"参考"（本月数据）、"备用"（历史数据）。当桌面快满了，他会把"备用"资料先收进抽屉，腾出空间给新的"必读"。

**第三层：资料太多时的取舍**

当他发现即使只放"必读"，桌面还是堆不下时，他做了一件更聪明的事：把三个月前的"必读"资料缩写成一段话的摘要，然后把原始资料扔掉。摘要只占原来 1/10 的空间，但关键结论都保留了。

**Agent 的上下文管理，就是这位实习生的"资料整理术"。**

LLM 的上下文窗口就像小李的桌面——面积有限。如果 Agent 把什么资料都往里塞，要么"桌面堆不下"（API 返回 context_length_exceeded 错误），要么"重要资料被挤到看不见的地方"（用户指令被淹没在冗余信息中）。上下文管理要做的，就是决定**什么进、什么出、以什么形态出、以什么时机出**。

---

## 8.2 业务概念：上下文管理是什么

**上下文管理（Context Management）**是 Agent 系统的"信息策展人"。它负责将多源异构数据（系统指令、历史对话、工具结果、环境信息、项目规范等）组装成 LLM 可直接消费的消息格式，同时在上下文窗口的硬约束下进行裁剪、压缩和适配。

### 技术定义

上下文管理不是简单的"把 messages 数组传给 LLM"。它包含三个层次：

1. **组装层**：把 system prompt、历史消息、当前用户输入、运行时元数据拼成完整的对话上下文
2. **过滤层**：去除冗余信息（如已被压缩的旧消息、过时的工具结果），防止无效信息淹没有效信号
3. **适配层**：按不同 LLM provider 的能力差异调整消息格式（如工具结果中的媒体支持、消息角色序列合法性）

> 💡 **名词解释：上下文窗口（Context Window）**
>
> 通俗地说：实习生的"桌面面积"。他只能在桌上摊开这么多资料，超出部分要么收进抽屉，要么扔掉。
>
> 技术定义：LLM 单次推理能处理的最大 token 数量。当输入消息的总 token 数超过这个值时，API 会直接返回 400/413 错误。不同模型的窗口大小差异很大（GPT-4 为 128K，Claude 3.5 为 200K，部分小模型只有 4K）。

### 一句话说清边界

- **上下文管理负责**：消息怎么组装、token 怎么估算、超限时怎么压缩、不同 provider 怎么适配
- **上下文管理不负责**：具体工具怎么实现（那是工具系统）、对话历史怎么长期存储（那是记忆系统）、提示词怎么写（那是 Prompt 构建）

### 没有上下文管理会怎样？

如果把上下文管理从 Agent 中拿掉：

- **API 直接报错**：消息一多就 context_length_exceeded，Agent 当场崩溃
- **工具结果淹没对话**：`cat` 一个大文件可能输出数万 token，挤占用户指令的空间
- **消息序列非法**：连续两条 user 消息、孤儿 tool_result 都会导致 provider 返回 400
- **跨 provider 不兼容**：给 OpenAI 发 Anthropic 格式的消息，直接报错

## 8.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，上下文管理的**最小可行实现**只需要以下四个要素：

### 要素一：消息组装

把 system prompt、历史消息、当前用户输入按正确的角色序列拼接成 `messages` 数组。

### 要素二：Token 估算

在发送给 LLM 之前估算总 token 数，提前发现超限风险。不需要 100% 精确，但不能差一个数量级。

### 要素三：溢出处理

当估算值接近上下文窗口上限时，必须有释放空间的机制——要么丢弃旧消息，要么压缩成摘要。什么都不做 = API 报错。

### 要素四：消息序列合法性检查

确保消息序列满足 provider 的格式要求（如 OpenAI 要求 `tool` 消息必须紧跟 `assistant` 的 `tool_calls`，不能有连续同角色消息等）。

```python
# 所有 Agent 都必须有的"最小可行上下文管理"
# 就像实习生的"最低配置资料整理术"

def build_context(system_prompt, history_messages, user_input, max_tokens):
    messages = [
        {"role": "system", "content": system_prompt},
        *history_messages,
        {"role": "user", "content": user_input}
    ]
    
    # ② token 估算：粗略但够用
    estimated = estimate_tokens(messages)
    
    # ③ 溢出处理：如果超了，从最旧的消息开始删
    while estimated > max_tokens and len(messages) > 2:
        # 不能删 system prompt 和当前用户输入
        # 只删中间的旧消息
        removed = messages.pop(1)  # 删第二条（最早的 user/assistant）
        estimated = estimate_tokens(messages)
        
        # 如果删掉的是 tool_call，必须同时删掉对应的 tool_result
        if removed.get("role") == "assistant" and removed.get("tool_calls"):
            # 找到并删除对应的 tool_result
            call_ids = {tc["id"] for tc in removed["tool_calls"]}
            messages = [m for m in messages 
                       if not (m.get("role") == "tool" 
                               and m.get("tool_call_id") in call_ids)]
    
    # ④ 序列合法性检查：确保没有连续同角色消息
    messages = merge_consecutive_same_role(messages)
    
    return messages
```

**这就是"底线"**。少于这四点，Agent 的上下文管理就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 消息组装 | LLM 看不到 system prompt 或历史消息 |
| Token 估算 | 不知道什么时候该压缩，全靠 API 报错才知道 |
| 溢出处理 | 长对话必然触发 context_length_exceeded |
| 序列合法性 | 消息格式错误导致 provider 持续 400 |

## 8.4 四个项目的实现对比

四个框架在"底线"之上，基于各自的场景诉求做了截然不同的扩展。

### Hermes Agent："预算化流水线"的三段式管道

**设计定位**：上下文是带预算的写入流，每一步都要计量、预算、压缩——适合长会话、多模型切换、prefix cache 敏感的生产级网关。

> 💡 **名词解释：ContextCompressor（上下文压缩器）**
>
> 通俗地说：实习生的"资料缩印机"。当桌面堆不下时，他把三个月前的完整资料缩印成一页摘要，保留关键结论，腾出空间给新资料。
>
> 技术定义：Hermes 的 `ContextCompressor` 在上下文接近上限时，将旧消息替换为 LLM 生成的结构化摘要。摘要包含 12 个固定 section（Active Task / Goal / Completed / Blocked / Files 等），而非简单截断。支持多轮迭代式更新和辅助模型降级 fallback。

> 💡 **名词解释：Preflight Compression（预飞压缩）**
>
> 通俗地说：小李在动手做报表之前，先检查一下桌面够不够大。如果不够，他先把旧资料收进抽屉，再开始工作——而不是做到一半发现没地方放。
>
> 技术定义：Hermes 在每次 API 调用前先做 token 估算，如果超过阈值，先执行压缩再发送请求。这避免了"发送到一半被 provider 拒绝"的尴尬。入口在 `run_agent.py:11011-11069`。

> 💡 **名词解释：Ephemeral System Prompt（临时系统提示）**
>
> 通俗地说：主管每天会给小李一张"今日特别注意事项"便利贴。小李把它贴在眼前，但下班就撕掉——它不会进入正式的笔记本。
>
> 技术定义：Hermes 将 system prompt 分为"常驻部分"（cached，整个 session 不变）和"临时部分"（ephemeral，每轮变化）。临时部分在 API 调用时拼接但不写入持久化存储，从而保护 prefix cache 的稳定性。

> 💡 **名词解释：Prompt Caching（提示缓存）**
>
> 通俗地说：LLM 服务商的"记忆捷径"。如果连续多轮的 system prompt 完全一样，服务商可以跳过重复计算，直接复用之前的结果——省钱又省时间。
>
> 技术定义：Anthropic 等 provider 支持的优化特性，对完全相同的输入前缀做缓存命中。Hermes 通过保持 system prompt 字节级稳定 + 在 user 消息中注入变化内容，最大化 cache 命中率。

**关键源码位置**：
- Preflight 压缩判定：`run_agent.py:11011-11069`
- ContextCompressor 主流程：`agent/context_compressor.py:1278-1479`
- 尾部 token 预算保护：`agent/context_compressor.py:1195-1257`
- Tool 配对修复：`agent/context_compressor.py:1041-1099`
- 摘要生成 + fallback：`agent/context_compressor.py:899-994`
- Ephemeral 注入：`run_agent.py:11347-11386`
- Prompt caching 断点：`agent/prompt_caching.py:41-72`

```python
# Hermes 的上下文管理：像一个有严格预算纪律的资料整理员

class HermesContextManager:
    def build_request(self, messages):
        # ① 获取常驻 system prompt（session 内缓存，不重建）
        sys_prompt = self._cached_system_prompt or self._build_system_prompt()
        
        # ② Preflight：估算总 token（含 tools schema！），过阈值就先压再发
        estimated = self.estimate_tokens(messages, sys_prompt, self.tools)
        if estimated >= self.threshold:
            for _ in range(3):           # 最多压 3 轮，大 session 可能需要多压几次
                messages = self.compressor.compress(messages)
                if self.estimate_tokens(messages, sys_prompt, self.tools) < self.threshold:
                    break
        
        # ③ 拼接临时 system prompt（只参与本次请求，不入库）
        effective = sys_prompt
        if self.ephemeral_system_prompt:
            effective += "\n\n" + self.ephemeral_system_prompt
        
        api_messages = [{"role": "system", "content": effective}] + messages
        
        # ④ 应用 Anthropic prompt caching（4 个 cache 断点）
        if self._use_prompt_caching:
            api_messages = apply_anthropic_cache_control(api_messages)
        
        return api_messages
    
    def compress(self, messages):
        # 压缩流程：不是简单截断，而是生成结构化摘要
        head = messages[:self.protect_first_n]       # 头部：最早几条受保护
        tail = self._find_tail_by_tokens(messages)   # 尾部：按 token 预算保护最近消息
        middle = messages[len(head):len(tail)]       # 中间：可压缩区
        
        # 用辅助模型生成 12-section 结构化摘要
        summary = self._generate_summary(middle)
        
        # 修复压缩后的 tool_call/result 配对断裂
        result = head + [{"role": "user", "content": summary}] + tail
        return self._sanitize_tool_pairs(result)
```

### nanobot："轻量装配工"的 ContextBuilder

**设计定位**：上下文管理要极简、零外部依赖、消息序列合法性优先——适合个人助手场景。

> 💡 **名词解释：RuntimeContext（运行时上下文）**
>
> 通俗地说：小李每次开始工作前，都会在便签上写下"现在是周几、几点、我在哪个办公室"。这张便签他贴在当前任务资料旁边，但下班就扔掉——不会存档。
>
> 技术定义：nanobot 的 `ContextBuilder` 在每轮对话中生成包含当前时间、渠道、Chat ID 等运行时元数据的字符串。它被合并到当前 user 消息中，而非作为独立消息插入——避免连续同角色消息被 provider 拒绝。

> 💡 **名词解释：Message Sanitization（消息消毒）**
>
> 通俗地说：小李下班前整理桌面，把临时便签撕掉、把过长的打印稿截断、把照片换成标签——只保留精华存档。
>
> 技术定义：nanobot 在 `_save_turn()` 中对即将持久化的消息执行三项消毒：截断超长工具结果（>16K 字符）、剥离 RuntimeContext（避免过时时间戳污染历史）、将图片 base64 替换为 `"[image]"` 占位符。

**关键源码位置**：
- RuntimeContext 合并到 user message：`nanobot/agent/context.py:129-144`
- 丢弃非 user 开头历史：`nanobot/session/manager.py:46-64`
- 消息消毒（_save_turn）：`nanobot/agent/loop.py:458-491`
- 工具结果截断：`nanobot/agent/loop.py:466-467`

```python
# nanobot 的上下文管理：一个只带便签和剪刀的极简主义者

class NanobotContextManager:
    def build_messages(self, session, current_message):
        # ① 获取历史消息，丢弃前缀非 user 的（避免孤儿 tool_result）
        history = session.get_history()
        
        # ② 构建 system prompt（身份 + 记忆 + 技能）
        system = self.build_system_prompt()
        
        # ③ 运行时元数据合并到 user 消息，避免连续同角色
        runtime_ctx = self._build_runtime_context()
        merged_user = f"{runtime_ctx}\n\n{current_message}"
        
        return [
            {"role": "system", "content": system},
            *history,
            {"role": "user", "content": merged_user}
        ]
    
    def save_turn(self, session, messages):
        # ④ 持久化前消毒：截断、剥离、过滤
        for m in messages:
            if m["role"] == "tool" and len(m["content"]) > 16000:
                m["content"] = m["content"][:16000] + "\n... (truncated)"
            elif m["role"] == "user":
                # 剥离 RuntimeContext，只保留用户原文
                m["content"] = self._strip_runtime_context(m["content"])
        session.messages.extend(messages)
```

### OpenClaw："多层漏斗"的分级过滤管道

**设计定位**：上下文是稀缺资源，不同来源的信息需要不同的预算策略——适合需要处理大量文件操作、工具输出冗长的生产级场景。

> 💡 **名词解释：Bootstrap Budget（引导预算）**
>
> 通俗地说：主管给小李一本"新员工手册"，但规定"你只能带前三章去工位，后面章节想看再回去取"。
>
> 技术定义：OpenClaw 对注入到 system prompt 中的工作区文件（如 `CLAUDE.md`、`README.md`）设置独立的字符预算。分为 per-file limit（单文件上限）和 total limit（所有文件总上限），超限则截断并记录截断原因。

> 💡 **名词解释：Tool Result Context Guard（工具结果上下文守卫）**
>
> 通俗地说：小李的打印机每次最多出 50 页。如果一次打印任务超过 50 页，打印机自动只打前 25 页和后 25 页，中间用"……"代替。
>
> 技术定义：OpenClaw 在消息发往 LLM 之前拦截超长的工具结果。分为两层：单结果上限（不超过上下文窗口的 50%）和总量上限（所有消息不超过 75%）。超限后从最旧的工具结果开始 compact，保留 head+tail。

> 💡 **名词解释：Context Window Guard（上下文窗口守卫）**
>
> 通俗地说：公司规定"桌面小于 30cm×30cm 的工位不适合做报表"。如果小李的工位太小，他直接被分配到别的岗位。
>
> 技术定义：OpenClaw 在配置层面检查模型上下文窗口大小。低于 32K 时发出警告，低于 16K 时直接阻断运行——因为在这种极限窗口下，compaction 和截断机制会频繁触发，体验极差。

**关键源码位置**：
- Bootstrap 预算分析：`src/agents/bootstrap-budget.ts:164-221`
- 工具结果守卫：`src/agents/pi-embedded-runner/tool-result-context-guard.ts:154-182`
- 上下文窗口守卫：`src/agents/context-window-guard.ts:57-74`
- Compaction 多阶段摘要：`src/agents/compaction.ts:264-331`
- 上下文剪枝：`src/agents/pi-extensions/context-pruning/pruner.ts:188-221`

```typescript
// OpenClaw 的上下文管理：像一家有严格预算部门的机构

class OpenClawContextManager {
    async buildRequest(messages, model) {
        // ① Bootstrap 预算：控制注入的工作区文件大小
        const bootstrap = await this.loadBootstrapFiles();
        const budget = analyzeBootstrapBudget(bootstrap, {
            bootstrapMaxChars: 4000,
            bootstrapTotalMaxChars: 8000
        });
        
        // ② 工具结果守卫：截断超长 tool 输出
        enforceToolResultContextBudgetInPlace({
            messages,
            contextBudgetChars: model.contextWindow * 0.75,
            maxSingleToolResultChars: model.contextWindow * 0.5
        });
        
        // ③ 上下文窗口守卫：小窗口模型直接阻断
        const guard = evaluateContextWindowGuard({
            tokens: model.contextWindow,
            warnBelow: 32000,
            hardMin: 16000
        });
        if (guard.shouldBlock) {
            throw new Error("Context window too small for safe operation");
        }
        
        // ④ 溢出时 compaction（agent 生成结构化摘要）
        if (this.isOverflow(messages, model)) {
            messages = await this.compactMessages(messages, model);
        }
        
        return messages;
    }
}
```

### OpenCode："信息组装车间"的上下文流水线

**设计定位**：上下文管理是多源异构数据的策展过程——适合和 IDE 深度集成、需要处理多种文件类型和 provider 差异的场景。

> 💡 **名词解释：InstructionPrompt（指令提示）**
>
> 通俗地说：小李每打开一个项目文件夹，系统会自动把该文件夹和上级目录里的"项目规范文档"贴到他眼前。不同项目的规范不同，但他不需要手动去找。
>
> 技术定义：OpenCode 的 `InstructionPrompt` 按文件路径向上查找 `AGENTS.md`/`CLAUDE.md` 等指令文件，并加载到 system prompt 中。支持邻近发现（monorepo 中不同子项目有不同规范）和去重（同一指令不会被重复加载）。

> 💡 **名词解释：Provider-specific Prompt（Provider 专属提示）**
>
> 通俗地说：不同主管有不同的沟通习惯。给 A 主管的报告要加页码，给 B 主管的要加摘要。小李在交报告前会根据主管是谁调整格式。
>
> 技术定义：OpenCode 根据模型类型（GPT/Claude/Gemini 等）注入不同的 system prompt 片段。这些 prompt 以 `.txt` 文件形式存储，按 `model.api.id` 字符串匹配加载。

> 💡 **名词解释：toModelMessages（消息格式转换）**
>
> 通俗地说：不同公司的报表格式不同。小李交报告前要把内部格式转换成目标公司要求的格式——有的公司只接受纯文本，有的接受带图片的。
>
> 技术定义：OpenCode 将内部的 `Part` 格式转换为 AI SDK 兼容的 `ModelMessage` 格式。处理不同 provider 的媒体支持差异（如 OpenAI 只支持字符串 tool result，Anthropic 支持 content 数组）。

**关键源码位置**：
- 环境信息组装：`packages/opencode/src/session/system.ts:29-53`
- Provider 专属 prompt：`packages/opencode/src/session/system.ts:19-27`
- 指令文件动态加载：`packages/opencode/src/session/instruction.ts:72-115`
- 邻近指令发现：`packages/opencode/src/session/instruction.ts:168-191`
- 消息格式转换：`packages/opencode/src/session/message-v2.ts:496-555`

```typescript
// OpenCode 的上下文管理：像一个精密的信息组装车间

class OpenCodeContextManager {
    async buildContext(sessionID, model) {
        // ① 加载历史消息，过滤已压缩的
        const stream = MessageV2.stream(sessionID);
        const messages = await MessageV2.filterCompacted(stream);
        
        // ② 组装环境信息（工作目录、git 状态、平台、日期）
        const environment = await SystemPrompt.environment(model);
        
        // ③ 加载项目指令（AGENTS.md / CLAUDE.md，向上查找）
        const instructions = await InstructionPrompt.system();
        
        // ④ Provider 专属 prompt（GPT/Claude/Gemini 各有不同）
        const providerPrompt = SystemPrompt.provider(model);
        
        // ⑤ 拼接 system prompt
        const system = [...environment, ...instructions, ...providerPrompt];
        
        // ⑥ 转换为 AI SDK 格式（处理 provider 差异）
        const modelMessages = MessageV2.toModelMessages(messages, model);
        
        return { system, messages: modelMessages };
    }
}
```

### 四项目核心差异对比表

| 维度 | Hermes Agent | nanobot | OpenClaw | OpenCode |
|------|-------------|---------|----------|----------|
| **核心策略** | 三段式管道（system + messages + tools），Preflight 压缩 | 轻量装配（ContextBuilder + _save_turn 消毒） | 多层漏斗过滤（Bootstrap → History → Tool → Compaction） | 信息策展流水线（Environment → Instruction → Filter → Adapt） |
| **溢出处理** | Preflight + 响应后 + 错误恢复，12-section 结构化摘要 | 记忆系统的 consolidation（LLM 固化） | Compaction + Pruning + Bootstrap 截断 | Prune + Compaction（依赖记忆系统） |
| **压缩触发时机** | 请求前预检、响应后检测、错误恢复三种时机 | Token 超限触发 consolidation | 上下文窗口溢出、手动 `/compress` | 溢出检测后创建 compaction 任务 |

## 8.5 独特高价值设计：各项目的闪光点

### Hermes Agent：Token 预算化的尾部保护

`agent/context_compressor.py:1195-1257`：把"保护最近 N 条消息"换成"保护最近的 N 千 token 消息"。

**解决的问题**：固定条数保护对工具结果体积差异极大的场景失效。一个 50KB 的 `write_file` result 顶得上 30 个普通 turn——如果按 `protect_last_n=20` 保护，要么巨型 result 全保了导致压不下来，要么用更激进的条数把真正最近的对话也压走。

**什么场景值得借鉴**：任何需要处理"体积差异极大消息"的系统（如文件操作、日志查看、代码搜索）。

### Hermes Agent：摘要的"反指令性"措辞

`agent/context_compressor.py:37-51`：摘要消息自带 `[CONTEXT COMPACTION — REFERENCE ONLY]` wrapper，明确告诉模型"这是背景参考，不是当前指令"。

**解决的问题**：LLM 可能把摘要中提到的用户问题当作"当前需要回答的问题"，导致回声循环（issue #11475）。

**什么场景值得借鉴**：任何用 LLM 生成摘要并插入到对话中的系统。

### Hermes Agent：Tool 配对的边界乱切 + 终点对齐

`agent/context_compressor.py:1041-1099`：允许压缩边界乱切，再统一修复孤儿 tool_call/result。

**解决的问题**：OpenAI 协议要求 tool_call 和 tool_result 必须配对。压缩边界很难 100% 对齐这种配对。

**什么场景值得借鉴**：任何需要对消息列表做"截断/压缩/摘要"的系统。

### nanobot：RuntimeContext 合并到 user message

`nanobot/agent/context.py:129-144`：将时间戳等运行时元数据拼接到 user 消息中，而非作为独立消息。

**解决的问题**：OpenAI 等 provider 拒绝连续同角色消息（user 后不能直接跟另一个 user）。

**什么场景值得借鉴**：任何需要注入"每轮变化的元数据"的系统。

### nanobot：持久化前的消息消毒

`nanobot/agent/loop.py:458-491`：截断超长工具结果、剥离 RuntimeContext、替换图片 base64 为占位符。

**解决的问题**：防止历史记录"慢性中毒"——动态时间戳和超大内容进入持久化后，下次加载时 token 数瞬间爆炸。

**什么场景值得借鉴**：所有需要持久化对话历史的系统。

### OpenClaw：Bootstrap 预算控制

`src/agents/bootstrap-budget.ts:164-221`：对注入 system prompt 的工作区文件设置 per-file 和 total 两级预算。

**解决的问题**：`CLAUDE.md`、`README.md` 可能很大，不加限制会在每次请求时重复消耗大量 token。

**什么场景值得借鉴**：任何需要注入"项目级文档"到 system prompt 的系统。

### OpenClaw：工具结果上下文守卫

`src/agents/pi-embedded-runner/tool-result-context-guard.ts:154-182`：在消息发往 LLM 之前截断超长工具结果， preemptive 而非 reactive。

**解决的问题**：与其等整个上下文溢出后再处理，不如在工具结果进入消息流时就进行截断。

**什么场景值得借鉴**：任何工具输出可能产生大量数据的系统（如文件操作、日志查看）。

### OpenCode：邻近指令发现

`packages/opencode/src/session/instruction.ts:168-191`：按文件路径向上查找指令文件，支持 monorepo 中不同子项目有不同规范。

**解决的问题**：项目根目录的全局规范可能不适用于子项目，子项目需要自己的局部规范。

**什么场景值得借鉴**：任何需要在 monorepo 或多模块项目中工作的 Agent 系统。

## 8.6 设计思想总结

如果我要自己构建一个 Agent 系统，上下文管理部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 消息组装 | system + history + user input 的正确拼接 |
| ☐ | Token 估算 | 发送前估算总 token，提前发现超限 |
| ☐ | 溢出处理 | 超限时丢弃旧消息或压缩成摘要 |
| ☐ | 序列合法性 | 修复孤儿 tool result、合并连续同角色消息 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 长会话 + prefix cache 敏感 | Preflight 压缩 + Ephemeral 注入 + Prompt caching | Hermes |
| 极简个人助手 | ContextBuilder + _save_turn 消毒 | nanobot |
| 大量文件操作 / 冗长工具输出 | Bootstrap 预算 + Tool result guard + 多级漏斗 | OpenClaw |
| IDE 集成 / monorepo | 邻近指令发现 + Provider-specific prompt | OpenCode |
| 多模型切换 | 辅助模型摘要 + 多层 fallback | Hermes |
| 消息序列严格性要求高 | Tool 配对 sanitize + 边界对齐 | Hermes |

### 最重要的三条经验

1. **"静态进 system，动态进 user"是 prefix cache 的纪律**：任何每轮变化的内容（时间戳、召回结果、插件上下文）都不该进 system prompt，否则 cache 完全失效。

2. **压缩不是截断，是结构化摘要**：Hermes 的 12-section 模板和 OpenClaw 的 compaction agent 都说明——简单截断会丢失任务连续性，用 LLM 生成保留关键信息的摘要才是正解。

3. **消息消毒和持久化是同一枚硬币的两面**：nanobot 的 `_save_turn()` 展示了"临时元数据绝不进长期存储"的原则。RuntimeContext、超大工具结果、图片 base64 都是"本轮有效、下轮有害"的信息，必须在持久化前剥离。
