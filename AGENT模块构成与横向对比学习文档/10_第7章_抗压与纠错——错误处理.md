# 第7章 抗压与纠错——错误处理

> "实习生小李打错了一个电话，把竞品 B 的价格记成了竞品 C 的。他发现后没有慌，而是重新拨号确认、在笔记本上划掉错字、标注'已更正'。Agent 的错误处理，就是这套'发现错误→分类判断→选择对策→记录复盘'的完整流程。"

---

## 7.1 开篇故事：小李的纠错日记

实习生小李入职第二个月，已经学会了"工作节奏"，也熟悉了各种工具。但人非圣贤，他还是会犯错——而且犯错的方式五花八门。

**第一类：外部世界的"临时故障"**

小李打电话给供应商确认价格，对方说"线路忙，请稍后再拨"。他没有放弃，等了 5 秒再打，通了。如果第一次没打通就汇报"联系不上"，主管会觉得他不够尽力。

**第二类：自己的"操作失误"**

小李用 Excel 公式算总价时，把单元格引用错了，结果差了十倍。他发现数字不合理，回头检查公式，找到错误，重新计算。如果他不复核就直接交报告，后果不堪设想。

**第三类："钻牛角尖"的死循环**

有一次，小李反复打开同一个网页刷新，期待价格会变——但那个页面只是缓存了旧数据。刷了十几次后，他自己都笑了："我是不是傻了？"换了个信息源，问题迎刃而解。

**第四类："不可抗力"的系统性故障**

公司内网突然断了，小李的所有在线工具都用不了。他没有对着黑屏发呆，而是先把能离线做的事做完，等网络恢复后再同步。如果他在断网时疯狂刷新浏览器，只会浪费更多时间。

**Agent 的错误处理，就是教这位实习生：什么时候该重试、什么时候该换方法、什么时候该放弃、什么时候该喊人帮忙。**

但 Agent 比小李更惨——它面对的不是"线路忙"，而是 LLM API 的 429/503/402；不是"公式写错"，而是工具执行抛出的异常；不是"钻牛角尖"，而是模型反复调用同一个工具却不产生进展。错误处理的设计，决定了 Agent 是"越挫越勇"还是"一碰就碎"。

---

## 7.2 业务概念：错误处理是什么

**错误处理（Error Handling）**是 Agent 系统的"免疫系统"。它负责在 LLM 调用失败、工具执行异常、网络波动、上下文溢出等各种故障场景下，让系统从"异常状态"恢复到"可继续推进状态"，或在无法恢复时优雅终止并给用户一个交代。

### 技术定义

Agent 中的错误不是简单的"程序 bug"，而是**外部不可靠世界与内部确定性流程之间的摩擦点**。它分为四个层次：

1. **LLM 层错误**：API 返回 429（限流）、503（过载）、402（账单）、上下文溢出等。这是 Agent 最频繁遇到的错误类型。
2. **工具层错误**：文件不存在、命令执行失败、网络请求超时等。工具是 Agent 的"手"，手会打滑。
3. **协议层错误**：消息序列不合法（如 assistant 发了 tool_calls 但没有对应的 tool 应答）、模型输出格式异常等。
4. **逻辑层错误**：模型陷入死循环（反复调用同一工具）、上下文无限膨胀、预算耗尽等。这是"智能体"特有的错误类型。

> 💡 **名词解释：指数退避（Exponential Backoff）**
>
> 通俗地说：小李第一次打电话占线，等 1 秒再打；第二次还占线，等 2 秒；第三次等 4 秒。每次等待时间翻倍，避免疯狂重试把对方服务器打爆。
>
> 技术定义：一种重试策略，第 n 次重试的等待时间为 `base * 2^(n-1)`，通常加上随机抖动（jitter）防止多个客户端同步重试造成"惊群效应"。

### 一句话说清边界

- **错误处理负责**：识别错误类型、选择恢复策略（重试/降级/终止）、防止错误扩散、保证协议一致性
- **错误处理不负责**：预防错误发生（那是 Prompt 设计和工具校验的事）、修复底层 bug（那是开发者的事）、替用户做决策（那是编排循环的事）

### 没有错误处理会怎样？

如果把错误处理从 Agent 中拿掉：

- **一次 429 就终止会话**：LLM 提供商的瞬时限流是常态，没有重试机制意味着用户频繁看到"请求失败"
- **工具崩溃拖垮整个循环**：一个 `cat` 命令遇到不存在的文件，整个 Agent 进程直接退出
- **错误消息污染上下文**：LLM 返回的畸形错误内容如果写入对话历史，会导致后续每轮都触发 400，形成"毒消息→永久错误"死循环
- **模型钻牛角尖无人制止**：反复调用同一个搜索工具却不产生进展，直到 API 账单爆炸

## 7.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，错误处理的**最小可行实现**只需要以下四个要素：

### 要素一：错误分类

不是所有错误都值得重试。429 可以等一会儿再试，401（认证失败）重试一百次也没用。必须有一个分类器，把错误分为"可重试""需降级""应终止"三类。

### 要素二：重试与退避

对可重试错误（如网络抖动、服务过载），必须实现带上限的重试机制。固定间隔重试会造成惊群，指数退避 + 抖动是标准答案。

### 要素三：工具失败降级

单个工具执行失败不应该终止整个会话。把异常捕获后转成字符串结果（如 `"Error executing tool 'terminal': File not found"`），让模型基于这个错误信息自主规划下一步。

### 要素四：兜底与隔离

任何未被上层捕获的异常，都必须有一个最终兜底，防止进程崩溃。同时，错误内容不能无差别写入对话历史——某些错误（如 LLM 返回的畸形响应）进入历史后会"毒害"后续所有轮次。

```python
# 所有 Agent 都必须有的"最小可行错误处理"
# 就像实习生的"应急手册"——遇到什么情况该怎么办

def agent_loop_with_error_handling(user_input, tools, max_iterations=40):
    messages = [system_message, user_message(user_input)]
    
    for iteration in range(max_iterations):
        try:
            # 实习生向学霸请教——但学霸可能没空（429）或断网了
            response = call_llm_with_retry(messages, tools=tools.get_definitions())
            
        except TransientError as e:   # ① 可重试错误：线路忙，等一会儿再打
            wait = exponential_backoff(attempt=e.retry_count)
            time.sleep(wait)
            continue                    # 回到循环顶部，重新尝试
            
        except FatalError as e:       # ② 不可重试错误：账号被封了，别试了
            return f"任务无法继续：{e.message}"
        
        if response.has_tool_calls:
            messages.append(assistant_message(response.content, response.tool_calls))
            
            for tc in response.tool_calls:
                try:
                    result = tools.execute(tc.name, tc.arguments)
                except Exception as tool_error:   # ③ 工具失败降级
                    # 手滑了没关系，记下来告诉学霸，让他决定下一步
                    result = f"Error executing tool '{tc.name}': {tool_error}"
                
                messages.append(tool_result(tc.id, result))
            continue
        
        else:
            # ④ 毒消息隔离：如果学霸返回的是错误内容，别往笔记本上记
            if response.finish_reason == "error":
                return "抱歉，遇到了技术问题，请稍后重试。"
            
            return response.content
    
    return f"达到最大迭代次数（{max_iterations}），任务未能完成。"
```

**这就是"底线"**。少于这四点，Agent 的错误处理就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 错误分类 | 把认证失败当网络抖动重试 100 次，浪费时间和配额 |
| 重试与退避 | 第一次 429 就直接崩溃，用户体验极差 |
| 工具失败降级 | 一个文件不存在就终止整个会话，前功尽弃 |
| 兜底与隔离 | 毒消息进入历史，导致后续每轮都 400，会话彻底报废 |

## 7.4 四个项目的实现对比

四个框架都在"底线"之上，基于各自的部署场景构建了截然不同的错误处理体系。

### Hermes Agent：结构化分类器 + 优先级恢复流水线

**设计定位**：在多供应商、多协议、多瞬时故障的生产环境中保持"不崩溃、不空转、不放大故障"——适合同时对接十几个 LLM provider 的网关型 Agent。

> 💡 **名词解释：FailoverReason（故障转移原因）**
>
> 通俗地说：实习生的应急手册上列了 17 种故障类型——"线路忙""对方停机""号码错误""账单欠费"……每种类型对应不同的对策。FailoverReason 就是这 17 种类型的标签。
>
> 技术定义：Hermes 在 `agent/error_classifier.py` 中定义的 17 种错误分类标签（如 `rate_limit`、`billing`、`context_overflow`、`timeout` 等）。分类器将任意异常归一到其中一个标签，主循环根据标签选择恢复策略。

> 💡 **名词解释：Jittered Backoff（抖动退避）**
>
> 通俗地说：电梯高峰期，如果所有人都在 5 秒后按按钮，电梯门永远关不上。Hermes 让每个人等一个随机时间再按，大大降低了同时抢电梯的概率。
>
> 技术定义：指数退避基础上增加随机抖动。Hermes 用 `time_ns ^ counter * 0x9E3779B9` 作为随机种子，保证即使 100 个 session 在同一毫秒进入退避，每个的等待时间都不同，避免 thundering herd（惊群效应）。

> 💡 **名词解释：凭证池轮换（Credential Pool Rotation）**
>
> 通俗地说：小李有 5 张电话卡，第一张欠费了立刻换第二张，而不是反复拨打欠费的号码。
>
> 技术定义：Hermes 维护多个 API key 的凭证池。当某个 key 因 rate limit 或 billing 被标记为耗尽时，自动切换到下一个可用 key，而不是在同一 key 上无限重试。

**关键源码位置**：
- 结构化分类器（8 层优先级流水线）：`agent/error_classifier.py:331-570`
- 402 歧义消解（周期配额 vs 真破产）：`agent/error_classifier.py:698-724`
- 断流 + 大会话 → 上下文溢出推导：`agent/error_classifier.py:541-561`
- 抖动退避：`agent/retry_utils.py:19-57`
- 单工具失败降级：`run_agent.py:9956-9974`
- 主循环错误恢复决策树：`run_agent.py:12398-13297`
- 协议缺口修复（orphan tool_call_id）：`run_agent.py:14154-14188`
- 跨进程 Nous 限流广播：`agent/nous_rate_guard.py` 全文件

```python
# Hermes 的错误处理：像一家大型外包公司的"应急响应中心"
# 17 种故障类型、14 步恢复流水线、跨进程协调——复杂但可靠

class HermesErrorHandling:
    def run_conversation(self, user_message):
        messages = init_messages(user_message)
        retry_count = 0
        
        while retry_count < max_retries:
            try:
                response = self.api_call(messages)
                
            except Exception as api_error:
                # ① 先把错误送进"分类器"——这是什么类型的故障？
                classified = classify_api_error(
                    api_error,
                    provider=self.provider,
                    model=self.model,
                    approx_tokens=estimate_tokens(messages),
                    context_length=self.context_length,
                    num_messages=len(messages),
                )
                
                # ② 按"代价从小到大"的顺序尝试恢复
                # 先试试换张电话卡（凭证轮换）——最便宜
                if self._recover_with_credential_pool(classified):
                    continue
                
                # 再试试压缩一下笔记本（上下文压缩）——中等开销
                if classified.should_compress:
                    self._compress_context(messages)
                    continue
                
                # 如果是限流且还有备用供应商，切换 provider
                if classified.reason == FailoverReason.rate_limit and self._fallback_chain:
                    if self._try_activate_fallback(classified.reason):
                        retry_count = 0   # 切换后重置重试计数
                        continue
                
                # ③ Nous 的特殊处理：跨进程广播限流状态
                if (classified.reason == FailoverReason.rate_limit 
                    and self.provider == "nous"):
                    if is_genuine_nous_rate_limit(api_error):
                        record_nous_rate_limit(api_error)  # 所有进程都能看到
                        retry_count = max_retries          # 跳过重试，直接 fallback
                        continue
                
                # ④ 真的没救了？指数退避后重试
                if classified.retryable:
                    wait = jittered_backoff(retry_count)   # 带抖动的退避
                    time.sleep(wait)
                    retry_count += 1
                    continue
                
                # ⑤ 不可恢复，终止并给用户一个交代
                return f"请求失败：{classified.message}"
            
            # 正常路径：处理 tool calls...
            if response.has_tool_calls:
                for tc in response.tool_calls:
                    try:
                        result = self._invoke_tool(tc.name, tc.arguments)
                    except Exception as tool_error:
                        # ⑥ 单工具失败降级为字符串——不让整个会话崩溃
                        result = f"Error executing tool '{tc.name}': {tool_error}"
                    messages.append(tool_result(tc.id, result))
                continue
            
            return response.content
        
        return "达到最大重试次数，任务未能完成。"
    
    def _repair_protocol_gap(self, messages):
        """⑦ 外层兜底：如果中途崩溃，补齐 orphan tool_call_id"""
        # OpenAI/Anthropic 协议要求：每个 tool_call_id 必须有对应的 tool 应答
        # 如果异常导致 tool_calls 发了但应答没写，下一轮 API 调用会 400
        # 反向扫描 messages，给每个未应答的 tool_call_id 合成 error tool 消息
        for msg in reversed(messages):
            if msg.get("role") == "assistant" and msg.get("tool_calls"):
                answered_ids = {m["tool_call_id"] for m in messages if m.get("role") == "tool"}
                for tc in msg["tool_calls"]:
                    if tc["id"] not in answered_ids:
                        messages.append({
                            "role": "tool",
                            "tool_call_id": tc["id"],
                            "content": f"Error executing tool: 会话中断"
                        })
                break
```

### nanobot：四层分层降级 + 毒消息过滤

**设计定位**：错误处理按"恢复能力"分层——Provider 能重试网络错误，Registry 能提示 LLM 自修复，Loop 能兜底防止崩溃，Memory 能降级保证数据不丢。适合个人助手场景。

> 💡 **名词解释：Session Poisoning（会话中毒）**
>
> 通俗地说：小李在笔记本上记了一个错电话号码。下次查电话时，他照着这个错号码打，对方说"打错了"，他把"打错了"也记下来。再下次查电话，他看到"错号码→打错了"两条记录，更迷糊了——恶性循环。
>
> 技术定义：LLM 返回的 error 内容如果写入 session.messages，下一轮迭代会基于这个错误上下文继续生成，可能导致永久 400 错误循环。nanobot 的 issue #1303 就是真实案例。

> 💡 **名词解释：_HINT（错误提示注入）**
>
> 通俗地说：小李打错电话后，主管在旁边递了一张纸条："分析一下上面的错误，换个方法试试。"这比在员工手册里写"打电话要注意"更及时、更聚焦。
>
> 技术定义：nanobot 在工具执行失败时，在错误返回末尾追加字符串 `"\n\n[Analyze the error above and try a different approach.]"`。利用 LLM 的 in-context learning，让模型在错误发生的当下就获得修正提示。

**关键源码位置**：
- Provider 层自动重试：`nanobot/providers/base.py:225-284`
- Registry 层统一捕获 + _HINT：`nanobot/agent/tools/registry.py:38-59`
- Loop 层 error 响应过滤：`nanobot/agent/loop.py:232-245`
- Loop 层全局兜底：`nanobot/agent/loop.py:311-331`
- Memory 层连续失败降级：`nanobot/agent/memory.py:114-208`

```python
# nanobot 的错误处理：像一个个人助理的"四层防护网"
# 每层只处理自己能恢复的错误，无法恢复的就地消化

class NanobotErrorHandling:
    # ── Layer 1: Provider 层 —— 网络抖动自动重试 ──
    async def chat_with_retry(self, messages, tools):
        _CHAT_RETRY_DELAYS = (1, 2, 4)   # 指数退避：1秒→2秒→4秒
        
        for attempt, delay in enumerate(_CHAT_RETRY_DELAYS, start=1):
            response = await self._safe_chat(messages, tools)
            
            if response.finish_reason != "error":
                return response              # 成功了，直接返回
            
            if not self._is_transient_error(response.content):
                # 不是瞬态错误（如不支持图片），尝试降级后返回
                if self._is_image_unsupported_error(response.content):
                    stripped = self._strip_image_content(messages)
                    if stripped:
                        return await self._safe_chat(stripped, tools)
                return response              # 非瞬态错误，直接返回给上层
            
            # 线路忙，等一会儿再打
            await asyncio.sleep(delay)
        
        return await self._safe_chat(messages, tools)  # 最后一次，不等待
    
    # ── Layer 2: Registry 层 —— 工具错误捕获 + 提示注入 ──
    async def execute_tool(self, name, params):
        _HINT = "\n\n[Analyze the error above and try a different approach.]"
        
        try:
            tool = self._tools.get(name)
            if not tool:
                return f"Error: Tool '{name}' not found." + _HINT
            
            params = tool.cast_params(params)      # 类型转换
            errors = tool.validate_params(params)   # Schema 校验
            if errors:
                return f"Error: Invalid parameters..." + _HINT
            
            result = await tool.execute(**params)
            if isinstance(result, str) and result.startswith("Error"):
                return result + _HINT               # 工具自身返回错误也加提示
            return result
            
        except Exception as e:
            # 任何 bug 都被兜住，不会传播到 Loop 层
            return f"Error executing {name}: {str(e)}" + _HINT
    
    # ── Layer 3: Loop 层 —— 毒消息过滤 + 全局兜底 ──
    async def _run_agent_loop(self, initial_messages):
        messages = initial_messages
        
        for iteration in range(max_iterations):
            response = await self.provider.chat_with_retry(messages, tools)
            
            if response.has_tool_calls:
                # 正常执行工具...
                continue
            else:
                clean = self._strip_think(response.content)
                
                # ⚠️ 关键防御：error 响应不写入历史！
                # 就像实习生记错了一个电话，如果把这个错号码写进笔记本，
                # 下次查电话时就会反复打错——形成"毒消息→永久错误"死循环
                if response.finish_reason == "error":
                    final_content = clean or "Sorry, I encountered an error."
                    break                           # break 但不持久化
                
                messages = self.context.add_assistant_message(messages, clean)
                final_content = clean
                break
        
        return final_content, messages
    
    async def _dispatch(self, msg):
        """最后一道防线：任何未捕获异常都不让服务崩溃"""
        async with self._processing_lock:          # 全局锁——一次只处理一条
            try:
                response = await self._process_message(msg)
                await self.bus.publish_outbound(response)
            except asyncio.CancelledError:
                raise                              # /stop 取消信号要正确传播
            except Exception:
                logger.exception("Unhandled error")
                await self.bus.publish_outbound(
                    OutboundMessage(content="Sorry, I encountered an error.")
                )
    
    # ── Layer 4: Memory 层 —— 固化失败降级归档 ──
    async def consolidate_with_fallback(self, messages):
        try:
            success = await self.store.consolidate(messages, provider, model)
            if success:
                self._consecutive_failures = 0
                return True
        except Exception:
            logger.exception("Memory consolidation failed")
        
        # 连续失败 3 次后，不再尝试 LLM 摘要，直接把原始消息 dump 到 HISTORY.md
        return self._fail_or_raw_archive(messages)
```

### OpenClaw：五层恢复链 + 模型故障转移 + 循环检测

**设计定位**：LLM 是不可靠的，每一层都要有独立的恢复策略——适合 7×24 小时运行的生产级网关。

> 💡 **名词解释：Model Fallback（模型故障转移）**
>
> 通俗地说：小李的主电话卡（Claude Opus）欠费了，系统自动切换到备用卡（GPT-4），用户完全无感知。等主卡充值后，系统再切回来。
>
> 技术定义：当主模型因额度用尽、区域故障或 provider 过载不可用时，自动切换到配置好的 fallback 模型链。OpenClaw 的 `model-fallback.ts` 实现了基于 cooldown 探测的智能切换——不是简单轮询，而是根据错误类型判断"这个模型多久后可能恢复"。

> 💡 **名词解释：Tool Loop Detection（工具循环检测）**
>
> 通俗地说：小李反复打开同一个网页刷新，期待价格会变——但那个页面只是缓存了旧数据。系统发现他已经刷了 10 次，弹窗提醒："你好像在重复同样的操作，确定要继续吗？"
>
> 技术定义：检测 Agent 是否陷入"反复调用相同工具却不产生进展"的死循环。OpenClaw 使用三种检测器（genericRepeat、knownPollNoProgress、pingPong），阈值分层：10 次警告、20 次阻断、30 次熔断。

> 💡 **名词解释：Cooldown Decision（冷却决策）**
>
> 通俗地说：小李的电话卡欠费了，系统判断"auth 错误几乎不会自愈→永久跳过""billing 错误用户可能充值→偶尔探测""rate_limit 通常几分钟恢复→主卡探测、备用卡尝试"。不同错误类型有不同的"冷却时间"。
>
> 技术定义：`model-fallback.ts:428-500` 中根据错误原因（auth/billing/rate_limit/overloaded）和模型角色（primary/fallback）决定是否跳过、探测或尝试候选模型。

**关键源码位置**：
- 五层恢复链（主循环）：`src/agents/pi-embedded-runner/run.ts:807-1285`
- 模型故障转移 + cooldown 决策：`src/agents/model-fallback.ts:428-500, 502-763`
- 上下文溢出显式排除 fallback：`src/agents/model-fallback.ts:698-701`
- 工具循环检测：`src/agents/tool-loop-detection.ts:372-401`
- 未处理 rejection 分类：`src/infra/unhandled-rejections.ts:219-254`
- 指数退避 + retry-after 支持：`src/infra/retry.ts:100-136`

```typescript
// OpenClaw 的错误处理：像一家跨国集团的"应急预案体系"
// 从低成本恢复策略到高成本恢复策略，层层递进

class OpenClawErrorHandling {
    async runWithRecovery(params) {
        let runLoopIterations = 0
        
        while (true) {
            if (runLoopIterations >= MAX_RUN_LOOP_ITERATIONS) {
                return { text: "Request failed after repeated internal retries.", isError: true }
            }
            runLoopIterations++
            
            try {
                const result = await runEmbeddedAttempt(params)
                break  // 成功，跳出重试循环
                
            } catch (err) {
                const errMessage = err instanceof Error ? err.message : String(err)
                
                // ① 上下文溢出？触发 compaction，不走 fallback！
                // 换一张电话卡解决不了"笔记本写满了"的问题
                if (isLikelyContextOverflowError(errMessage)) {
                    const compacted = await contextEngine.compact(params)
                    if (compacted) continue
                }
                
                // ② 可重试错误？指数退避后重试
                if (isRetryableError(err)) {
                    await retryAsync(() => runEmbeddedAttempt(params), {
                        maxRetries: 3,
                        delay: exponentialBackoff + jitter,
                        retryAfterMs: parseRetryAfterHeader(err),  // 尊重服务端意愿
                    })
                    continue
                }
                
                // ③ 模型不可用？按 fallback 链切换
                // auth 错误→永久跳过；billing→偶尔探测；rate_limit→探测+尝试
                const fallbackResult = await runWithModelFallback({
                    provider: params.provider,
                    model: params.model,
                    run: () => runEmbeddedAttempt(params),
                })
                if (fallbackResult.success) break
                
                // ④ 真的没救了，返回用户友好错误
                return { text: "任务失败，请稍后重试。", isError: true }
            }
        }
    }
    
    // 工具循环检测——防止模型"钻牛角尖"
    detectToolCallLoop(state, toolName, params) {
        const currentHash = hashToolCall(toolName, params)  // 确定性哈希
        const noProgress = getNoProgressStreak(history, toolName, currentHash)
        
        if (noProgressStreak >= 30) {   // 熔断阈值
            return {
                stuck: true,
                level: "critical",
                message: `CRITICAL: ${toolName} 已连续无进展重复 ${noProgressStreak} 次，会话执行被阻断。`
            }
        } else if (noProgressStreak >= 20) {  // 阻断
            return { stuck: true, level: "block", message: "..." }
        } else if (noProgressStreak >= 10) {  // 警告
            return { stuck: true, level: "warn", message: "..." }
        }
        
        return { stuck: false }
    }
    
    // 全局未处理 Rejection 处理器——进程的"最后防线"
    installUnhandledRejectionHandler() {
        process.on("unhandledRejection", (reason) => {
            if (isAbortError(reason)) {
                return  // 用户取消，静默处理
            }
            if (isFatalError(reason)) {
                console.error("FATAL:", reason)
                process.exit(1)  // OOM 等致命错误必须退出
            }
            if (isConfigError(reason)) {
                console.error("CONFIG ERROR:", reason)
                process.exit(1)  // 配置错误需要修复后重启
            }
            if (isTransientNetworkError(reason)) {
                console.warn("Non-fatal network error, continuing:", reason)
                return  // 网络抖动，继续运行
            }
            // 未知错误：保守策略，退出
            console.error("Unhandled rejection:", reason)
            process.exit(1)
        })
    }
}
```

### OpenCode：三级分类 + 统一错误转换 + Doom Loop 检测

**设计定位**：让 AI SDK 处理底层流控制，错误处理聚焦在"分类→恢复→通知"的状态转移——适合和 IDE 深度集成、需要实时反馈的场景。

> 💡 **名词解释：Doom Loop（厄运循环）**
>
> 通俗地说：实习生反复用同样的方法查同一个资料，连续 3 次得到同样的结果——系统弹窗问他："你确定要继续吗？"这比等他查了 100 次才发现问题更智能。
>
> 技术定义：OpenCode 在 `processor.ts:20` 中设置 `DOOM_LOOP_THRESHOLD = 3`。如果模型连续 3 次用相同参数调用同一个工具，系统判定为死循环，通过 `PermissionNext.ask` 弹窗请求用户确认。

> 💡 **名词解释：NamedError（命名错误）**
>
> 通俗地说：公司统一了错误报告格式——不管哪个部门出的问题，报告上都写着"错误类型：XX，原因：YY，是否可重试：是/否"。这样处理部门一看就知道该怎么应对。
>
> 技术定义：OpenCode 的 `MessageV2.fromError()` 将 AI SDK 的各种异常（`APICallError`、`LoadAPIKeyError`、`DOMException` 等）统一转换为内部 `NamedError` 对象。使用 `switch(true)` 模式进行多类型分发，每种错误保留原始 cause 便于调试。

**关键源码位置**：
- 三级错误分类（catch 块）：`packages/opencode/src/session/processor.ts:353-385`
- 指数退避 + retry-after 支持：`packages/opencode/src/session/retry.ts:28-59`
- 错误统一转换：`packages/opencode/src/session/message-v2.ts:827-913`
- Doom Loop 检测：`packages/opencode/src/session/processor.ts:20,151-176`

```typescript
// OpenCode 的错误处理：像一个和设计软件深度集成的"工作室助理"
// 错误不是"崩溃"，而是"状态转移"——从 busy 到 retry 到 idle

class OpenCodeErrorHandling {
    async loop(sessionID) {
        let attempt = 0
        
        while (true) {
            if (abort.aborted) break  // 用户点了"取消"
            
            try {
                const stream = await LLM.stream({ messages, tools, abort })
                
                for await (const event of stream.fullStream) {
                    switch (event.type) {
                        case "text-delta":
                            Session.updatePartDelta(event.text)  // 实时更新 UI
                            break
                        
                        case "tool-call":
                            // ⚠️ Doom Loop 检测：连续 3 次相同工具+相同参数
                            const lastThree = parts.slice(-3)
                            if (lastThree.every(p => 
                                p.tool === event.toolName &&
                                JSON.stringify(p.input) === JSON.stringify(event.input)
                            )) {
                                await PermissionNext.ask({
                                    permission: "doom_loop",
                                    patterns: [event.toolName],
                                })  // 弹窗问用户："助理好像在重复同样的操作，继续吗？"
                            }
                            break
                        
                        case "tool-result":
                            Session.updatePart({ status: "done", result: event.result })
                            break
                    }
                }
                
            } catch (e) {
                // ① 统一错误转换：不管什么异常，先转成 NamedError
                const error = MessageV2.fromError(e, { providerID: model.providerID })
                
                // ② 三级分类决策
                if (MessageV2.ContextOverflowError.isInstance(error)) {
                    // 笔记本写满了 → 触发 compaction（自愈）
                    needsCompaction = true
                    Bus.publish(Session.Event.Error, { sessionID, error })
                    
                } else {
                    const retry = SessionRetry.retryable(error)
                    if (retry !== undefined) {
                        // 可重试错误 → 计算退避时间 → sleep → continue
                        attempt++
                        const delay = SessionRetry.delay(attempt, error)
                        SessionStatus.set(sessionID, { 
                            type: "retry", attempt, message: retry, 
                            next: Date.now() + delay 
                        })
                        await SessionRetry.sleep(delay, abort)
                        continue  // 回到循环顶部重试
                        
                    } else {
                        // 不可重试错误 → 写入 error → 停止 loop
                        input.assistantMessage.error = error
                        Bus.publish(Session.Event.Error, { sessionID, error })
                        SessionStatus.set(sessionID, { type: "idle" })
                        break
                    }
                }
            }
        }
    }
    
    // 指数退避：优先尊重服务端的 retry-after 头
    static delay(attempt: number, error?: MessageV2.APIError) {
        if (error) {
            const headers = error.data.responseHeaders
            if (headers) {
                const retryAfterMs = headers["retry-after-ms"]
                if (retryAfterMs) return Number.parseFloat(retryAfterMs)
                
                const retryAfter = headers["retry-after"]
                if (retryAfter) {
                    const seconds = Number.parseFloat(retryAfter)
                    if (!Number.isNaN(seconds)) return Math.ceil(seconds * 1000)
                    const parsed = Date.parse(retryAfter) - Date.now()
                    if (!Number.isNaN(parsed) && parsed > 0) return Math.ceil(parsed)
                }
            }
        }
        // 服务端没指示，用客户端指数退避
        return Math.min(RETRY_INITIAL_DELAY * Math.pow(2, attempt - 1), RETRY_MAX_DELAY)
    }
    
    // 统一错误转换：switch(true) 多类型分发
    static fromError(e: unknown, ctx: { providerID: string }) {
        switch (true) {
            case e instanceof DOMException && e.name === "AbortError":
                return new MessageV2.AbortedError({ message: e.message }).toObject()
            case LoadAPIKeyError.isInstance(e):
                return new MessageV2.AuthError({ providerID: ctx.providerID, message: e.message }).toObject()
            case (e as SystemError)?.code === "ECONNRESET":
                return new MessageV2.APIError({ message: "Connection reset", isRetryable: true }).toObject()
            case APICallError.isInstance(e):
                const parsed = ProviderError.parseAPICallError({ providerID: ctx.providerID, error: e })
                if (parsed.type === "context_overflow")
                    return new MessageV2.ContextOverflowError({ message: parsed.message }).toObject()
                return new MessageV2.APIError({...parsed}).toObject()
        }
    }
}
```

## 7.5 独特高价值设计：各项目的闪光点

每个项目都因为特定的场景诉求，做了其他项目没有做的高价值设计。

### Hermes Agent：402 歧义消解——6 行代码避免凭证池被"错杀"

`agent/error_classifier.py:698-724`：OpenRouter 等 provider 返回的 402 错误有两种完全不同的语义——"账单耗尽"（需要换 key）和"周期性配额用完，5 分钟后恢复"（不需要换 key）。`_classify_402` 通过检查错误消息中是否包含 `"try again"`、`"retry"`、`"resets at"` 等 transient signal 来区分两者。

**解决的问题**：如果把周期性配额误判为账单耗尽，凭证池会被全部标记为耗尽，导致所有 key 都被错误地跳过，系统彻底停摆。

**什么场景值得借鉴**：任何维护多个 API key 或凭证池的系统。HTTP 状态码的语义是模糊的，必须结合消息内容做二次分类。

### Hermes Agent：断流 + 大会话 → 上下文溢出推导

`agent/error_classifier.py:541-561`：很多 API gateway（特别是 Cloudflare 前置的 Anthropic）面对超大 payload 不返回 413，而是直接 RST TCP。如果只看异常类型，`RemoteProtocolError` 会被当 timeout 重试，永远卡死。Hermes 用 `approx_tokens > context_length * 0.6` 作为启发式规则，从上下文规模反推"沉默拒绝"的真实意图。

**解决的问题**：传输层断流不等于网络抖动——在大会话场景下，它很可能是协议层的"故意拒绝"。

**什么场景值得借鉴**：任何处理大上下文 + 多 provider 的 Agent 系统。不要只看异常类型，同时看协议外的 contextual signal。

### nanobot："错误不入历史"——4 行代码挡住整类事故

`nanobot/agent/loop.py:236-239`：

```python
if response.finish_reason == "error":
    final_content = clean or "Sorry, I encountered an error."
    break  # break 但不持久化
```

错误响应只返回给用户，**不写入 session.messages**。背后是 issue #1303 的真实事故：错误响应写入历史后，下一轮 LLM 看到畸形的 assistant 消息，反复触发 400，形成"毒消息→永久 400"死循环。

**什么场景值得借鉴**：所有 Agent 系统。这是一个反直觉但极其重要的工程经验——任何 LLM error 都属于"瞬时事件"，不该污染会话状态。

### nanobot：_HINT 动态提示注入

`nanobot/agent/tools/registry.py:38-59`：`_HINT` 不是静态配置在 system prompt 中，而是只在错误发生时动态追加到返回内容里。这利用了 LLM 的 in-context learning——错误发生的当下，上下文里立刻出现 `"Analyze the error above and try a different approach"`，比员工手册里的静态指令更及时、更聚焦。

**什么场景值得借鉴**：任何需要 LLM 根据错误自修复的系统。静态指令容易被淹没在上下文中，动态注入更聚焦。

### OpenClaw：五层恢复链——生产级 Agent 的分界线

OpenClaw 的恢复策略按**成本从低到高**严格排序：`compaction`（纯计算）→ `tool result truncation`（局部修改）→ `Auth Profile 轮换`（切换 key）→ `thinking 降级`（降低能力）→ `model fallback`（切换模型）。上下文溢出被显式排除在 fallback 之外（`model-fallback.ts:698-701`），因为切换模型无法解决"笔记本写满了"的问题。

**什么场景值得借鉴**：7×24 小时运行的生产级网关服务。个人助手不需要这个，但对外服务的系统必须有分层恢复链。

### OpenClaw：未处理 Rejection 分类器

`src/infra/unhandled-rejections.ts:219-254`：Node.js 默认会在未处理 rejection 时终止进程。OpenClaw 安装全局处理器，将错误分为 fatal（OOM→退出）、config（配置错误→退出）、transient（网络抖动→继续）、abort（用户取消→静默）四类。已知安全的继续运行，已知危险的退出，未知的保守退出。

**什么场景值得借鉴**：任何 Node.js 长期运行进程。一个边缘 bug 不应该杀死整个 gateway。

### OpenCode：Doom Loop 检测

`processor.ts:20,151-176`：`DOOM_LOOP_THRESHOLD = 3`。如果模型连续 3 次用相同参数调用同一个工具，系统判定为死循环，通过 `PermissionNext.ask` 弹窗请求用户确认。这比单纯的迭代预算更智能——它不是"跑满 N 轮就停"，而是"发现重复无用功就停"。

**什么场景值得借鉴**：任何面向终端用户、需要防止模型"钻牛角尖"的交互式 Agent。

### OpenCode：尊重服务端退避意愿

`retry.ts:28-59`：优先解析 HTTP 响应头中的 `retry-after-ms` 和 `retry-after`（支持秒数和 HTTP Date 两种格式），而不是盲目使用客户端计算的退避时间。这体现了"服务端比客户端更了解自己的负载状况"的设计假设。

**什么场景值得借鉴**：任何调用第三方 API 的系统。尊重服务端的流量控制意愿，是良好的"API 公民"行为。

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 错误分类 | 至少区分"可重试""需降级""应终止"三类 |
| ☐ | 重试与退避 | 指数退避 + 抖动，避免惊群效应 |
| ☐ | 工具失败降级 | 单工具异常不终止会话，转为字符串让模型自主规划 |
| ☐ | 兜底与隔离 | 全局 except 防止进程崩溃；毒消息不写入历史 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 多 provider 网关 | 结构化分类器 + 凭证池轮换 + provider fallback | Hermes |
| 大上下文 + 多 provider | 断流推导 + 上下文溢出启发式 | Hermes |
| 个人助手 / 聊天机器人 | 四层分层降级 + 毒消息过滤 + _HINT 注入 | nanobot |
| 生产级 7×24 运行 | 五层恢复链 + 模型 fallback + 未处理 rejection 分类 | OpenClaw |
| 工具调用频繁 | 循环检测（阈值分层）+ 向 LLM 注入警告 | OpenClaw |
| IDE 集成 / 流式 UI | Doom Loop 检测 + 统一错误转换 + 尊重 retry-after | OpenCode |
| 跨进程部署 | 文件级共享状态协调限流（如 Nous rate guard） | Hermes |

### 最重要的三条经验

1. **"分类"和"决策"必须分离**：Hermes 的 `classify_api_error()` 是纯函数，只回答"这是什么错"；主循环根据上下文决定"怎么办"。这让分类器可单测、决策树可调整、两者互不污染。

2. **降级路径比最优路径更重要**：nanobot 的原始归档、OpenClaw 的 FTS-only 降级、Hermes 的 provider 失败静默，都体现了一个原则——错误处理系统的故障不能阻塞主流程。LLM 不是 100% 可靠，必须有不依赖 LLM 的 fallback 路径。

3. **毒消息隔离是底线中的底线**：nanobot 的 issue #1303 证明，一次错误响应写入历史可能导致整个会话永久报废。任何 LLM error 都属于"瞬时事件"，不该污染持久化状态。
