# 第10章 自我检查——验证循环

> "实习生写完报告后，会自己检查一遍：数据有没有错？格式对不对？有没有漏掉什么？验证循环，就是让 Agent 学会这套'交稿前的自检流程'。"

---

## 10.1 开篇故事：小李的交稿前检查

实习生小李花了整整一下午写了一份竞品分析报告。在点击"发送"之前，他做了一套"自检流程"：

**第一层：格式对不对**

他先检查报告结构——主管要求"竞品名称-定价模式-单价-备注"四列，他数了数，没错。然后看字体、字号、行距是否符合公司模板。"格式不对，再好的内容也白搭。"他对自己说。

**第二层：数据有没有错**

他逐个核对数字——竞品 A 的月费是 $29 还是 $299？他翻回笔记本确认了一遍。竞品 B 的"按调用量收费"模式，他确认自己没有理解成"按用户数收费"。

**第三层：有没有遗漏或重复**

他扫了一遍目录——主管要求三家竞品，他只写了两家？不对，第三家在第二页。然后他发现竞品 A 的价格出现了两次，一次在正文、一次在附录，数字一致，没问题。

**第四层：交给别人再看看**

他把报告发给了邻座的同事小王："帮我看一眼有没有低级错误？"小王扫了两分钟，指着一处说："这里单位写错了，应该是'千次调用'不是'万次调用'。"

**Agent 的验证循环，就是这位实习生的"交稿前自检"。**

但 Agent 面临一个实习生没有的问题：LLM 的输出是概率性的，它可能会"手滑"——工具名拼错、参数类型写错、JSON 格式不合法、陷入"再试一次"的死循环。验证循环要做的，就是在这些"手滑"造成实际损害之前，把它们拦住或修正。

---

## 10.2 业务概念：验证循环是什么

**验证循环（Validation Loop）**是 Agent 系统的"质量守门员"。它负责在 LLM 的决策输出与实际执行之间插入多层检查，确保工具调用合法、参数有效、行为合理、输出符合预期格式。

### 技术定义

验证循环不是简单的"try-catch"。它包含四个层面：

1. **格式验证层**：LLM 输出的工具调用是否符合预期的 schema？JSON 结构是否完整？参数类型是否正确？
2. **语义验证层**：工具名是否存在？参数值是否在合法范围内？必填字段是否缺失？
3. **行为验证层**：Agent 是否陷入了无意义的重复调用？是否在原地打转消耗 token？
4. **意图验证层**：LLM 是否误解了用户的指令？是否需要主动向用户确认歧义？

> 💡 **名词解释：JSON Schema**
>
> 通俗地说：公司给实习生的一份"填表规范"——"这个格子只能填数字""这个格子必填""这个格子的值只能是'A'或'B'"。
>
> 技术定义：一种用于描述 JSON 数据结构的规范语言。Agent 的工具定义使用 JSON Schema 来告诉 LLM"这个工具需要什么参数、每个参数是什么类型、有什么约束"。

### 一句话说清边界

- **验证循环负责**：工具参数校验、schema 兼容性处理、死循环检测、输出格式强制
- **验证循环不负责**：具体工具怎么实现（那是工具系统）、危险命令的审批（那是安全防护）、用户身份认证（那是网关系统）

### 没有验证循环会怎样？

如果把验证循环从 Agent 中拿掉：

- **工具调用直接崩溃**：LLM 把 `"timeout": "9999"` 当字符串传入，而工具期望的是整数，Python 直接抛 `TypeError`
- **schema 不兼容导致整轮请求被拒**：某个工具的 schema 用了 `"anyOf": [{"type": "string"}, {"type": "null"}]`，后端直接返回 400，整轮对话报废
- **Agent 原地打转烧 token**：同一个 `read_file` 用相同参数调用 30 次，LLM 每次都"再试一次"，直到预算耗尽
- **输出格式不合法**：用户要求 JSON 输出，LLM 却返回了一段散文，下游解析直接失败

## 10.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，验证循环的**最小可行实现**只需要以下四个要素：

### 要素一：参数类型转换

LLM 输出的参数常是字符串（如 `"true"`、`"42"`），但工具期望的是原生类型。必须先做宽松转换，再进入严格校验。

### 要素二：参数约束校验

检查必填字段、数值范围、字符串长度、枚举值等约束。缺失或越界的参数应该被拦截，并给 LLM 清晰的错误提示让它自行修正。

### 要素三：工具调用修复

LLM 可能拼错工具名（大小写错误）、调用不存在的工具。系统应该能自动修复常见错误（如大小写纠正），或优雅降级而不是直接崩溃。

### 要素四：重复调用检测

Agent 可能在同一轮中反复调用同一个工具（尤其是只读工具）。必须检测这种无进展的重复，并通过提示让 LLM 停止。

```python
# 所有 Agent 都必须有的"最小可行验证循环"
# 就像实习生的"交稿前最低检查清单"

def validate_tool_call(tool_name, params, tools_registry):
    # ① 工具存在性检查
    tool = tools_registry.get(tool_name.lower())  # 自动纠正大小写
    if not tool:
        return {"error": f"Tool '{tool_name}' not found"}
    
    # ② 参数类型转换（LLM 常输出字符串化的数值和布尔值）
    params = cast_params(params, tool.schema)
    
    # ③ 参数约束校验
    errors = validate_params(params, tool.schema)
    if errors:
        # 返回错误给 LLM，让它下一轮修正
        return {"error": f"Invalid parameters: {', '.join(errors)}"}
    
    # ④ 执行前检查是否重复调用
    signature = (tool_name, json.dumps(params, sort_keys=True))
    if signature in recent_calls:
        recent_calls[signature] += 1
        if recent_calls[signature] >= 3:
            return {"error": "Repeated identical call detected. Use the result already provided."}
    else:
        recent_calls[signature] = 1
    
    # 通过验证，执行工具
    return tool.execute(**params)
```

**这就是"底线"**。少于这四点，Agent 的验证循环就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 参数类型转换 | `"true"` 当字符串传入，`if not replace_all:` 永远为真，逻辑颠倒 |
| 参数约束校验 | 必填字段缺失导致 `TypeError`，整轮对话中断 |
| 工具调用修复 | 大小写错误直接报错，用户体验极差 |
| 重复调用检测 | Agent 原地打转，token 被无意义消耗 |

## 10.4 四个项目的实现对比

四个框架在"底线"之上，基于各自对"LLM 输出不完美"的应对策略做了不同的扩展。

### Hermes Agent："多道把关"的 LLM 输出质检流水线

**设计定位**：验证不是"事后检查"，而是嵌入执行流程的多层防御——从 schema 兼容性到危险命令审批到行为护栏，每一层独立生效。

> 💡 **名词解释：Schema Sanitizer（Schema 消毒器）**
>
> 通俗地说：公司各部门的报表格式要求不同——财务部要 Excel、人事部要 PDF、市场部要 PPT。实习生交报告前，需要把同一份内容转换成不同部门能接受的格式。
>
> 技术定义：Hermes 的 `schema_sanitizer.py` 在工具 schema 投递给 LLM 之前做"等效转换"——把某些后端无法消化但语义可推断的 schema 形态（如 `anyOf` 可空联合、`oneOf`）折叠为"最大公约数"形态，确保最差后端（如 llama.cpp）也能接受。

> 💡 **名词解释：Tool Guardrails（工具护栏）**
>
> 通俗地说：小李发现自己在反复查同一份文件（文件内容没变，但他忘了已经查过）。同事在他旁边贴了张便签："这份文件你刚才已经看过了，内容没变。"——不是阻止他查，而是提醒他别再浪费时间。
>
> 技术定义：Hermes 的 `ToolCallGuardrailController` 在工具调用前后分别执行 `before_call` 和 `after_call`。检测维度包括：相同参数反复失败、幂等工具反复返回相同结果、同一工具连续失败次数超限。默认只 warn 不 block，避免误伤合法的重复读取。

> 💡 **名词解释：Clarify Tool（澄清工具）**
>
> 通俗地说：小李接到一个模糊的任务——"整理一下最近的资料"。他没有瞎猜，而是主动问主管："您是指销售资料还是技术资料？需要按时间还是按项目分类？"——在动手之前先确认方向。
>
> 技术定义：Hermes 让 LLM 在任务模糊、存在有意义的取舍、需要用户决策时，主动调用 `clarify` 工具向用户确认。这是"反向验证"——不是系统验证 LLM，而是让 LLM 验证用户意图。

**关键源码位置**：
- Schema 清理：`tools/schema_sanitizer.py:171-189`
- 反应式 schema 回退：`run_agent.py:12595-12618`
- Tool guardrails before_call：`run_agent.py:9858`
- Tool guardrails after_call：`run_agent.py:9616`
- Guardrails 无进展检测：`agent/tool_guardrails.py:354-373`
- Clarify 工具：`tools/clarify_tool.py:96-103`
- Smart approval：`tools/approval.py:743-787`

```python
# Hermes 的验证循环：像一家有质检部门的大型外包公司

class HermesValidationSystem:
    def build_tools_for_llm(self, tools):
        # ① Schema 消毒：把后端无法消化的 schema 折叠为最大公约数
        # 如 {"anyOf": [{"type": "string"}, {"type": "null"}]} → {"type": "string", "nullable": true}
        sanitized = sanitize_tool_schemas(tools)
        return sanitized
    
    def on_llama_cpp_grammar_error(self, tools):
        # ② 反应式回退：如果后端报 grammar 错误，更激进地剥离 schema
        return strip_pattern_and_format(tools)  # 仅当出错时触发，避免过度剥离
    
    def before_tool_call(self, tool_name, args):
        # ③ 工具护栏：执行前检查是否该被阻止
        decision = self.guardrails.before_call(tool_name, args)
        if decision.action == "block":
            return {"blocked": True, "reason": decision.message}
        return {"blocked": False}
    
    def after_tool_call(self, tool_name, args, result, failed):
        # ④ 执行后记录结果，检测无进展循环
        decision = self.guardrails.after_call(tool_name, args, result, failed=failed)
        if decision.action == "warn":
            # 把提醒文字拼进 tool result，LLM 下一轮就能看到
            return result + "\n[Note: " + decision.message + "]"
        elif decision.action == "halt":
            self._halt_decision = decision  # 强制结束本轮 turn
        return result
    
    def on_ambiguous_task(self, question, choices):
        # ⑤ Clarify：LLM 主动问用户确认歧义
        return self.clarify_tool.ask(question, choices)
```

### nanobot："类型防火墙"的两阶段校验

**设计定位**：验证要极简、零外部依赖、LLM 的错误应该是可恢复的循环内错误而非致命异常。

> 💡 **名词解释：Cast + Validate（转换与校验）**
>
> 通俗地说：主管在纸上写了一个数字，但字迹潦草——"42"看起来像是"42"但也可能是"'42'"。小李先"辨认"（cast）一下这是数字还是字符串，然后再"核实"（validate）这个数字是否在合理范围内。
>
> 技术定义：nanobot 在 `ToolRegistry.execute()` 中执行两阶段校验。`cast_params` 负责宽松类型转换（`"42"` → `42`、`"true"` → `True`），`validate_params` 负责严格约束检查（必填、范围、枚举）。两个阶段顺序不可交换——必须先 cast 再 validate。

**关键源码位置**：
- 类型转换：`nanobot/agent/tools/base.py:55-122`
- 约束校验：`nanobot/agent/tools/base.py:124-170`
- 工具注册执行：`nanobot/agent/tools/registry.py:38-59`
- Schema 共用：`nanobot/agent/tools/base.py:172-181`

```python
# nanobot 的验证循环：一个随身携带检查清单的极简主义者

class NanobotValidationSystem:
    def execute_tool(self, tool_name, params):
        tool = self.registry.get(tool_name)
        
        # ① 宽松转换：LLM 常输出字符串化的值，先转成 Python 原生类型
        # "42" → 42, "true" → True, "1.5" → 1.5
        params = tool.cast_params(params)
        
        # ② 严格校验：类型、必填、范围、枚举、长度
        errors = tool.validate_params(params)
        if errors:
            # 返回错误给 LLM，让它下一轮修正——不中断循环
            return f"Error: Invalid parameters: {'; '.join(errors)}"
        
        # ③ 通过校验，执行工具
        return tool.execute(**params)
    
    def cast_params(self, params, schema):
        # Python 陷阱：bool 是 int 子类，必须先判 bool 再判 int
        # 否则 True 会被当成 1，replace_all=True 变成 replace_all=1
        for key, val in params.items():
            prop = schema["properties"].get(key, {})
            if prop.get("type") == "boolean" and isinstance(val, str):
                if val.lower() in ("true", "1", "yes"):
                    params[key] = True
                elif val.lower() in ("false", "0", "no"):
                    params[key] = False
            elif prop.get("type") == "integer" and isinstance(val, str):
                try:
                    params[key] = int(val)
                except ValueError:
                    pass  # 转换失败保留原值，validate 会报错
        return params
```

### OpenClaw："多层哨兵"的持续验证体系

**设计定位**：验证不是"检查点"，而是持续运行的背景进程——从工具调用行为到配置正确性到系统健康状态，全方位监控。

> 💡 **名词解释：Tool Loop Detection（工具循环检测）**
>
> 通俗地说：小李在等一个文件生成，每 5 分钟去文件夹里看一眼。看了 3 次还没好——正常。看了 10 次还没好——同事提醒他"可能有问题"。看了 30 次还没好——主管直接说"别等了，先干别的"。
>
> 技术定义：OpenClaw 的 `detectToolCallLoop` 使用三层渐进式阈值：warning（10 次）通知 LLM 自行纠正、critical（20 次）更强硬阻断、global_circuit_breaker（30 次）彻底熔断。区分"轮询"（结果在变化）和"循环"（结果始终不变）。

**关键源码位置**：
- 工具循环检测：`src/agents/tool-loop-detection.ts:372-401`
- 配置验证：`src/config/validation.ts:50-80`
- Skill 安全扫描：`src/security/skill-scanner.ts:74-76`
- Doctor 诊断：`src/commands/doctor-state-integrity.ts:46-62`
- Session 文件修复：`src/agents/session-file-repair.ts`

```typescript
// OpenClaw 的验证循环：像一家有持续监控系统的跨国集团

class OpenClawValidationSystem {
    async executeTool(toolName, params, history) {
        // ① 工具循环检测：检查是否陷入无意义重复
        const loopCheck = detectToolCallLoop(history, toolName, params);
        if (loopCheck.stuck) {
            if (loopCheck.level === "critical") {
                return { error: loopCheck.message };  // 强硬阻断
            }
            // warning 级别：把提醒注入上下文，让 LLM 自行调整
            return { result: "...", warning: loopCheck.message };
        }
        
        // 执行工具...
        const result = await this.tools.execute(toolName, params);
        
        // ② 记录调用结果，用于下一轮循环检测
        recordToolCall(history, toolName, params, result);
        return result;
    }
    
    validateConfig(config) {
        // ③ 配置验证：不仅说"错了"，还说"可以填什么"
        const issues = this.schema.safeParse(config);
        return issues.errors.map(e => ({
            field: e.path,
            message: e.message,
            allowedValues: collectAllowedValuesFromIssue(e),  // 给用户友好提示
        }));
    }
    
    async doctor() {
        // ④ 主动诊断：检查目录权限、会话完整性、安全配置
        const findings = [
            ...checkStateIntegrity(),
            ...checkDirPermissions(),
            ...checkSecurityConfig(),
        ];
        return findings.map(f => ({
            ...f,
            remediation: f.fixCommand,  // 不仅检测问题，还给修复命令
        }));
    }
}
```

### OpenCode："质量守门员"的多层输出校验

**设计定位**：让 AI SDK 处理流控制，验证聚焦在输出格式强制、工具调用修复和行为异常检测——适合和 IDE 深度集成、对输出格式要求严格的场景。

> 💡 **名词解释：StructuredOutput（结构化输出工具）**>
> 通俗地说：主管要求"交一份 Excel 表格"，但实习生习惯性地写了一段文字发过去。系统会强制提醒："主管要求的是表格，不是文字——请重新整理成表格格式。"
>
> 技术定义：OpenCode 在用户请求 JSON Schema 输出时，向 LLM 注入 `StructuredOutput` 工具并设置 `toolChoice: "required"`，强制 LLM 必须调用该工具输出结构化数据。如果 LLM 未调用而直接结束，系统设置 `StructuredOutputError`。

> 💡 **名词解释：Doom Loop（末日循环）**>
> 通俗地说：实习生反复打开同一个网页，期待出现不同的结果——页面明明没变，他却刷了 3 次。同事看不下去了，拍了拍他肩膀："你确定这个页面会变吗？"
>
> 技术定义：OpenCode 检测连续 3 次用相同参数调用同一个工具的情况，通过 `PermissionNext.ask` 弹窗请求用户确认。这比单纯的迭代预算更智能——不是"跑满 N 轮就停"，而是"发现重复无用功就停"。

**关键源码位置**：
- 结构化输出强制：`packages/opencode/src/session/prompt.ts:614-703`
- 工具调用修复：`packages/opencode/src/session/llm.ts:178-198`
- 参数校验：`packages/opencode/src/tool/tool.ts:48-88`
- Doom Loop 检测：`packages/opencode/src/session/processor.ts:152-176`

```typescript
// OpenCode 的验证循环：像一个有自动校对功能的设计工作室

class OpenCodeValidationSystem {
    async buildPrompt(userRequest) {
        // ① 如果用户要求 JSON Schema 输出，注入 StructuredOutput 工具并强制调用
        if (userRequest.format?.type === "json_schema") {
            this.tools["StructuredOutput"] = createStructuredOutputTool({
                schema: userRequest.format.schema,
                onSuccess: (output) => { this.structuredOutput = output },
            });
            this.toolChoice = "required";  // 必须调用某个工具
        }
    }
    
    async onModelResponse(response) {
        // ② 检查 LLM 是否按要求调用了 StructuredOutput
        if (this.structuredOutput !== undefined) {
            return { output: this.structuredOutput, done: true };
        }
        if (response.finished && this.expectedStructuredOutput) {
            return { error: new StructuredOutputError("Model did not produce structured output") };
        }
    }
    
    repairToolCall(failed) {
        // ③ 工具调用修复：大小写错误自动纠正，不存在的工具降级为 invalid
        const lower = failed.toolCall.toolName.toLowerCase();
        if (lower !== failed.toolCall.toolName && this.tools[lower]) {
            return { ...failed.toolCall, toolName: lower };  // 大小写修复
        }
        return {
            ...failed.toolCall,
            toolName: "invalid",  // 优雅降级
            input: JSON.stringify({ tool: failed.toolCall.toolName, error: failed.error }),
        };
    }
    
    async validateParams(tool, args) {
        // ④ zod 参数校验：AOP 式自动包装，错误信息对 LLM 友好
        try {
            tool.parameters.parse(args);
        } catch (error) {
            throw new Error(
                `The ${tool.id} tool was called with invalid arguments: ${error}.\nPlease rewrite the input...`
            );
        }
    }
    
    detectDoomLoop(parts, currentTool, currentInput) {
        // ⑤ Doom Loop 检测：连续 3 次相同参数调用同一工具
        const lastThree = parts.slice(-3);
        if (lastThree.every(p =>
            p.type === "tool" &&
            p.tool === currentTool &&
            JSON.stringify(p.state.input) === JSON.stringify(currentInput)
        )) {
            return PermissionNext.ask({ permission: "doom_loop", patterns: [currentTool] });
        }
    }
}
```

### 四项目核心差异对比表

| 维度 | Hermes Agent | nanobot | OpenClaw | OpenCode |
|------|-------------|---------|----------|----------|
| **核心策略** | 多道把关（schema → 审批 → guardrails → clarify） | 两阶段类型防火墙（cast → validate） | 多层哨兵（行为检测 → 配置验证 → 安全扫描 → 诊断） | 输出质量守门员（结构化强制 → 修复 → 校验 → 行为检测） |
| **Schema 处理** | 无条件 sanitize + 反应式激进回退 | 手写轻量校验器（7 个关键字） | Zod schema 验证 | zod 自动包装 + toolChoice: required |
| **参数校验** | 依赖后端/工具的校验 | cast_params + validate_params（零外部依赖） | 运行时参数校验 | zod parse（Tool.define 自动包装） |
| **死循环检测** | Tool guardrails（幂等工具无进展检测） | 未内置 | 三层渐进式阈值（warn/critical/circuit_breaker） | Doom Loop 检测（连续 3 次相同调用） |
| **输出格式强制** | 无特别机制 | 无特别机制 | 无特别机制 | StructuredOutput 工具 + 强制调用 |
| **工具调用修复** | 无 | 无 | 无 | 大小写纠正 + 降级为 invalid |
| **意图验证** | Clarify 工具（LLM 主动问用户） | 无 | 无 | 无 |
| **辅助验证** | Smart approval（aux LLM 仲裁误报） | 无 | Doctor 诊断命令 | 无 |

## 10.5 独特高价值设计：各项目的闪光点

### Hermes Agent：Schema Sanitizer——"宽进严出"的后端兼容性

`tools/schema_sanitizer.py:171-189`：把 `"anyOf": [{"type": "string"}, {"type": "null"}]` 折叠为 `{"type": "string", "nullable": true}`。区分"nullable union"和"真 union"——只折叠前者，保留后者的语义完整性。

**解决的问题**：不同 LLM 后端的 schema 接收能力差异极大（Anthropic 拒 nullable union；llama.cpp 拒空 properties），如果不做兼容性处理，轮内任何一个工具的 schema 错都会让整轮请求直接 400。

**什么场景值得借鉴**：任何需要支持多个 LLM provider 的 Agent 系统。

### Hermes Agent：Clarify Tool——"反向验证"让 LLM 主动确认意图

`tools/clarify_tool.py:96-103`：当任务模糊、存在有意义的取舍时，让 LLM 主动问用户，而不是瞎猜。description 里既劝进（"什么时候要用"）又劝退（"什么时候不要用"）。

**解决的问题**：LLM 沿着错误方向执行到底，浪费大量 token 后才被发现方向错了。

**什么场景值得借鉴**：任何涉及"架构决策""删除操作""格式选择"等需要用户确认的 Agent 系统。

### nanobot：bool/int 特判顺序——4 行代码挡住 Python 的类型陷阱

`nanobot/agent/tools/base.py:83-86`：先检查 `target_type == "boolean"`，再检查 `target_type == "integer"`。因为 Python 中 `isinstance(True, int) == True`，如果顺序颠倒，`True` 会被当成整数 1 通过。

**解决的问题**：Python 的语言特性陷阱导致类型转换错误，`replace_all=True` 被误 cast 为 `1`，逻辑完全颠倒。

**什么场景值得借鉴**：任何用 Python 手写类型转换的 Agent 系统。

### nanobot：错误返回给 LLM 而非抛出异常

`nanobot/agent/tools/registry.py:52-53`：校验失败返回 `"Error: Invalid parameters..."` 字符串，Agent Loop 将其作为 tool result 写入历史，让 LLM 在下一轮自行修正。

**解决的问题**：参数错误是 LLM 的"手滑"，不是系统故障。抛出异常会中断整个循环，而返回错误让 LLM 自己纠正更符合 Agent 的自治迭代哲学。

**什么场景值得借鉴**：所有 Agent 系统。这是一个反直觉但极其重要的设计——LLM 的错误应该是可恢复的。

### OpenClaw：三层渐进式循环检测

`src/agents/tool-loop-detection.ts:372-401`：warning（10 次）→ critical（20 次）→ global_circuit_breaker（30 次）。区分"轮询"（结果在变化，可能是等 CI 完成）和"循环"（结果始终不变）。

**解决的问题**：一刀切地阻断所有重复调用会误伤合法场景（如等待文件生成），而完全不检测会让 Agent 原地打转烧 token。

**什么场景值得借鉴**：任何需要执行长时间任务或轮询操作的 Agent 系统。

### OpenClaw：Doctor 诊断——"不仅检测问题，还给修复命令"

`src/commands/doctor-state-integrity.ts:46-62`：`dirPermissionHint` 将底层权限问题转化为用户可以直接执行的 `sudo chown` 命令。

**解决的问题**：自动验证覆盖不了所有场景，用户需要手动诊断工具。但"发现问题"不够，还要"告诉用户怎么修"。

**什么场景值得借鉴**：任何面向终端用户的 CLI 工具或 Agent 框架。

### OpenCode：StructuredOutput 强制——用工具模式替代 JSON mode

`packages/opencode/src/session/prompt.ts:614-703`：注入 `StructuredOutput` 工具 + `toolChoice: "required"`，强制 LLM 以工具调用的方式输出结构化数据。

**解决的问题**：传统 JSON mode 没有 schema 校验，LLM 可能输出不合法的 JSON。工具模式有内置的 schema 约束，比 JSON mode 更可靠。

**什么场景值得借鉴**：任何需要 LLM 输出结构化数据（JSON、表格、配置）的系统。

### OpenCode：Doom Loop 检测——"发现重复无用功就停"

`packages/opencode/src/session/processor.ts:152-176`：连续 3 次相同参数调用同一工具时触发权限询问。检测条件精确到 `JSON.stringify` 级别的参数比较。

**解决的问题**：比单纯的迭代预算更智能——不是"跑满 N 轮就停"，而是"发现模型在钻牛角尖就停"。

**什么场景值得借鉴**：任何面向终端用户的交互式 Agent。

## 10.6 设计思想总结

如果我要自己构建一个 Agent 系统，验证循环部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 参数类型转换 | LLM 常输出字符串化数值/布尔值，先 cast 再 validate |
| ☐ | 参数约束校验 | 必填、范围、枚举、长度检查，失败返回错误给 LLM 修正 |
| ☐ | 工具调用修复 | 大小写纠正、不存在的工具优雅降级 |
| ☐ | 重复调用检测 | 相同参数反复调用时提醒 LLM 停止 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 多模型后端适配 | Schema sanitizer（等效转换到最大公约数） | Hermes |
| 极简部署 / 零外部依赖 | 手写轻量 JSON Schema 校验器（cast + validate） | nanobot |
| 长时间任务 / 轮询场景 | 渐进式循环检测（warn → critical → circuit_breaker） | OpenClaw |
| IDE 集成 / 结构化输出 | StructuredOutput 工具强制 + zod 校验 | OpenCode |
| 高风险操作 / 架构决策 | Clarify 工具（LLM 主动确认用户意图） | Hermes |
| 配置复杂的生产系统 | Doctor 诊断命令（检测 + 修复建议） | OpenClaw |
| 审批误报多的场景 | Smart approval（aux LLM 仲裁） | Hermes |

### 最重要的三条经验

1. **"先宽容转换、后严格校验"是类型校验的最佳顺序**：nanobot 的两阶段管道说明，LLM 的参数输出是"大致正确但类型不精确"的。如果直接严格校验，会产生大量误报；先 cast 给 LLM 一个容错窗口，再 validate 保证正确性。

2. **LLM 的错误应该是可恢复的循环内错误**：nanobot 返回错误字符串让 LLM 自行修正、OpenCode 降级为 `invalid` 工具保留流连续性——这些设计共同说明：LLM 的"手滑"是常态，不是异常。系统应该帮助 LLM 纠正，而不是一出错就崩溃。

3. **验证要嵌入关键路径，而不是作为独立检查点**：Hermes 的 schema sanitizer 在每次构建工具列表时运行、OpenClaw 的循环检测在每次工具调用后运行、OpenCode 的 Doom Loop 检测在流式事件处理中内联执行——验证不是"等做完了再检查"，而是"每走一步就看一下"。
