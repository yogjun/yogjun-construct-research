# 第5章 汇报成果——输出解析

> "实习生查完资料、做完分析，最后要把结果写成报告交给主管。但主管不是谁的话都听——格式不对要重写，数据错了要核对，泄露了内部信息要追责。输出解析，就是 Agent 写完报告后的'质检与包装'环节。"

---

## 5.1 开篇故事：小李的报告风波

实习生小李花了整整一上午，终于完成了竞品调研。他把三份资料整理成一份报告，兴冲冲地发给主管。

**第一轮汇报**：主管看了一眼，皱起眉头——报告里夹杂着小李的"内心独白"："让我想想竞品 A 的价格……嗯，应该是 99 美元……"这些思考过程原封不动地出现在正文里。主管回复："把'内心戏'删掉，我只要结论。"

**第二轮汇报**：小李删掉思考过程，重新发送。主管又发现问题——报告里引用了一个叫 `web_search` 的工具输出，但格式是原始 JSON，主管根本看不懂。更糟的是，其中一段输出长达 3 万字符，把邮件系统都卡住了。主管回复："格式化一下，太长的内容截断到一页纸。"

**第三轮汇报**：小李做了精简和格式化。这次主管基本满意，但注意到一个细节：报告末尾有一段奇怪的符号 `[[reply:123]]`，像是某种内部指令。主管警惕地问："这是什么？是不是把不该给我看的东西也贴进来了？"小李赶紧检查，发现这是系统生成的回复标记，确实不该出现在用户可见的内容里。

**第四轮汇报**：经过三轮修改，小李终于交出了合格的报告——内容干净、格式正确、没有内部标记泄露。

**Agent 的输出解析，就是小李这四轮修改的自动化版本。** 它的核心任务是：把 LLM 生成的"原始草稿"转化为"可交付的成果"，同时确保不泄露内部信息、不传递错误格式、不撑爆系统带宽。

但 Agent 面临一个实习生没有的问题：LLM 的"原始草稿"来自不同的"供应商"（OpenAI、Anthropic、DeepSeek 等），每个供应商的格式都不一样。有的把工具调用放在 `tool_calls` 字段，有的放在 `content_blocks` 里，有的直接塞进正文。输出解析必须把这些"方言"统一翻译成系统内部的标准格式。

---

## 5.2 业务概念：输出解析是什么

**输出解析（Output Parsing）**是 Agent 系统的"质检与包装车间"。它位于 LLM 返回原始响应与系统内部消费之间，负责将不可控的模型输出转化为可控的标准化内容。

### 技术定义

输出解析由三个核心职责构成：

1. **格式归一化**：将不同 Provider（OpenAI、Anthropic、DeepSeek 等）的差异化响应格式统一为内部标准结构，提取 `content`、`tool_calls`、`reasoning`、`finish_reason` 等语义单元
2. **内容清洗**：剥离模型泄露的内部标记（如 `<think>` 标签、推理过程），截断过长的工具输出，防止敏感信息外泄
3. **状态决策**：根据解析结果决定下一步——是执行工具、继续循环，还是向用户交付最终答案

> 💡 **名词解释：Provider（模型提供商）**
>
> 通俗地说：不同的"快递公司"——有的用顺丰，有的用中通，包裹（API 响应）的包装格式各不相同。
>
> 技术定义：提供大语言模型 API 服务的厂商，如 OpenAI、Anthropic、Google（Gemini）、DeepSeek、Moonshot 等。不同 Provider 对 tool call、reasoning content、流式事件的封装格式存在差异。

> 💡 **名词解释：Reasoning Content（推理内容）**
>
> 通俗地说：小李写报告时在心里嘀咕的"让我想想……"——这是他的思考过程，不是最终结论。
>
> 技术定义：部分模型（如 DeepSeek-R1、Claude 3.7 Sonnet）在生成最终答案前会先输出一段内部推理文本。这段内容对调试有用，但不应展示给最终用户，也不应污染对话历史。

### 一句话说清边界

- **输出解析负责**：把 LLM 的原始响应翻译成系统能理解的结构化消息，清洗泄露标记，截断超长输出
- **输出解析不负责**：具体工具怎么执行（那是工具系统）、对话历史怎么存储（那是记忆系统）、循环什么时候终止（那是编排循环）

### 没有输出解析会怎样？

如果把输出解析从 Agent 中拿掉：

- **用户看到模型的"内心独白"**：DeepSeek 的 `<think>...</think>` 标签直接出现在聊天界面，体验极差
- **工具调用无法执行**：OpenAI 用 `tool_calls[].function.name`，Anthropic 用 `content_blocks[].tool_use.name`——不做归一化，系统根本不知道模型想调用什么工具
- **非法 JSON 直接崩溃**：本地模型（如 GLM-5.1 via Ollama）经常生成 trailing comma 或 Python `None` 作为工具参数，`json.loads` 一抛异常，整个会话中断
- **消息序列损坏导致死循环**：工具调用轮次异常中断后，历史记录中留下"孤儿工具结果"，下一轮 API 返回空内容，触发无限空回复循环

## 5.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，输出解析的**最小可行实现**只需要以下四个要素：

### 要素一：响应归一化

把不同 Provider 的原始响应统一为内部标准结构（`content`、`tool_calls`、`finish_reason`）。

### 要素二：内容清洗

剥离 `<think>`、`<thinking>` 等模型泄露的内部标记，防止推理内容进入用户可见输出。

### 要素三：工具参数校验与修复

工具调用的参数必须是合法 JSON。LLM 输出经常不合法——需要修复或降级，而不是直接崩溃。

### 要素四：消息序列防御性修复

每次调用 API 前，检查并修复消息历史中的角色交替违规、孤儿工具结果等问题。

```python
# 所有 Agent 都必须有的"最小可行输出解析"
# 就像实习生交报告前的"最低检查清单"

def parse_llm_response(raw_response, valid_tool_names):
    # ① 响应归一化：把 Provider 的"方言"翻译成普通话
    normalized = {
        "content": extract_content(raw_response),      # 提取正文
        "tool_calls": extract_tool_calls(raw_response), # 提取工具调用意图
        "finish_reason": raw_response.finish_reason,   # 停止原因
        "reasoning": extract_reasoning(raw_response),  # 提取推理内容（调试用）
    }
    
    # ② 内容清洗：删掉"内心独白"，只保留结论
    if normalized["content"]:
        normalized["content"] = strip_think_blocks(normalized["content"])
    
    # ③ 工具参数校验与修复：参数必须是合法 JSON
    for tc in normalized["tool_calls"] or []:
        args = tc["arguments"]
        if not args or args.strip() == "":
            tc["arguments"] = "{}"          # 空参数 → 空对象
        elif args == "None":
            tc["arguments"] = "{}"          # Python None → 空对象
        else:
            try:
                json.loads(args)             # 能解析？没问题
            except json.JSONDecodeError:
                # 实习生填表写错了——试着修一下，修不好就空着
                fixed = try_repair_json(args)
                tc["arguments"] = fixed if fixed else "{}"
    
    # ④ 消息序列防御性修复：检查有没有"孤儿工具结果"
    messages = sanitize_message_sequence(messages)
    
    return normalized, messages


def sanitize_message_sequence(messages):
    """修复消息序列中的'断链'——就像检查报告页码是否连续"""
    # 收集 assistant 声明过的 tool_call_id
    declared_ids = set()
    for m in messages:
        if m.get("role") == "assistant":
            for tc in m.get("tool_calls") or []:
                declared_ids.add(tc.get("id"))
    
    # 收集 tool 消息实际回应的 id
    result_ids = set()
    for m in messages:
        if m.get("role") == "tool":
            result_ids.add(m.get("tool_call_id"))
    
    # 删除"没有对应 assistant 声明"的孤儿 tool result
    orphaned = result_ids - declared_ids
    messages = [m for m in messages if not (
        m.get("role") == "tool" and m.get("tool_call_id") in orphaned
    )]
    
    # 为"缺少 tool result"的 tool_call 注入占位结果
    missing = declared_ids - result_ids
    # ... 在对应 assistant 消息后插入 stub result
    
    return messages
```

**这就是"底线"**。少于这四点，Agent 的输出就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 响应归一化 | 每新增一个 Provider 就要改一遍核心循环 |
| 内容清洗 | 用户看到模型的推理过程，体验极差 |
| 工具参数校验与修复 | 非法 JSON 直接崩溃，会话中断 |
| 消息序列防御性修复 | 孤儿工具结果导致 API 400 或空回复死循环 |

## 5.4 四个项目的实现对比

四个框架都在上述"底线"之上，基于各自的部署场景做了截然不同的扩展。

### Hermes Agent：Transport 归一化 + 五层防御修复链

**设计定位**：Provider 生态碎片化是长期现实，输出解析必须像"万能翻译器"一样兼容 16+ 个 Provider——适合跨平台部署的网关型 Agent。

> 💡 **名词解释：Transport 层（传输层）**
>
> 通俗地说：公司有一个"翻译部"，专门负责把不同快递公司（Provider）的包裹格式翻译成公司内部统一的标准格式。核心业务部门（编排循环）只认标准格式，不需要知道快递公司是顺丰还是中通。
>
> 技术定义：Hermes 在 `agent/transports/` 目录下为每个 Provider 模式（chat_completions、anthropic_messages、bedrock_converse、codex_responses）实现独立的 Transport 类，统一输出 `NormalizedResponse`。核心循环通过 `_get_transport()` 动态获取，无 Provider 感知代码。

> 💡 **名词解释：NormalizedResponse（归一化响应）**
>
> 通俗地说：翻译部输出的"标准格式报告"——不管原始包裹长什么样，最后都变成统一模板的报告，方便后续部门处理。
>
> 技术定义：Hermes 定义的 dataclass，包含 `content`、`tool_calls`、`reasoning`、`finish_reason`、`usage` 等跨 Provider 通用字段。`ToolCall.function` 返回 `self` 的巧妙设计让旧代码中的 `tc.function.name` 无需修改即可兼容。

> 💡 **名词解释：StreamingThinkScrubber（流式思考清洗器）**
>
> 通俗地说：小李在电话里向主管实时汇报，但偶尔会不小心说出"让我想想……"——旁边有个助手，听到这种话就自动消音，只让主管听到正式结论。
>
> 技术定义：Hermes 在 SSE 流式传输中维护跨 delta 边界的状态机，跟踪 `<think>` 标签的开启和关闭。Per-delta 正则无法处理标签被拆分到多个 delta 的情况，状态机通过 `_in_block` 和 `_buf` 字段保证推理内容不会泄漏到用户可见输出。

**关键源码位置**：
- Transport 归一化：`agent/transports/types.py:18-77`
- Reasoning 多层提取：`run_agent.py:3343-3408`
- 流式状态机清洗：`agent/think_scrubber.py:64-201`
- 工具参数修复：`run_agent.py:613-706`
- 消息序列防御修复：`run_agent.py:5332-5400`
- Reasoning 双轨回传：`run_agent.py:9201-9269`

```python
# Hermes 的输出解析：像一家跨国公司的"翻译与质检中心"
# 16+ 个快递公司的包裹都能译，还能自动修复破损单据

class HermesOutputParser:
    def parse_response(self, raw_response):
        # ① 翻译部上岗：不管什么快递公司的包裹，统一译成标准格式
        transport = self._get_transport()          # 根据 api_mode 选翻译员
        normalized = transport.normalize_response(raw_response)
        
        # ② 提取"内心独白"（reasoning）——四层回退策略
        reasoning = self._extract_reasoning(normalized)
        #   第1层：直接 reasoning 字段（DeepSeek、Qwen）
        #   第2层：reasoning_content 字段（Moonshot、Novita）
        #   第3层：reasoning_details 数组（OpenRouter）
        #   第4层：内联 <think> 标签正则提取（MiniMax、GLM）
        
        # ③ 清洗正文：把推理标签从 content 中剥离
        # 否则用户会看到"让我想想……"，还会膨胀 16% 的上下文
        content = self._strip_think_blocks(normalized.content)
        
        # ④ 修复工具参数——五层渐进式修复
        for tc in normalized.tool_calls or []:
            args = tc.function.arguments
            if not args or args == "None":
                tc.function.arguments = "{}"
            else:
                try:
                    json.loads(args, strict=False)   # Pass 0：允许控制字符
                except:
                    fixed = self._repair_tool_call_arguments(args)  # Pass 1-4
                    tc.function.arguments = fixed     # 修不好就回退到 "{}"
        
        # ⑤ 构建标准 assistant 消息
        assistant_msg = {
            "role": "assistant",
            "content": content,
            "reasoning": reasoning,                   # 内部调试用
            "tool_calls": [...],                      # 标准化后的工具调用
        }
        
        # ⑥ API 回传前：根据目标 Provider 重新映射 reasoning 字段
        # DeepSeek 要空格占位、Kimi 要 reasoning_content、Anthropic 要 details
        self._copy_reasoning_content_for_api(assistant_msg, api_msg)
        
        return assistant_msg
    
    def sanitize_messages(self, messages):
        # ⑦ 每次调用 API 前的"体检"——修复断链
        messages = self._sanitize_api_messages(messages)      # 删孤儿 tool result
        messages = self._repair_message_sequence(messages)    # 修复角色交替
        messages = self._drop_thinking_only_and_merge_users(messages)  # 删纯 thinking turn
        return messages
```

### nanobot：三层过滤管道 + 历史防腐

**设计定位**：输出解析要极简、零外部依赖、人可理解——适合个人助手场景。

> 💡 **名词解释：Session Poisoning（会话中毒）**
>
> 通俗地说：小李在某次汇报中出了错，但他把这份错误报告也存进了档案柜。下次主管让他基于档案写新报告时，错误报告被一起参考，导致新报告也出错——错误像病毒一样在档案中传播。
>
> 技术定义：nanobot 的 issue #1303 记录的真实事故：LLM 返回 `finish_reason="error"` 的响应被存入 `session.messages` 后，下一轮请求将该错误内容作为 assistant 消息发送给 Provider，触发 400 错误。由于错误响应被持久化，后续每一轮都会重复触发 400，形成永久性中毒循环。

> 💡 **名词解释：Runtime Context Tag（运行时上下文标记）**
>
> 通俗地说：小李每次汇报前，秘书都会在他耳边提醒"现在是周三下午 3 点，你在会议室 A"。这个提醒对当前汇报有用，但不应该被写进档案——否则档案里全是重复的时间地点信息。
>
> 技术定义：nanobot 每轮在 user 消息前注入 `[Runtime Context — metadata only]` 前缀，包含当前时间、渠道等信息。`_save_turn` 在持久化时识别该标记并剥离，防止运行时元数据污染长期记忆。

**关键源码位置**：
- Think 块剥离：`nanobot/agent/loop.py:165-170`
- Error 响应过滤：`nanobot/agent/loop.py:232-245`
- 回合持久化防腐：`nanobot/agent/loop.py:458-491`
- 空 content 消毒：`nanobot/providers/base.py:108-152`
- 工具提示格式化：`nanobot/agent/loop.py:172-181`

```python
# nanobot 的输出解析：像一个极简主义者的"报告检查流程"
# 只有三道工序，但每道都直击要害

class NanobotOutputParser:
    def parse_response(self, response):
        # ① 语义清洗：删掉"内心独白"
        clean = self._strip_think(response.content)
        
        if response.has_tool_calls:
            # 工具调用分支：给渠道发一个轻量进度提示
            hint = self._tool_hint(response.tool_calls)   # "web_search('竞品定价')"
            return {"type": "tool_calls", "hint": hint, "tool_calls": response.tool_calls}
        
        else:
            # 最终回复分支——关键防御！
            if response.finish_reason == "error":
                # ⚠️ 错误响应绝对不能进档案！否则档案会"中毒"
                # 就像把写错的草稿也存进档案柜，下次会越写越错
                logger.error("LLM returned error: {}", clean[:200])
                return {"type": "error", "content": clean or "Sorry, I encountered an error."}
            
            return {"type": "final", "content": clean}
    
    def save_turn(self, session, messages, skip):
        # ② 历史防腐：什么能进档案，什么不能
        for m in messages[skip:]:
            entry = dict(m)
            role, content = entry.get("role"), entry.get("content")
            
            # 空 assistant 消息会 poison session——跳过
            if role == "assistant" and not content and not entry.get("tool_calls"):
                continue
            
            # 工具结果太长？截断到 16K，否则档案柜塞爆
            if role == "tool" and isinstance(content, str) and len(content) > 16_000:
                entry["content"] = content[:16_000] + "\n... (truncated)"
            
            # 运行时上下文标记？剥离，不存档案
            elif role == "user" and isinstance(content, str):
                if content.startswith("[Runtime Context"):
                    parts = content.split("\n\n", 1)
                    entry["content"] = parts[1] if len(parts) > 1 else ""
                # base64 图片替换成占位符，节省空间
                if isinstance(content, list):
                    for c in content:
                        if c.get("type") == "image_url" and c["image_url"]["url"].startswith("data:image/"):
                            c["type"] = "text"
                            c["text"] = "[image]"
            
            session.messages.append(entry)
```

### OpenClaw：多级流式过滤器管道

**设计定位**：输出解析是生产级网关的"安全边界"——流式、增量、防御性编程是默认假设。

> 💡 **名词解释：Delta Buffer（增量缓冲区）**
>
> 通俗地说：主管在电话里实时听小李汇报，但有的电话线路会"重播"——把刚才说过的话再讲一遍。Delta Buffer 就是主管手里的笔记本，他只记录"新内容"，重复的部分自动忽略。
>
> 技术定义：OpenClaw 在 `handleMessageUpdate` 中维护 `deltaBuffer` 累积整个 assistant message 的全文。当 Provider 在 `text_end` 时重发完整内容（而非增量 delta），通过 `startsWith` 前缀比较提取真正的新增内容，保证输出严格单调递增。

> 💡 **名词解释：Block Chunker（块分片器）**
>
> 通俗地说：小李的报告太长，需要分页打印。但他不能在一行代码中间分页——否则代码块会被切成两半，读者看不懂。块分片器会找"安全分页点"，如果必须在代码块中间分页，它会主动加上"代码块结束"和"代码块开始"的标记，保证每页都是合法的 Markdown。
>
> 技术定义：OpenClaw 的 `EmbeddedBlockChunker` 将长文本按语义边界切分为适合 UI 渲染的块。当强制切断点落在 Markdown fenced code block 内部时，主动插入 close fence 并在下一 chunk 前缀插入 open fence，保证任意 chunk 都是合法 Markdown。

> 💡 **名词解释：Reply Directive（回复指令）**
>
> 通俗地说：小李的报告里夹杂着一些"内部指令"，比如"[[reply:123]]"——这是告诉系统"这条消息要回复到第 123 号对话"。这些指令对系统有用，但用户不应该看到。
>
> 技术定义：OpenClaw 从 LLM 输出中提取 `MEDIA:` 路径、`[[reply:ID]]` 目标、silent tokens 等机器指令，将机器控制流与用户可见文本分离。`createStreamingDirectiveAccumulator` 处理指令标签跨 chunk 的问题。

- 单调增量累积：`src/agents/pi-embedded-subscribe.handlers.messages.ts:146-162`

// OpenClaw 的输出解析：像一家跨国集团的"实时广播控制中心"
// 每个字都要实时处理，不能等整篇报告写完再校对

function handleMessageUpdate(ctx, evt) {
    const delta = evt.delta ?? "";
    const content = evt.content ?? "";
    
    // ① 单调增量累积：主管只记"新内容"，重复自动忽略
    let chunk = "";
    if (evtType === "text_delta") {
        chunk = delta;
    } else if (evtType === "text_end") {
        // 有的电话线路会在结束时重播全文——只取新增部分
        if (content.startsWith(ctx.state.deltaBuffer)) {
            chunk = content.slice(ctx.state.deltaBuffer.length);
        } else if (ctx.state.deltaBuffer.startsWith(content)) {
            chunk = "";  // 回退了？忽略
        } else if (!ctx.state.deltaBuffer.includes(content)) {
            chunk = content;  // 全新内容，全量追加
        }
    }
    
    if (chunk) {
        ctx.state.deltaBuffer += chunk;
        ctx.blockChunker?.append(chunk);  // 送入块分片器
    }
    
    // ② 状态化标签剥离：跨 chunk 跟踪 <think> 标签
    // 就像实时消音器——即使"让我想想"被拆成两个电话片段，也能正确识别
    const visibleDelta = ctx.stripBlockTags(chunk, ctx.state.partialBlockState);
    
    // ③ Reply 指令解析：提取内部指令，不让用户看到
    const parsed = ctx.consumePartialReplyDirectives(visibleDelta);
    
    // ④ 发射用户可见事件
    if (parsed.text) {
        emitAgentEvent({ stream: "assistant", data: { text: parsed.text, delta: visibleDelta } });
    }
}

function sanitizeToolResult(result) {
    // ⑤ 工具结果消毒：截断长文本、删除图片原始 bytes
    const content = Array.isArray(result.content) ? result.content : null;
    if (!content) return result;
    
    return content.map(item => {
        if (item.type === "text") {
            return { ...item, text: truncateToolText(item.text) };  // 截断到 8K
        }
        if (item.type === "image") {
            const cleaned = { ...item };
            delete cleaned.data;  // 删除原始 base64，只保留长度标记
            return { ...cleaned, bytes: item.data?.length, omitted: true };
        }
        return item;
    });
}

### OpenCode：流式事件路由 + 工具调用修复 + Doom Loop 检测

**设计定位**：让 AI SDK 处理底层协议，输出解析专注于"事件翻译与防御"——适合和 IDE 深度集成的场景。

> 💡 **名词解释：Doom Loop（厄运循环）**
>
> 通俗地说：实习生反复打开同一个网页查同一个信息，查了三遍还在查——主管看不下去了，弹窗问他"你确定还要再查一次吗？"
>
> 技术定义：OpenCode 在 `processor.ts` 中检测模型是否连续 3 次用相同参数调用同一个工具。触发后通过 `PermissionNext.ask` 请求用户确认，防止模型"钻牛角尖"消耗无限 token。

> 💡 **名词解释：experimental_repairToolCall（实验性工具调用修复）**
>
> 通俗地说：实习生写错了工具名称的大小写（`Read_File` 而不是 `read_file`），系统不是直接报错，而是先问"你是不是指 read_file？"——如果是，自动纠正；如果不是，降级为"无效工具"返回友好错误。
>
> 技术定义：OpenCode 在 AI SDK 的 `streamText` 配置中注册 `experimental_repairToolCall` 回调。对大小写错误自动修复；对不存在的工具名降级为 `invalid` 工具，保留流式输出连续性。

> 💡 **名词解释：Part（消息片段）**
>
> 通俗地说：一条消息不只是"一段文字"，可能包含"文字 + 工具调用 + 文件附件 + 压缩摘要"等多个部分。OpenCode 把消息的每个部分都拆成独立的"片段"来存储和更新。
>
> 技术定义：OpenCode 的三层存储中，`PartTable` 存储消息的各个内容片段（text / tool / reasoning / compaction / media 等）。一个 Message 可以有多个 Part，支持精细化查询和独立更新。

- 流式事件路由：`packages/opencode/src/session/processor.ts:55-176`
- 工具调用修复：`packages/opencode/src/session/llm.ts:178-198`
- Doom Loop 检测：`packages/opencode/src/session/processor.ts:151-176`
- 错误统一转换：`packages/opencode/src/session/message-v2.ts:827-913`
- 结构化输出工具：`packages/opencode/src/session/prompt.ts:928-955`

// OpenCode 的输出解析：像一个和设计软件深度集成的"实时字幕组"
// 一边接收信号，一边翻译、校对、打码，实时输出给观众

async function processStream(streamInput) {
    const stream = await LLM.stream(streamInput);
    
    for await (const value of stream.fullStream) {
        switch (value.type) {
            case "start":
                SessionStatus.set(sessionID, { type: "busy" });  // 开始直播
                break;
            
            case "reasoning-delta":
                // 实时更新推理片段——观众能看到"正在思考……"
                await Session.updatePartDelta({ partID: reasoningPart.id, field: "text", delta: value.text });
                break;
            
            case "tool-call": {
                const part = await Session.updatePart({
                    type: "tool", tool: value.toolName,
                    state: { status: "running", input: value.input }
                });
                
                // ⚠️ Doom Loop 检测：连续 3 次相同调用？弹窗确认
                const lastThree = parts.slice(-3);
                if (lastThree.length === 3 && lastThree.every(p =>
                    p.type === "tool" && p.tool === value.toolName &&
                    JSON.stringify(p.state.input) === JSON.stringify(value.input)
                )) {
                    await PermissionNext.ask({ permission: "doom_loop", patterns: [value.toolName] });
                }
                break;
            }
            
            case "tool-result":
                // 工具执行完成，更新片段状态
                await Session.updatePart({ ...part, state: { status: "done", result: value.result } });
                break;
            
            case "text-delta":
                // 实时更新正文——观众能看到打字效果
                await Session.updatePartDelta({ partID: textPart.id, field: "text", delta: value.text });
                break;
            
            case "error":
                // 统一错误转换：API 错误、网络错误、取消错误分类处理
                throw MessageV2.fromError(value.error, { providerID: model.providerID });
        }
    }
}

// 工具调用修复：大小写纠正 + 不存在工具降级
async function experimental_repairToolCall(failed) {
    const lower = failed.toolCall.toolName.toLowerCase();
    if (lower !== failed.toolCall.toolName && tools[lower]) {
        // 实习生手滑大小写——自动纠正
        return { ...failed.toolCall, toolName: lower };
    }
    // 工具根本不存在？降级为 invalid，不中断流
    return {
        ...failed.toolCall,
        toolName: "invalid",
        input: JSON.stringify({ tool: failed.toolCall.toolName, error: failed.error.message }),
    };
}

## 5.5 独特高价值设计：各项目的闪光点

每个项目都因为特定的场景诉求，做了其他项目没有做的高价值设计。

### Hermes Agent：Transport 归一化层——应对 Provider 生态碎片化的标准答案

`agent/transports/types.py:18-77` 定义了 `NormalizedResponse` 和 `ToolCall`，`ToolCall.function` 返回 `self` 的兼容性设计让 45+ 处旧代码无需修改即可迁移。

**解决的问题**：OpenAI 用 `message.tool_calls[].function.name`，Anthropic 用 `content_blocks[].tool_use.name`，Gemini 用 `parts[].functionCall`，Bedrock 用 `output.message.content[].toolUse`——没有归一化层，核心循环将与 Provider 实现深度耦合。

**什么场景值得借鉴**：任何需要支持 3 个以上 Provider 的 Agent 系统。归一化层是"尽早引入、后期省心"的设计。

### Hermes Agent：五层工具参数修复链

`run_agent.py:613-706`：从 `strict=False` 的 `json.loads` 到 trailing comma 修复、未闭合括号补全、多余括号删除、控制字符转义，最终回退到 `"{}"`。

**解决的问题**：本地模型（GLM-5.1 via Ollama、Qwen 等）经常生成非法 JSON 作为 tool-call arguments。直接崩溃会让用户体验极差；返回 `"{}"` 让模型在下一轮有机会自我纠正。

**什么场景值得借鉴**：使用本地模型或开放权重模型的系统。云端模型（GPT-4、Claude）很少出现这种问题，但本地模型是"标配"。

### Hermes Agent：Reasoning 双轨存储与五层回传

`run_agent.py:9201-9269`：内部用 `reasoning` 字段存储纯文本，API 回传时根据目标 Provider 重新映射为 `reasoning_content`（DeepSeek/Kimi）、`reasoning_details`（OpenRouter）或空格占位。

**解决的问题**：DeepSeek V4 Pro 要求 tool-call 轮次必须回传 `reasoning_content`，缺失即 400。不同 Provider 对 reasoning 的 schema 要求完全不同，双轨存储是唯一的兼容方案。

**什么场景值得借鉴**：任何支持 reasoning 模型且需要跨 Provider 切换的系统。

### nanobot："Error 不入历史"——4 行代码挡住整类事故

`nanobot/agent/loop.py:236-239`：

```python
if response.finish_reason == "error":
    final_content = clean or "Sorry, I encountered an error..."
    break
```

错误响应只返回给用户，**不写入 session.messages**。背后是 issue #1303 的真实事故：错误响应写入历史后，下一轮 LLM 看到畸形的 assistant 消息，反复触发 400，形成"毒消息→永久 400"死循环。

**什么场景值得借鉴**：所有 Agent 系统。这是一个反直觉但极其重要的工程经验——任何 LLM error 都属于"瞬时事件"，不该污染会话状态。

### nanobot：回合持久化防腐的四重过滤

`nanobot/agent/loop.py:458-491`：空 assistant 消息跳过、工具结果截断到 16K、运行时上下文剥离、base64 图片替换为 `[image]`。

**解决的问题**：这四行过滤逻辑比任何 prompt engineering 都更能保障系统的长期稳定运行。空消息会 poison session，超长工具结果会撑爆上下文，运行时元数据会污染长期记忆。

**什么场景值得借鉴**：所有需要持久化对话历史的 Agent 系统。

### OpenClaw：Delta Buffer 单调累积——不信任 Provider 的防御性编程

`src/agents/pi-embedded-subscribe.handlers.messages.ts:146-162`：用 `deltaBuffer` 作为 ground truth，通过 `startsWith` 前缀比较计算真正的新增内容。

**解决的问题**：部分 Provider 在 `text_end` 时会重发完整内容（而非增量 delta），如果不做单调性保证，前端会看到文字回跳或重复追加。

**什么场景值得借鉴**：任何支持流式输出且需要实时 UI 更新的系统。

### OpenClaw：Block Chunker 的 Fence 保护

`src/agents/pi-embedded-block-chunker.ts:125-218`：当强制切断点落在 Markdown fenced code block 内部时，主动插入 close fence 并在下一 chunk 前缀插入 open fence。

**解决的问题**：前端增量渲染时，如果在一个代码块中间切断，Markdown 解析会错乱（fence 未闭合导致后续所有内容被误解析为代码）。

**什么场景值得借鉴**：任何需要流式渲染 Markdown 内容（尤其是代码块）的系统。

### OpenCode：Doom Loop 检测——在输出解析层拦截"钻牛角尖"

`packages/opencode/src/session/processor.ts:151-176`：`DOOM_LOOP_THRESHOLD = 3`，连续 3 次相同工具调用触发 `PermissionNext.ask` 弹窗确认。

**解决的问题**：模型在长任务中可能反复调用同一个工具（如反复读取同一个文件），消耗大量 token。这比单纯的迭代预算更智能——它不是"跑满 N 轮就停"，而是"发现重复无用功就停"。

**什么场景值得借鉴**：任何面向终端用户、需要防止模型"钻牛角尖"的交互式 Agent。

### OpenCode：工具调用修复的优雅降级

`packages/opencode/src/session/llm.ts:178-198`：大小写错误自动修复，不存在工具降级为 `invalid` 工具返回友好错误。

**解决的问题**：LLM 拼错工具名（大小写错误）是常见"手滑"。自动修复比报错更优雅；降级为 `invalid` 工具而非直接终止，保留了流式输出的连续性。

**什么场景值得借鉴**：任何使用流式输出、需要高可用用户体验的系统。

## 5.6 设计思想总结

如果我要自己构建一个 Agent 系统，输出解析部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | 响应归一化 | 定义 `NormalizedResponse` 标准结构，屏蔽 Provider 差异 |
| ☐ | 内容清洗 | 剥离 `<think>`、`<thinking>` 等模型泄露的内部标记 |
| ☐ | 工具参数校验 | 工具调用的参数必须是合法 JSON，非法时修复或降级 |
| ☐ | 消息序列防御性修复 | 每次 API 调用前检查孤儿 tool result、角色交替违规 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 支持 3+ Provider | Transport 归一化层 | Hermes |
| 使用本地/开放权重模型 | 五层工具参数修复链 | Hermes |
| 支持 reasoning 模型 | 双轨存储 + Provider 级回传映射 | Hermes |
| 流式输出 + 实时 UI | Delta Buffer 单调累积 + Block Chunker | OpenClaw |
| 流式渲染 Markdown | Fence 保护（主动关闭/重新打开） | OpenClaw |
| 生产级网关 + 大输出工具 | 工具结果消毒（截断 + 脱敏 + 媒体提取） | OpenClaw |
| IDE 集成 / 交互式 Agent | Doom Loop 检测 + 工具调用修复 | OpenCode |
| 极简个人助手 | 三层过滤管道 + error 不入历史 | nanobot |
| 跨会话持久化 | 回合持久化防腐（截断/剥离/替换） | nanobot |

### 最重要的三条经验

1. **Provider 差异必须被隔离在单一层**：不要让 `if api_mode == "openai"` 这样的分支散落在核心循环中。Hermes 的 Transport 层和 OpenCode 的 AI SDK 封装都是正确的做法。

2. **把"模型输出不可靠"作为第一性原理**：模型会生成非法 JSON、错误的工具名、truncated arguments、泄露的 `<think>` 标签。为每种不可靠性设计降级路径（修复 → 重试 → 回退 → 报错），而不是假设模型总是返回合法内容。

3. **流式处理需要状态机**：如果支持 SSE 流式输出，任何跨 delta 的语义单元（think block、XML tag、JSON object）都必须用状态机维护，不能用 per-delta 正则。OpenClaw 的 `deltaBuffer` 和 Hermes 的 `StreamingThinkScrubber` 都是这一原则的体现。
