# 第1章 工作节奏——编排循环

> "实习生不会接到任务就直接给你一份报告。他会先问清楚要求，然后查资料、记笔记、遇到问题换方法——这个过程反复推进，直到完成为止。编排循环，就是让 Agent 学会这套'工作节奏'。"

---

## 1.1 开篇故事：小李的第一份竞品调研

早上 9:30，实习生小李接到主管的任务："调研我们三个主要竞品的定价策略，下午 5 点给我报告。"

小李没有直接坐在工位上"思考"然后凭空写出一份报告。他的工作是这样推进的：

**第一轮**：他先问主管——"三个竞品是哪三家？""报告需要什么格式？"主管回复后，他把要点记在笔记本上。

**第二轮**：他打开浏览器，搜索竞品 A 的官网，找到定价页面，把价格、计费模式抄到笔记本上。

**第三轮**：他继续搜竞品 B，发现官网价格隐藏了，需要注册才能看。他没放弃，换了个搜索引擎，在第三方评测网站上找到了参考价格。

**第四轮**：搜竞品 C 时，他发现 C 的定价不是按用户数收费，而是按 API 调用量收费——这和 A、B 完全不同。他在笔记本上标注了这个异常，决定后面重点分析这种差异。

**第五轮**：笔记本上的信息已经够多了。他开始整理：把零散的价格数据按"竞品名称-定价模式-单价-备注"的格式填入表格，写出分析结论，检查一遍有没有错别字，发到主管邮箱。

这个过程中，小李经历了完整的**"理解→执行→观察→调整→再执行"**循环。每一轮结束后，他都会根据上一轮的结果决定下一步做什么——不是主管手把手教他，而是他自己推进。

**Agent 的编排循环，就是模拟这个工作节奏。**

但有一个关键区别：小李是真人，他不会无限循环下去。而 Agent 没有人类的"累了就停"的本能——如果模型在某一步陷入了死胡同（比如反复调用同一个搜索工具却期待不同的结果），它可能会永远循环下去。所以编排循环的设计核心问题是：**如何让 Agent 像小李一样自主推进，同时又不会陷入无限循环？**

---

## 1.2 业务概念：编排循环是什么

**编排循环（Orchestration Loop）**是 Agent 系统的"心脏"。它负责把一次用户指令转化为多轮"推理→行动→观察→再推理"的自治迭代，直到任务完成或系统判定需要停止。

### 技术定义

编排循环以大语言模型（LLM）为核心决策器，遵循 **ReAct 范式**（Reasoning + Acting）：

1. **推理（Reasoning）**：LLM 分析当前上下文，决定下一步做什么
2. **行动（Acting）**：如果 LLM 认为需要工具（如搜索、读文件、发邮件），循环负责调用工具
3. **观察（Observation）**：工具执行的结果被回灌到上下文中
4. **再推理**：LLM 基于新的观察结果，决定继续行动还是给出最终答案

这个"推理→行动→观察→再推理"的循环反复推进，直到 LLM 不再请求工具（认为任务已完成），或者触发了循环的终止条件（如迭代预算耗尽、用户中断）。

> 💡 **名词解释：ReAct 范式**
>
> 通俗地说：实习生接到任务后"先想想怎么做，然后动手做，做完看看结果，再想下一步"的工作方法。
>
> 技术定义：一种将 LLM 的推理能力与外部工具的执行能力相结合的 Agent 设计模式。核心思想是让模型在每一步都先"思考"（生成推理文本），再"行动"（调用工具），并将工具结果作为"观察"回输给模型，形成闭环。

### 一句话说清边界

- **编排循环负责**：什么时候调用 LLM、什么时候执行工具、什么时候停止、怎么应对中断和错误
- **编排循环不负责**：具体工具怎么实现（那是工具系统）、对话历史怎么存储（那是记忆系统）、提示词怎么拼（那是 Prompt 构建）

### 没有编排循环会怎样？

如果把编排循环从 Agent 系统中拿掉，系统会退化成**单轮问答机**：

- LLM 说"我需要搜索竞品 A 的价格"，但没人去执行搜索，对话直接断在"Act"步骤上
- 即使手动执行了搜索，结果也无人回灌给 LLM，模型永远看不到工具的执行反馈
- 用户面对一个 30 秒沉默的界面，不知道 Agent 是在思考还是已经卡死

## 1.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，编排循环的**最小可行实现**只需要以下四个要素：

### 要素一：ReAct 主循环

一个 `while` 循环，反复执行"调 LLM → 执行工具 → 回灌结果"。

### 要素二：循环终止条件

主要出口：LLM 不再请求工具（`finish_reason == "stop"` 或 `has_tool_calls == False`）。

兜底出口：达到最大迭代次数，强制终止。

### 要素三：工具执行与结果回灌

把 LLM 返回的 `tool_calls` 逐个执行，将结果以 `tool` 角色的消息追加到对话历史中。

### 要素四：迭代预算

防止模型陷入死循环（如反复调用同一个工具），设置一个硬上限。

```python
# 所有 Agent 都必须有的"最小可行编排循环"
# 就像实习生工作的"最低要求清单"

def agent_loop(user_input, tools, max_iterations=40):
    messages = [system_message, user_message(user_input)]
    
    for iteration in range(max_iterations):
        # 实习生拿起电话，向"超级学霸"（LLM）请教下一步怎么做
        response = call_llm(messages, tools=tools.get_definitions())
        
        if response.has_tool_calls:
            # 学霸说："去查一下竞品 A 的价格"
            # 实习生记下学霸的指示（assistant 消息）
            messages.append(assistant_message(response.content, response.tool_calls))
            
            # 实习生动手执行——打开浏览器搜索
            for tc in response.tool_calls:
                result = tools.execute(tc.name, tc.arguments)
                # 把搜索结果记到笔记本上（tool 结果回灌）
                messages.append(tool_result(tc.id, result))
            
            # 本轮结束，回到循环顶部——再向学霸汇报搜索结果
            continue
        
        else:
            # 学霸说："报告写好了，这就是最终答案"
            # 任务完成，循环退出
            return response.content
    
    # 兜底：迭代预算耗尽。就像实习生忙了一整天还没搞定，
    # 领导说"先到这里，明天继续"——至少给用户一个交代
    return f"达到最大迭代次数（{max_iterations}），任务未能完成。"
```

**这就是"底线"**。少于这四点，Agent 就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| ReAct 主循环 | 工具链断裂，单次调用后无人执行工具 |
| 终止条件 | 模型可能无限循环，API 费用爆炸 |
| 工具执行与回灌 | LLM 看不到工具结果，后续推理失去依据 |
| 迭代预算 | 遇到"毒消息"或模型死循环时无法自救 |

## 1.4 四个项目的实现对比

四个框架都在上述"底线"之上做了各自的扩展。本节用伪代码展示它们的核心差异。

### Hermes Agent：带预算控制的可中断 ReAct 循环

**设计定位**：循环要简单，中断要可靠，工具可以并发——适合同时服务多个用户的网关型 Agent。

**关键源码位置**：
- 核心循环：`run_agent.py:11158`
- 预算控制：`run_agent.py:272`（`IterationBudget`）
- 可中断 API 调用：`run_agent.py:6661`
- 线程级中断：`tools/interrupt.py:35`
- 并发工具执行：`run_agent.py:9784`

```python
# Hermes 的编排循环：像一家大型外包公司的项目管控系统
# 每个项目有"加班额度"，客户可以随时喊停，多个任务可以并行推进

class HermesAgentLoop:
    def run_conversation(self, user_message):
        messages = init_messages(user_message)
        api_call_count = 0
        
        # 绑定当前线程——客户喊停时，只停这个项目，不影响隔壁项目组
        bind_execution_thread()
        
        # 双保险循环条件：迭代次数 + 预算额度
        while (api_call_count < max_iterations 
               and iteration_budget.remaining > 0) \
              or budget_grace_call:
            
            if interrupt_requested:           # 客户喊"停"——立即退出
                break
            
            # grace call：加班额度用完了，但领导允许花5分钟做个简短汇报再走
            if budget_grace_call:
                budget_grace_call = False     # 最后一次机会，用完即止
            elif not iteration_budget.consume():
                break                         # 真的没额度了，必须下班
            
            api_call_count += 1
            
            # 取出客户中途追加的修改意见（不中断循环，只调整方向）
            steer = drain_pending_steer()
            api_messages = build_api_messages(messages, steer)
            api_messages = sanitize(api_messages)  # 修正消息序列中的"断链"
            
            # 可中断的 API 调用：在后台线程里等 LLM 回复
            # 主线程每 0.3 秒检查一次"有没有客户喊停"
            response = interruptible_api_call(api_messages)
            
            if response.has_tool_calls:
                # 判断这批工具能不能并行执行
                # 比如"同时读三个文件"可以并行，"先读后写同一个文件"不行
                if should_parallelize(response.tool_calls):
                    execute_concurrent(response.tool_calls, messages)
                else:
                    execute_sequential(response.tool_calls, messages)
                
                # 把客户中途的修改意见，附在最后一个工具结果的后面
                # 这样 LLM 下一轮就能看到，但又不破坏对话的 alternation 规则
                apply_steer_to_last_tool_result(messages)
            else:
                final_response = response.content
                break
        
        # 预算耗尽时的优雅收尾：给 LLM 一次"总结发言"的机会
        if final_response is None and budget_exhausted:
            final_response = handle_max_iterations(messages)
        
        persist_session(messages)             # 保存会话记录
        cleanup_task_resources(task_id)       # 释放线程等资源
        return final_response
```

### nanobot：两层嵌套的 actor + ReAct 循环

**设计定位**：循环分两层就够了，内层要纯函数，错误不入历史——适合个人助手场景。

**关键源码位置**：
- 内层 ReAct 循环：`nanobot/agent/loop.py:183-254`
- 外层消息泵：`nanobot/agent/loop.py:256-331`
- Error 隔离：`nanobot/agent/loop.py:236-239`
- 持久化消毒：`nanobot/agent/loop.py:458-491`

```python
# nanobot 的编排循环：像一个个人助理的日程本
# 外层是"消息收件箱"，内层是"今日待办清单"
# 所有事情一件一件做，但中途可以取消当前任务

async def run(self):  # 外层：消息泵（actor 模式）
    while self._running:
        # 每 1 秒检查一次收件箱——即使没有新消息，也让循环有机会响应"停止"信号
        msg = await wait_for(bus.consume_inbound(), timeout=1.0)
        
        cmd = msg.content.strip().lower()
        if cmd == "/stop":
            await handle_stop(msg)          # 取消当前任务——助理放下手头活
        elif cmd == "/restart":
            await handle_restart(msg)       # 重启整个系统
        else:
            # 把新任务派发给后台，但执行时加全局锁——助理一次只干一件事
            task = create_task(_dispatch(msg))
            active_tasks[msg.session_key].append(task)

async def _run_agent_loop(initial_messages):  # 内层：ReAct 状态机（纯函数）
    messages = initial_messages
    iteration = 0
    
    while iteration < max_iterations:        # 默认 40 轮——够用但不多给
        iteration += 1
        
        # 每轮都重新获取工具定义——支持 MCP 动态注册新工具
        tool_defs = tools.get_definitions()
        response = await provider.chat_with_retry(messages, tool_defs)
        
        if response.has_tool_calls:
            # 纯函数式拼接：不修改 session，返回新的 messages 列表
            messages = add_assistant_message(messages, response.content, tool_calls)
            
            for tc in response.tool_calls:
                result = await tools.execute(tc.name, tc.arguments)
                messages = add_tool_result(messages, tc.id, tc.name, result)
            continue                            # 还有工具要执行，继续循环
        
        else:
            clean = strip_think(response.content)
            
            # ⚠️ 关键防御：error 响应不写入历史！
            # 就像实习生记错了一个电话，如果把这个错号码写进笔记本，
            # 下次查电话时就会反复打错——形成"毒消息→永久错误"死循环
            if response.finish_reason == "error":
                final_content = clean or "Sorry, I encountered an error."
                break                           # break 但不持久化
            
            messages = add_assistant_message(messages, clean)
            final_content = clean
            break                               # 正常回复，任务完成
    
    if final_content is None:                  # 兜底：40 轮用完了
        final_content = "达到最大轮次，建议拆小步骤。"
    
    return final_content, tools_used, messages  # 纯函数：只返回值，不改 session
```

### OpenCode：单线程流式事件驱动循环

**设计定位**：让 AI SDK 处理流控制，循环只管调度——适合和 IDE 深度集成的场景。

**关键源码位置**：
- 主循环入口：`packages/opencode/src/session/prompt.ts:275`
- 流式事件处理：`packages/opencode/src/session/processor.ts:111-179`
- Doom loop 检测：`packages/opencode/src/session/processor.ts:20,151-176`
- 子任务内联：`packages/opencode/src/session/prompt.ts:353-526`

```typescript
// OpenCode 的编排循环：像一个和设计软件深度集成的工作室助理
// 单线程、流式输出、用户随时能看到助理在想什么

async function loop(sessionID) {
    let step = 0
    
    while (true) {
        if (abort.aborted) break                     // 用户点了"取消"
        
        // 扫描历史消息，识别待处理任务（子任务 / compaction）
        const msgs = await MessageV2.filterCompacted(MessageV2.stream(sessionID))
        const task = detect_pending_subtask_or_compaction(msgs)
        
        // 系统级任务插队：子任务和 compaction 优先于普通推理
        if (task?.type === "subtask") {
            // 内联执行子任务：在同一个循环里完成，不另开线程
            // 就像助理说"这个子任务我顺手做了"——简单但不适合长任务
            await TaskTool.execute(taskArgs, taskCtx)
            continue                                   // 做完子任务，回到循环顶部
        }
        
        if (task?.type === "compaction") {
            await SessionCompaction.process(task)      // 压缩历史消息
            continue
        }
        
        // 检查上下文是否溢出
        if (SessionCompaction.isOverflow(msgs)) {
            create_compaction_task()                   // 创建 compaction 任务，下轮处理
            continue
        }
        
        step++
        
        // 构建工具列表和 system prompt
        const tools = resolveTools(agent)
        
        // 流式调用 LLM——不是等全部想完再显示，而是一边想一边实时输出
        const stream = await LLM.stream({ messages: msgs, tools })
        
        for await (const event of stream.fullStream) {
            switch (event.type) {
                case "text-delta":
                    // 实时更新 UI：用户能看到助理正在打字
                    Session.updatePartDelta(event.text)
                    break
                
                case "tool-call":
                    // ⚠️ Doom Loop 检测：如果助理连续 3 次用相同参数调同一个工具
                    // 就像实习生反复打开同一个网页却期待不同结果——系统发现后弹窗确认
                    const lastThree = parts.slice(-DOOM_LOOP_THRESHOLD)  // = 3
                    if (lastThree.every(p => 
                        p.tool === event.toolName &&
                        JSON.stringify(p.input) === JSON.stringify(event.input)
                    )) {
                        await PermissionNext.ask({
                            permission: "doom_loop",
                            patterns: [event.toolName],
                        })
                    }
                    break
                
                case "tool-result":
                    Session.updatePart({ status: "done", result: event.result })
                    break
            }
        }
        
        // 检查是否完成：上一轮 assistant 的 finish 原因不是 "tool-calls"
        if (lastAssistant.finish && !["tool-calls", "unknown"].includes(lastAssistant.finish)) {
            break                                          // 任务完成，退出循环
        }
    }
}
```

### 四项目核心差异对比表

| 维度 | Hermes Agent | nanobot | OpenClaw | OpenCode |
|------|-------------|---------|----------|----------|
| **循环层级** | 3 层（CLI → chat → run_conversation） | 2 层（消息泵 → ReAct） | 5 层（Gateway → Lane → Run → Attempt → Stream） | 2 层（loop → processor） |
| **并发模型** | threading + ThreadPoolExecutor（工具可并行） | asyncio + 全局 Lock（串行） | 事件循环 + 双层队列 | 单线程事件循环 |
| **中断粒度** | 线程级（per-thread ID） | 任务级（asyncio.Task.cancel） | Lane 级（generation 标记） | 会话级（AbortController） |
| **预算控制** | IterationBudget + max_iterations + grace call | 硬编码 40 轮 | MAX_RUN_LOOP_ITERATIONS（动态计算） | agent.steps 配置 |
| **错误恢复** | 指数退避 + provider fallback | chat_with_retry 封装 | 五层恢复链 | 依赖 AI SDK |
| **子任务执行** | 异步派发，独立预算 | 通过 bus 回灌主会话 | Steer/Queue 双模式 | Inline 同步执行 |
| **进度反馈** | 无专门机制 | 思考摘要 + 工具调用提示 | Draft stream 节流输出 | 流式 text-delta |

## 1.5 独特高价值设计：各项目的闪光点

每个项目都因为特定的场景诉求，做了其他项目没有做的高价值设计。

### Hermes Agent：预算耗尽时的"Grace Call"

当 `IterationBudget` 耗尽时，Hermes 不会直接给用户一个硬截断的错误。它设置 `_budget_grace_call = True`，允许 LLM 再做**最后一次无工具的总结调用**（`run_agent.py:11174-11183`）。

**解决的问题**：用户看到"预算耗尽"的感受很差，像是被突然掐断。grace call 让用户看到一个自然的收尾——"我已经尽力了，这是目前的进展总结"。

**什么场景值得借鉴**：任何有"预算"或"配额"概念的 Agent 系统。预算是必要的，但预算耗尽时的用户体验比预算本身更重要。

### Hermes Agent：线程级中断与并发工具执行

在多会话网关场景下，一个用户的中断不能杀死其他用户的会话。Hermes 用 `set[int]` 精确到线程 ID（`tools/interrupt.py:35`），并做三层级联传播——主线程、并发工具工作线程、子 Agent（`run_agent.py:4593-4657`）。

同时，Hermes 是唯一支持工具级并行的框架：`_should_parallelize_tool_batch()` 用静态白名单 + 路径重叠检测做决策（`run_agent.py:377`）——保守但零误伤。

**什么场景值得借鉴**：需要同时服务多个用户、且工具调用可能长时间阻塞（如文件 IO、网络请求）的网关型 Agent。

### nanobot："错误不入历史"——4 行代码挡住整类事故

`nanobot/agent/loop.py:236-239`：

```python
if response.finish_reason == "error":
    final_content = clean or "Sorry, I encountered an error..."
    break
```

错误响应只返回给用户，**不写入 session.messages**。背后是 issue #1303 的真实事故：错误响应写入历史后，下一轮 LLM 看到畸形的 assistant 消息，反复触发 400，形成"毒消息→永久 400"死循环。

**什么场景值得借鉴**：所有 Agent 系统。这是一个反直觉但极其重要的工程经验——任何 LLM error 都属于"瞬时事件"，不该污染会话状态。

### nanobot：纯函数式内循环

`_run_agent_loop` 既不读 session 也不写 session，接收 `initial_messages` 后纯函数式拼接（`loop.py:183-254`）。这让 ReAct 状态机可以独立测试、被 CLI 入口和 Cron 入口复用，而无需关心持久化细节。

**什么场景值得借鉴**：需要多入口（聊天、CLI、cron）复用同一套推理逻辑的系统。

### OpenClaw：五层恢复链——生产级 Agent 的分界线

OpenClaw 的恢复策略按**成本从低到高**严格排序：`compaction`（纯计算）→ `tool result truncation`（局部修改）→ `Auth Profile 轮换`（切换 key）→ `thinking 降级`（降低能力）→ `model fallback`（切换模型）。

每一层都是前一层失败后的"最后手段"。这种"低成本优先"的排序最小化用户感知延迟（`run.ts:986-1094`）。

**什么场景值得借鉴**：7×24 小时运行的生产级网关服务。个人助手和 IDE 插件不需要这个，但对外服务的系统必须有。

### OpenClaw：Compaction 超时快照回退

当 compaction 阶段超时时，session 可能处于结构不一致的中间态。OpenClaw 在 compaction 等待前捕获 `preCompactionSnapshot`，超时后回退到该快照（`attempt.ts:1797-1883`）。

**什么场景值得借鉴**：任何在循环中执行"重写历史"操作（如上下文压缩、消息摘要）的系统。压缩期间的状态损坏是容易被忽视的边界情况。

### OpenCode：Doom Loop 检测

`DOOM_LOOP_THRESHOLD = 3`（`processor.ts:20`）：如果模型连续 3 次用相同参数调用同一个工具，系统判定为"死循环"，通过 `PermissionNext.ask` 弹窗请求用户确认（`processor.ts:151-176`）。

**什么场景值得借鉴**：任何面向终端用户、需要防止模型"钻牛角尖"的交互式 Agent。这比单纯的迭代预算更智能——它不是"跑满 N 轮就停"，而是"发现重复无用功就停"。

### OpenCode：流式事件驱动

OpenCode 基于 AI SDK 的 `fullStream`，将 LLM 输出解析为 `text-delta`、`tool-call`、`tool-result` 等事件类型。这让 IDE 可以实时显示模型的思考过程，而不是等全部输出完成再一次性显示。

**什么场景值得借鉴**：任何需要和 UI（IDE、聊天界面）深度集成、需要实时反馈的 Agent。

## 1.6 设计思想总结

如果我要自己构建一个 Agent 系统，编排循环部分的设计 checklist 是什么？

### 必须做（底线）

| Check | 项目 | 说明 |
|-------|------|------|
| ☐ | ReAct 主循环 | `while` 循环推进"推理→工具执行→结果回灌→再推理" |
| ☐ | 循环终止条件 | 主出口：模型不再请求工具；兜底出口：最大迭代次数 |
| ☐ | 迭代预算 | 防止模型死循环，必须设置硬上限 |
| ☐ | 工具执行与结果回灌 | 将 tool_calls 的执行结果追加到 messages 中 |
| ☐ | 消息序列合法性检查 | 修复孤儿 tool result、合并相邻 user 消息等 |

### 视场景而定（加分项）

| 场景 | 推荐设计 | 参考项目 |
|------|---------|---------|
| 多用户网关服务 | 线程级中断 + 工具级并发 + 双层队列 | Hermes + OpenClaw |
| 生产级 7×24 运行 | 分层恢复链 + 模型降级 + compaction 快照回退 | OpenClaw |
| 个人助手 / 聊天机器人 | 纯函数内循环 + error 不入历史 + 全局锁串行 | nanobot |
| IDE 集成 / 流式 UI | 流式事件解析 + doom loop 检测 + 子任务内联 | OpenCode |
| 预算耗尽用户体验 | Grace call（最后一次无工具总结） | Hermes |
| 多入口复用（CLI + Chat + Cron） | 消息泵与推理状态机分离两层 | nanobot |

### 最重要的三条经验

1. **对模型的信任程度与部署场景正相关**：个人助手可以信任 `has_tool_calls`，网关服务不能——必须加 grace call、恢复链、错误分类。

2. **循环终止的信任谁，决定了系统的稳定性上限**：nanobot 和 OpenCode 完全信任模型的协议字段；Hermes 和 OpenClaw 更不信任模型，加了额外的兜底。这个选择直接影响框架的稳定性上限。

3. **并发模型决定了能力天花板**：Hermes 的线程模型支持工具级并发，OpenClaw 的双层队列支持会话级并发。在"让 Agent 同时做多件事"这个方向上，并发设计比算法设计更重要。
