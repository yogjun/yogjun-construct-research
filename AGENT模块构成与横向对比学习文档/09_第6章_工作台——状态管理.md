# 第6章 工作台——状态管理

> "实习生小李的工位上永远摆着三样东西：正在用的文件（桌面）、归档的文件夹（抽屉）、和一块写着'外出中/在岗'的状态牌。Agent 的状态管理，就是这套'桌面 + 抽屉 + 状态牌'的组合——让系统知道'我现在在干什么''之前干了什么''万一断电了能不能恢复'。"

---

## 6.1 开篇故事：小李的工作台

早上 9:00，实习生小李坐到工位上。他的工作台有三层：

**桌面（运行时状态）**：今天正在处理的竞品调研报告、打开的浏览器标签、写到一半的 Excel 表格——这些东西如果咖啡洒了，他可以快速重来，但丢了会很麻烦。

**抽屉（持久化状态）**：过去三个月的所有项目文档、会议纪要、邮件往来。即使小李出差一周，回来打开抽屉，所有东西都在原处。

**状态牌（状态机）**：小李座位旁有一块小牌子，翻过来是"在岗"，翻过去是"外出中"。同事路过看一眼就知道能不能找他讨论问题，不会在他去洗手间的时候狂发消息。

这天下午，公司突然停电了。来电后，小李发现：
- **桌面上的东西丢了**：写到一半的表格没保存，需要重做
- **抽屉里的东西完好**：所有归档文档都在
- **状态牌被同事翻了回来**：同事以为他回来了，其实他在楼下买咖啡

Agent 的状态管理要解决的就是类似的问题：
1. **运行时状态怎么管**——Agent 正在执行的循环、当前的迭代次数、用户有没有喊停
2. **持久化状态怎么存**——对话历史、会话元数据，进程重启后能不能恢复
3. **状态怎么同步**——UI 怎么知道 Agent 是在"思考中"还是"已空闲"

不同项目对这三层的设计截然不同：有的把"抽屉"做成 SQLite 数据库，有的用 JSONL 文本文件；有的给每个会话配一把锁，有的用全局锁；有的状态牌能广播给全公司，有的只贴在工位上。

## 6.2 业务概念：状态管理是什么

**状态管理（State Management）**是 Agent 系统的"工作台"，负责维护 Agent 在运行期、持久化层和跨组件之间的全部可变数据，并保证这些数据在并发、故障、重启等场景下的一致性。

### 技术定义

状态管理包含三个核心层级：

1. **运行时状态（Runtime State）**：进程内存中的可变数据，如当前迭代次数、中断信号、活动描述、API 调用计数等。特点是读写极快，但进程崩溃即丢失。
2. **持久化状态（Persistent State）**：落盘存储的会话数据，如消息历史、会话元数据、Token 统计等。特点是可跨进程共享、可崩溃恢复，但读写有 I/O 开销。
3. **状态同步机制（State Synchronization）**：将状态变更广播给 UI、监控、其他组件的通道，如事件总线、心跳定时器、状态机。

> 💡 **名词解释：状态机（State Machine）**
>
> 通俗地说：实习生的状态牌只有三种状态——"在岗""外出中""请勿打扰"。状态机就是一套规则，规定什么条件下可以从"在岗"变成"请勿打扰"，以及每个状态下能做什么、不能做什么。
>
> 技术定义：一种数学计算模型，由有限个状态、状态之间的转移条件和转移动作组成。在 Agent 系统中，状态机用于精确控制会话的生命周期（如 idle → busy → retry → idle），防止非法状态转移导致的逻辑错误。

### 一句话说清边界

- **状态管理负责**：会话的创建/读取/更新/删除、运行时变量的维护、状态变更的广播、崩溃后的恢复
- **状态管理不负责**：具体消息怎么生成（那是 Prompt 构建）、工具怎么执行（那是工具系统）、循环怎么推进（那是编排循环）

### 没有状态管理会怎样？

如果把状态管理从 Agent 中拿掉：

- 用户发了三条消息，Agent 每次都会"失忆"——因为它没有持久化对话历史
- 两个用户同时发消息，Agent 的回答可能互相串台——因为没有并发隔离
- UI 上永远显示"思考中"，即使 Agent 早就完成了——因为没有状态广播
- 进程重启后，所有进行中的任务全部丢失——因为没有持久化恢复机制

## 6.3 必要设计：所有 Agent 都必须有的"底线"

从四个项目中提炼共性，状态管理的**最小可行实现**只需要以下四个要素：

### 要素一：会话数据结构

一个能标识会话、存储消息列表、记录元数据的对象。没有它，Agent 无法区分"这是用户 A 的问题还是用户 B 的问题"。

### 要素二：持久化机制

将消息历史写入磁盘，支持进程重启后的恢复。格式可以是 JSONL、SQLite、甚至纯文本——但必须有。

### 要素三：并发控制

防止同一时刻多个请求修改同一会话状态。最简单的方案是一把全局锁；复杂的系统需要每会话锁或分布式锁。

### 要素四：状态广播

当会话状态变化时（开始处理/完成/出错），通知 UI 或其他组件。最简单的方式是内存中的回调函数；复杂的系统需要事件总线。

```python
# 所有 Agent 都必须有的"最小可行状态管理"
# 就像实习生工作台的"最低配置清单"

@dataclass
class Session:
    """会话数据结构——工位上的文件夹"""
    key: str                      # 唯一标识，如 "user_123"
    messages: list[dict] = field(default_factory=list)
    created_at: datetime = field(default_factory=datetime.now)

class SessionStore:
    """持久化存储——抽屉的锁和钥匙"""
    
    def __init__(self, workspace: Path):
        self.workspace = workspace
        self._cache: dict[str, Session] = {}   # 内存缓存——桌面
        self._lock = asyncio.Lock()             # 并发控制——一次只让一个人翻抽屉
    
    def get_or_create(self, key: str) -> Session:
        # 先瞄一眼桌面有没有——有就直接用
        if key in self._cache:
            return self._cache[key]
        # 桌面上没有，去抽屉里翻——翻到了摆到桌面上
        session = self._load_from_disk(key)
        if session is None:
            session = Session(key=key)          # 新文件夹，现做
        self._cache[key] = session
        return session
    
    def save(self, session: Session) -> None:
        # 把桌面上的文件归档回抽屉
        self._write_to_disk(session)
        self._cache[session.key] = session      # 缓存同步更新
    
    async def process_message(self, key: str, message: str):
        # 处理消息前先把工位锁上——防止同事同时翻同一个抽屉
        async with self._lock:
            session = self.get_or_create(key)
            session.messages.append({"role": "user", "content": message})
            # ... 调用 LLM、执行工具 ...
            self.save(session)                   # 做完归档
            self._notify_status(key, "done")     # 状态广播——翻一下状态牌
    
    def _notify_status(self, key: str, status: str):
        # 最简单的状态广播：打印到日志
        # 复杂系统会换成 WebSocket、EventBus、消息队列
        print(f"Session {key} status: {status}")
```

**这就是"底线"**。少于这四点，Agent 的状态管理就不完整：

| 要素 | 少了会怎样 |
|------|-----------|
| 会话数据结构 | 无法区分不同用户/不同对话，消息全部混在一起 |
| 持久化机制 | 进程重启后所有历史丢失，用户感觉 Agent"失忆" |
| 并发控制 | 多请求同时修改同一会话，消息交错、文件损坏 |
| 状态广播 | UI 无法感知 Agent 进度，用户不知道是在思考还是卡死 |

## 6.4 四个项目的实现对比

四个框架在"底线"之上，各自扩展了不同的能力维度。本节用伪代码展示它们的核心差异。

### Hermes Agent：SQLite 双轨架构 + 声明式 Schema 调和

**设计定位**：运行时状态放内存，持久化状态用 SQLite WAL + 随机抖动重试——适合多进程并发、需要全文检索的网关型 Agent。

> 💡 **名词解释：WAL 模式（Write-Ahead Logging）**
>
> 通俗地说：公司改规章制度时，不是直接涂改原文件，而是先写一份"变更草案"。等草案确认无误后，再合并到正式文件中。这样多人同时提修改意见时不会互相覆盖。
>
> 技术定义：SQLite 的一种日志模式。写操作先追加到独立的 WAL 文件，而非直接修改数据库文件。这允许多个 reader 与一个 writer 并发工作，避免了传统 rollback journal 的读写互斥。

> 💡 **名词解释：声明式 Schema 调和（Declarative Schema Reconciliation）**
>
> 通俗地说：公司的人事档案表需要加一列"远程办公状态"。传统做法是写一份"迁移脚本"，逐个工位去改。Hermes 的做法是：在"标准档案模板"上加一列，系统启动时自动对比每个员工的档案，缺列的就补上——不需要手动跑脚本。
>
> 技术定义：以 `SCHEMA_SQL` 字符串为唯一真实来源，启动时通过内存 SQLite 解析目标列定义，再与现有表执行 `PRAGMA table_info` 对比，自动执行 `ALTER TABLE ADD COLUMN` 补齐缺失列。新增字段只需改 `SCHEMA_SQL`，无需手写迁移脚本。

> 💡 **名词解释：随机抖动重试（Jittered Retry）**
>
> 通俗地说：电梯高峰期，如果所有人都在 5 秒后按按钮，电梯门永远关不上。Hermes 让每个人等一个随机时间（20-150 毫秒）再按，大大降低了同时抢电梯的概率。
>
> 技术定义：在应用层实现写竞争重试，每次重试前 `sleep(random.uniform(0.02, 0.15))`。避免 SQLite 内置 busy handler 的确定性退避导致的" thundering herd "（惊群）问题。

**关键源码位置**：
- SQLite WAL 与写重试：`hermes_state.py:182-258`
- 声明式 Schema 调和：`hermes_state.py:296-382`
- 运行时状态（AIAgent 内存态）：`run_agent.py:1020-1280`
- 消息原子替换：`hermes_state.py:1353-1430`
- 全文检索（FTS5）：`hermes_state.py:1713-1957`

```python
# Hermes 的状态管理：像一家大型公司的"档案管理中心"
# 运行时状态在桌面上，持久化状态在带锁的保险柜里

class SessionDB:
    def __init__(self, db_path):
        self._conn = sqlite3.connect(str(db_path), timeout=1.0, isolation_level=None)
        self._conn.execute("PRAGMA journal_mode=WAL")   # ① WAL 模式：多人可读，一人可写
        self._lock = threading.Lock()
        self._init_schema()                              # ② 启动时自动调和 Schema
    
    def _execute_write(self, fn):
        """带随机抖动的写重试——防止多进程抢锁"""
        for attempt in range(15):                        # 最多试 15 次
            try:
                with self._lock:                         # 线程级互斥
                    self._conn.execute("BEGIN IMMEDIATE")  # ③ 事务开始即抢写锁
                    result = fn(self._conn)
                    self._conn.commit()
                # 每 50 次写做一次 WAL 合并——防止日志文件无限膨胀
                self._write_count += 1
                if self._write_count % 50 == 0:
                    self._try_wal_checkpoint()
                return result
            except sqlite3.OperationalError as exc:
                if "locked" in str(exc).lower():
                    # ④ 随机抖动：20-150ms，打破惊群
                    time.sleep(random.uniform(0.02, 0.15))
                    continue
                raise
    
    def _init_schema(self):
        """声明式 Schema 调和——加列只需改 SCHEMA_SQL"""
        cursor = self._conn.cursor()
        cursor.executescript(SCHEMA_SQL)                 # 创建基础表
        self._reconcile_columns(cursor)                  # 自动补齐缺失列
        # 版本门控：数据迁移（如 FTS 索引回填）按 state_meta 版本执行
        self._run_version_gated_migrations(cursor)
    
    def append_message(self, session_id, role, content, ...):
        """追加消息并更新计数器"""
        def _do(conn):
            cursor = conn.execute(
                "INSERT INTO messages (session_id, role, content, ...) VALUES (...)",
                (...)
            )
            # 同步更新会话的消息计数——不需要额外查表
            conn.execute(
                "UPDATE sessions SET message_count = message_count + 1 WHERE id = ?",
                (session_id,)
            )
            return cursor.lastrowid
        return self._execute_write(_do)
    
    def replace_messages(self, session_id, messages):
        """原子替换——/retry、/undo、/compress 用"""
        def _do(conn):
            conn.execute("DELETE FROM messages WHERE session_id = ?", (session_id,))
            conn.execute("UPDATE sessions SET message_count=0 WHERE id = ?", (session_id,))
            for msg in messages:
                conn.execute("INSERT INTO messages ...", (...))  # 批量重建
        self._execute_write(_do)                         # ⑤ 整个替换是一个事务

# AIAgent 运行时状态（内存态）
class AIAgent:
    def __init__(self, ...):
        self.iteration_budget = IterationBudget(max_iterations)  # 迭代预算
        self._interrupt_requested = False      # 用户喊停的信号旗
        self._last_activity_ts = time.time()   # 最后活动时间——用于运维观测
        self._api_call_count = 0               # 已调用 API 次数
        self._session_db = session_db          # 持久化句柄
        self._last_flushed_db_idx = 0          # 已刷盘的消息索引——增量持久化
```

### nanobot：JSONL 文件 + 全局锁 + 后台任务调度

**设计定位**：单用户个人助手，用人类可读的 JSONL 替代数据库，全局锁保平安——简单即正确。

> 💡 **名词解释：JSONL（JSON Lines）**
>
> 通俗地说：不是把所有记录塞进一个大表格（JSON 对象），而是每行一条记录，像写日记一样一行一行写。这样即使文件末尾损坏了，前面的记录还能读。
>
> 技术定义：一种文本格式，每行是一个独立的 JSON 对象。相比单文件 JSON，它支持流式读取、追加写入、损坏局部化；相比 SQLite，它零依赖、人类可读、无需 schema 迁移。

> 💡 **名词解释：`last_consolidated` 索引**
>
> 通俗地说：小李的笔记本上，前 50 页已经拍照存档（固化到 MEMORY.md），后面 10 页还在用。`last_consolidated = 50` 就是一个书签，告诉他"从第 51 页开始是新的"。
>
> 技术定义：Session 对象内部的一个整数字段，标记已固化到 `MEMORY.md/HISTORY.md` 的消息数量。`get_history()` 从该索引处切片，只返回未固化消息给 LLM，避免重复提交已归档内容。

> 💡 **名词解释：后台任务调度（Background Task Scheduling）**
>
> 通俗地说：小李写完报告后，把"整理归档"这件事记在便利贴上，贴在显示器边缘。等他不忙的时候再做，而不是让客户等着他归档完再回复。
>
> 技术定义：将耗时的非关键操作（如记忆固化、消息归档）从用户响应路径中剥离，通过 `asyncio.create_task` 在事件循环空闲时执行。通过 `_background_tasks` 列表跟踪，确保优雅关闭时等待所有后台任务完成。

**关键源码位置**：
- Session 数据结构与 JSONL 持久化：`session/manager.py:16-214`
- 全局锁与消息派发：`agent/loop.py:97-104,311-331`
- 后台任务调度：`agent/loop.py:345-349,379-380,446`

```python
# nanobot 的状态管理：像一个个人助理的"简约工作台"
# 抽屉是 JSONL 文本文件，锁只有一把，归档等不忙时再做

@dataclass
class Session:
    key: str
    messages: list[dict] = field(default_factory=list)
    last_consolidated: int = 0    # ① 固化索引——"已拍照存档到第几页"
    
    def get_history(self, max_messages=500):
        # 只返回未固化的消息——避免把存档内容重复发给 LLM
        unconsolidated = self.messages[self.last_consolidated:]
        sliced = unconsolidated[-max_messages:]
        # 去掉开头的非 user 消息——防止工具结果"孤儿化"
        for i, m in enumerate(sliced):
            if m.get("role") == "user":
                sliced = sliced[i:]
                break
        return sliced
    
    def clear(self):
        # 清空时索引同步归零——书签和笔记本一起重置
        self.messages = []
        self.last_consolidated = 0

class SessionManager:
    def __init__(self, workspace):
        self.sessions_dir = workspace / "sessions"
        self._cache: dict[str, Session] = {}   # ② 内存缓存——无过期、无大小限制
    
    def save(self, session):
        """全量覆写 JSONL——简单但 O(n)"""
        path = self._get_session_path(session.key)
        with open(path, "w", encoding="utf-8") as f:
            # 第一行是元数据——list_sessions() 只需读这一行
            metadata = {
                "_type": "metadata",
                "key": session.key,
                "last_consolidated": session.last_consolidated,
                ...
            }
            f.write(json.dumps(metadata) + "\n")
            for msg in session.messages:
                f.write(json.dumps(msg) + "\n")   # ③ 每消息一行，损坏只影响单行
        self._cache[session.key] = session       # 写盘后更新缓存

class AgentLoop:
    def __init__(self, ...):
        self._processing_lock = asyncio.Lock()   # ④ 全局唯一锁——所有会话共享
        self._background_tasks: list[asyncio.Task] = []
    
    async def _dispatch(self, msg):
        """任何消息处理前必须先获取全局锁"""
        async with self._processing_lock:        # 一次只处理一条消息
            response = await self._process_message(msg)
            ...
    
    def _schedule_background(self, coro):
        """把耗时操作挂到显示器边缘的便利贴上"""
        task = asyncio.create_task(coro)
        self._background_tasks.append(task)
        task.add_done_callback(self._background_tasks.remove)  # 做完撕掉便利贴
    
    async def _process_message(self, msg):
        session = self.sessions.get_or_create(msg.session_key)
        ...
        self._save_turn(session, all_msgs, ...)
        self.sessions.save(session)
        # ⑤ 记忆固化移出主路径——客户不用等归档
        self._schedule_background(
            self.memory_consolidator.maybe_consolidate_by_tokens(session)
        )
```

### OpenClaw：三层分层状态 + 跨进程写锁 + ACP 运行时缓存

**设计定位**：状态按生命周期分层——磁盘存元数据、内存存运行时、临时缓冲不持久化。适合 7×24 小时运行的生产级网关。

> 💡 **名词解释：跨进程写锁（Cross-Process Write Lock）**
>
> 通俗地说：公司档案室的门锁不是普通的室内锁，而是能跨楼层感知的电子锁。即使有人在三楼打开了档案柜，二楼的人也能看到"已上锁"，不会强行撬开。
>
> 技术定义：OpenClaw 用 `fs.open(wx)` 创建独占锁文件实现跨进程互斥，并处理了 PID 回收、孤儿锁清理、Windows 非原子 rename 等边界情况。锁文件内记录 PID 和进程启动时间，防止 Linux PID 回收导致的误判。

> 💡 **名词解释：ACP 运行时缓存（ACP Runtime Cache）**
>
> 通俗地说：公司有几个长期合作的外包团队（ACP 后端），每次项目都重新签合同、交押金很慢。OpenClaw 把"已签好的合同"缓存起来，新项目如果条件一样就直接复用，但长期不用的合同会自动销毁以节省管理费。
>
> 技术定义：在进程内缓存 ACP 后端运行时句柄，通过四维键（backend + agent + mode + cwd）校验缓存有效性。空闲句柄超过 `idleTtlMs` 后主动关闭，防止资源泄漏和 `maxConcurrentSessions` 超限。

> 💡 **名词解释：增量广播节流（Delta Broadcast Throttling）**
>
> 通俗地说：助理在打字，如果每敲一个字母就广播一次，公司的广播系统会瘫痪。OpenClaw 每 150 毫秒广播一次"到目前为止打了什么"，既让用户看到实时进度，又不压垮网络。
>
> 技术定义：在流式 LLM 响应场景下，控制向 WebSocket 客户端广播 assistant 增量文本的频率。`emitChatDelta` 在 150ms 内合并多个 token，并处理前缀重叠去重。

```typescript
class AcpSessionManager {
    private async ensureRuntimeHandle(params) {
        // 尝试缓存命中——四维键校验
        const cached = this.getCachedRuntimeState(params.sessionKey)
        if (cached && backendMatches && agentMatches && modeMatches && cwdMatches) {
            return { runtime: cached.runtime, handle: cached.handle }  // ② 复用合同
        }

        this.enforceConcurrentSessionLimit(params.cfg, params.sessionKey)
        
        // 缓存未命中：重新签合同
        const ensured = await runtime.ensureSession({...})
        this.setCachedRuntimeState(params.sessionKey, {
            runtime, handle: nextHandle, backend, agent, mode, cwd,
        })
        return { runtime, handle: nextHandle }
    }
    
    private async evictIdleRuntimeHandles(params) {
        // ③ 空闲驱逐：长期不用的合同自动销毁
        const candidates = this.runtimeCache.collectIdleCandidates({ maxIdleMs, now })
        for (const candidate of candidates) {
            // 双重检查：加入队列后可能又收到了新请求
            const lastTouched = this.runtimeCache.getLastTouchedAt(candidate.actorKey)
            if (now - lastTouched < idleTtlMs) continue
            
            this.runtimeCache.clear(candidate.actorKey)
            await cached.runtime.close({ handle: cached.handle, reason: "idle-evicted" })
        }
    }

const emitChatDelta = (sessionKey, clientRunId, text) => {
    const mergedText = resolveMergedAssistantText({ previousText, nextText: text })

function createRunStateMachine(params) {
    let activeRuns = 0
    let heartbeat = null
    
    return {
        onRunStart() {
            activeRuns += 1
            publish()                          // 立即广播状态变更
            // ⑤ 运行期间每 60s 心跳一次——防止"卡死"误判
            if (!heartbeat) {
                heartbeat = setInterval(() => publish(), 60_000)
                heartbeat.unref?.()            // 不阻止进程退出
            }
        },
        onRunEnd() {
            activeRuns = Math.max(0, activeRuns - 1)
            if (activeRuns <= 0) clearInterval(heartbeat)
            publish()
        }
    }
}
```

### OpenCode：三层隔离 + AbortSignal + 双模事件总线

**设计定位**：状态按"进程 → 目录 → 会话"三层隔离，AbortSignal 作为跨库取消协议，Bus 同时服务 Instance 内订阅和跨进程广播——适合 IDE 集成、多工作区并发的场景。

> 💡 **名词解释：Instance.state（目录级状态缓存）**
>
> 通俗地说：公司给每个项目组一间独立的办公室。同一套办公设备（init 函数）在同一个项目组只采购一次，不同项目组之间完全隔离——A 组的咖啡机坏了不影响 B 组。
>
> 技术定义：以项目目录（`root()`）为 key 的双层 Map 结构。同一初始化函数在同一目录下只执行一次，返回的状态对象被缓存。Instance reload 时自动调用 `dispose` 钩子清理资源。

> 💡 **名词解释：AbortSignal（取消信号）**
>
> 通俗地说：实习生接到任务后，主管给他发了一个"可随时响的铃铛"。如果主管摇铃，实习生立刻停下手头所有事——不管他是在查资料、写报告还是等电梯。这个铃铛是公司的标准装备，所有部门都认得。
>
> 技术定义：Web 标准的取消机制（`AbortController` + `AbortSignal`）。OpenCode 将其传递给所有异步操作（LLM.stream、工具执行等），用户点击"取消"时统一触发，避免各层自定义取消协议的碎片化。

> 💡 **名词解释：双模事件总线（Dual-Mode Event Bus）**
>
> 通俗地说：公司有两个广播系统——一个是楼层内的对讲机（Instance 内订阅），一个是跨楼层的公共广播（GlobalBus）。发通知时两个系统同时响，确保无论同事在哪个楼层都能收到。
>
> 技术定义：`Bus.publish` 既向 Instance 内的订阅者分发（内存 Map），又向 `GlobalBus`（进程级 EventEmitter）发射。支持 Electron 等多进程架构，wildcard 订阅（`*`）实现 topic 通配符匹配。

- SessionStatus 状态机：`session/status.ts:7-75`
- SessionPrompt 生命周期管理：`session/prompt.ts:66-85,239-284`
- Instance.state 目录级缓存：`project/state.ts`
- Bus 双模事件总线：`bus/index.ts`

```typescript
// OpenCode 的状态管理：像一个和设计软件深度集成的"工作室"
// 每个项目组（目录）有独立办公室，铃铛（AbortSignal）是标准装备

// ── Layer 1: 进程级 —— GlobalBus 跨进程广播 ──
// Bus.publish 同时走两条路：Instance 内订阅 + GlobalBus 跨进程
export namespace Bus {
    export async function publish(def, properties) {
        const payload = { type: def.type, properties }
        // ① 楼层内对讲机：按事件类型分发
        for (const key of [def.type, "*"]) {
            const match = state().subscriptions.get(key)
            for (const sub of match ?? []) pending.push(sub(payload))
        }
        // ② 跨楼层广播：支持 Electron 多进程
        GlobalBus.emit("event", { directory: Instance.directory, payload })
        return Promise.all(pending)
    }
}

// ── Layer 2: 目录级 —— Instance.state 隔离 ──
export namespace State {
    const recordsByKey = new Map<string, Map<any, Entry>>()
    
    export function create<S>(root, init, dispose?) {
        return () => {
            const key = root()                           // 项目组名称（目录路径）
            let entries = recordsByKey.get(key)
            if (!entries) {
                entries = new Map()
                recordsByKey.set(key, entries)
            }
            // ③ 同一套设备在同一项目组只采购一次
            const exists = entries.get(init)
            if (exists) return exists.state as S
            
            const state = init()
            entries.set(init, { state, dispose })
            return state
        }
    }
    
    export async function dispose(key) {
        // 项目组解散时，自动调用所有 dispose 钩子
        const entries = recordsByKey.get(key)
        for (const [init, entry] of entries) {
            if (entry.dispose) await entry.dispose(entry.state)
        }
        recordsByKey.delete(key)
    }
}

// ── Layer 3: 会话级 —— SessionStatus 状态机 + SessionPrompt 生命周期 ──
export namespace SessionStatus {
    // 三态设计：idle（空闲）/ busy（忙碌）/ retry（重试中）
    export const Info = z.union([
        z.object({ type: z.literal("idle") }),
        z.object({ type: z.literal("retry"), attempt: z.number(), message: z.string(), next: z.number() }),
        z.object({ type: z.literal("busy") }),
    ])
    
    const state = Instance.state(() => {
        const data: Record<string, Info> = {}
        return data
    })
    
    export function set(sessionID, status) {
        Bus.publish(Event.Status, { sessionID, status })  // ④ 状态变更即时广播
        if (status.type === "idle") {
            delete state()[sessionID]                       // 空闲时释放内存
            return
        }
        state()[sessionID] = status
    }
}

export namespace SessionPrompt {
    // 按 sessionID 存储 AbortController 与回调队列
    const state = Instance.state(
        () => {
            const data: Record<string, { abort: AbortController; callbacks: { resolve; reject }[] }> = {}
            return data
        },
        async (current) => {
            // ⑤ dispose 钩子：Instance reload 时自动取消所有运行中的操作
            for (const item of Object.values(current)) item.abort.abort()
        }
    )
    
    export function assertNotBusy(sessionID) {
        // 防止同一 Session 上并行触发多个 loop
        if (state()[sessionID]) throw new Session.BusyError(sessionID)
    }
    
    function start(sessionID) {
        const s = state()
        if (s[sessionID]) return                    // 已存在？复用（单例运行）
        const controller = new AbortController()
        s[sessionID] = { abort: controller, callbacks: [] }
        return controller.signal                   // ⑥ 标准铃铛，传给所有异步操作
    }
    
    export const loop = fn(LoopInput, async (input) => {
        const abort = start(input.sessionID)
        using _ = defer(() => cancel(input.sessionID))  // ⑦ 退出时自动清理
        
        while (true) {
            SessionStatus.set(sessionID, { type: "busy" })
            if (abort.aborted) break                    // 铃铛响了，立刻停
            
            const stream = await LLM.stream({ messages, tools, abort })  // 传给 LLM
            for await (const event of stream.fullStream) {
                // ... 处理事件
            }
        }
    })
}
```

## 6.5 独特高价值设计：各项目的闪光点

每个项目都因为特定的场景诉求，做了其他项目没有做的高价值设计。

### Hermes Agent：声明式 Schema 调和

`SCHEMA_SQL` 是数据库 schema 的唯一真实来源，启动时通过内存 SQLite 解析并与现有表对比，自动执行 `ALTER TABLE ADD COLUMN` 补齐缺失列（`hermes_state.py:339-382`）。

**解决的问题**：传统迁移脚本需要严格按版本号顺序执行，一旦版本号错乱或跳过，就会导致列缺失。声明式调和让"加列"变成纯声明操作——改 `SCHEMA_SQL` 即可，无需关心当前数据库版本。

**什么场景值得借鉴**：任何使用 SQLite 且需要频繁迭代 schema 的项目。尤其是网关型 Agent，CLI 实例和 Gateway 实例可能运行不同版本的代码，自动调和避免了手动迁移的运维负担。

### Hermes Agent：FTS5 双索引策略

针对 CJK（中文/日文/韩文）文本的检索需求，Hermes 同时维护 `messages_fts`（unicode61 tokenizer）和 `messages_fts_trigram`（trigram tokenizer）两个虚拟表（`hermes_state.py:103-156`）。搜索时先查 unicode61，无结果再降级到 trigram，最后 fallback 到 `LIKE` 子串匹配。

**解决的问题**：unicode61 对无空格分词语言（如中文）效果极差，会把"竞品调研"拆成"竞""品""调""研"四个独立 token，导致短语搜索失败。trigram 通过重叠三字节序列实现子串匹配，弥补了这一问题。

**什么场景值得借鉴**：任何需要支持中文/日文/韩文全文检索的 Agent 系统。

### nanobot：`last_consolidated` 索引与数据一致性

将固化索引作为 `Session` 的内部字段（`session/manager.py:33`），而非外置在 `SessionManager` 中。`clear()` 同时重置 `messages` 和 `last_consolidated`（`manager.py:68-69`），彻底消除"索引-数据"分离带来的同步风险。

**解决的问题**：如果索引外置，清空会话时需要跨对象更新两处状态，任何遗漏都会导致 `get_history()` 返回越界切片或空历史。

**什么场景值得借鉴**：所有需要"活跃数据 + 归档边界"设计的系统。将边界索引与数据绑定在同一对象内，是最简单且最可靠的方案。

### nanobot：后台任务调度

`_schedule_background()` 将记忆固化（涉及 LLM 调用 + 磁盘写入）从用户响应路径中剥离（`agent/loop.py:345-349`）。`_background_tasks` 列表跟踪所有后台任务，`close_mcp()` 时通过 `asyncio.gather` 等待全部完成。

**解决的问题**：如果记忆固化阻塞在主路径中，用户会感知到明显的回复延迟。后台调度让"即时响应"和"完整归档"两全。

**什么场景值得借鉴**：任何需要在响应用户的同时执行耗时维护操作（如日志归档、索引更新、数据同步）的系统。

### OpenClaw：跨进程写锁

用 `fs.open(wx)` 创建独占锁文件实现跨进程互斥，并记录 PID + 进程启动时间用于检测孤儿锁（`agents/session-write-lock.ts:444-553`）。Windows 下额外实现 5 次重试（`store.ts:466-484`）。

**解决的问题**：Node.js 的 `fs.writeFile` 不是原子的，多进程并发写入 `sessions.json` 会导致文件损坏。简单的文件存在性检查无法应对 PID 回收（Linux 上 PID 可能被新进程复用）。

**什么场景值得借鉴**：任何多进程共享同一文件存储的系统。尤其是 Gateway 场景，主进程和 worker 进程可能同时读写会话数据。

### OpenClaw：ACP 运行时缓存的四维键校验

`ensureRuntimeHandle` 用 backend + agent + mode + cwd 四个维度校验缓存有效性（`acp/control-plane/manager.core.ts:904-910`）。任一维度变化都会使缓存失效，避免"旧合同用于新项目"的配置漂移。

**解决的问题**：ACP 后端初始化成本高，缓存是必要的；但如果用户切换了 agent 或工作目录，复用旧句柄会导致行为异常。

**什么场景值得借鉴**：任何缓存"外部连接句柄"的系统。缓存键必须包含所有影响行为的配置维度，否则缓存命中即 bug。

### OpenCode：AbortSignal 作为跨库取消协议

将 `AbortController.signal` 传递给 LLM.stream、工具执行等所有异步操作（`session/prompt.ts:239-284`）。这是 Web 标准，与 ai SDK 原生兼容，避免了各层自定义取消协议的碎片化。

**解决的问题**：如果 LLM 层用 `AbortSignal`、工具层用自定义 `cancel()` 函数、UI 层用事件回调，取消操作需要三层转换，极易遗漏。

**什么场景值得借鉴**：任何使用 TypeScript/JavaScript 构建、需要与多个第三方库（ai SDK、fetch、stream）集成的 Agent 系统。

### OpenCode：Instance.state 的 dispose 钩子

`Instance.state` 支持传入 `dispose` 回调，在 Instance reload 或项目切换时自动清理资源（`project/state.ts:31-69`）。`SessionPrompt.state` 的 dispose 钩子会取消所有运行中的 AbortController（`session/prompt.ts:80-83`）。

**解决的问题**：IDE 场景下用户频繁切换项目目录，如果旧项目的 AbortController 和事件订阅没有被清理，会导致内存泄漏和幽灵回调。

**什么场景值得借鉴**：任何需要"热切换"上下文（如 IDE 多工作区、浏览器多标签页）的系统。

| 频繁迭代 schema | 声明式 Schema 调和 | Hermes |
| 需要全文检索（含中文） | FTS5 双索引（unicode61 + trigram） | Hermes |
| 单用户个人助手 | JSONL + 全局锁 + 后台任务调度 | nanobot |
| 记忆固化与响应分离 | `_schedule_background` + 任务排空 | nanobot |
| 7×24 生产级网关 | 跨进程写锁 + ACP 运行时缓存 + 空闲驱逐 | OpenClaw |
| 流式 UI 实时反馈 | 增量广播节流（150ms）+ 心跳 | OpenClaw |
| IDE 集成 / 多工作区 | Instance.state 目录级隔离 + dispose 钩子 | OpenCode |
| 跨库取消一致性 | AbortSignal 标准协议 | OpenCode |
| 多进程事件广播 | Bus 双模（Instance 内 + GlobalBus） | OpenCode |

### 最重要的三条经验

1. **持久化策略与数据生命周期匹配**：元数据低频写、需恢复 → 磁盘；运行时句柄高频读、可重建 → 内存缓存；临时流式数据低价值、可丢失 → 纯内存。不要试图用一种存储解决所有问题。

2. **缓存键必须包含所有影响行为的维度**：OpenClaw 的四维键校验（backend + agent + mode + cwd）是最佳实践。缓存命中但配置不匹配，是比缓存未命中更隐蔽的 bug。

3. **取消协议越早标准化越好**：OpenCode 的 AbortSignal 策略值得所有 TypeScript 项目借鉴。如果各层用不同的取消机制，用户点击"停止"后，系统可能"表面停了、后台还在跑"。
